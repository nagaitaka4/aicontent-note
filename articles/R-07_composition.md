# READMEとは？AIと人間が共有する業務マニュアルの作り方

<!-- GEO対応：H2より前に直接回答を配置 -->
READMEとは、プロジェクトや業務の「最初に読んでほしいファイル」です。
もともとはエンジニアの文化から来た言葉ですが、AIと人間が一緒に仕事をする現場では、
「誰が読んでも同じように動ける業務マニュアル」として機能します。

## READMEとは何か。エンジニア文化から実務に入ってきた理由
→ 「README」の名前の由来・"Read Me"（まず読んでくれ）という意味から説明
→ なぜ今、非エンジニアにも関係があるか：AIツールがこの慣習を引き継いでいる

## AIと仕事をするときにREADMEが必要になる理由
→ AIは毎回セッションをリセットして会話を始める。「前回と同じで」が通じない
→ READMEを渡すことで「毎回ゼロから説明する手間」がなくなる
→ 実務での使い方：このブログの運用でCLAUDE.mdがその役割を果たしている

## READMEに書くべき5つの要素
→ ①このプロジェクト・業務の目的　②誰が使うか（役割）　③ファイル構成の概要
→ ④やってよいこと・禁止事項　⑤最終更新日
→ 「何でも書く」ではなく「AIが迷わないために書く」が判断基準

## 非エンジニアが書けるREADMEの具体的な書き方
→ 箇条書きと見出しだけで十分。Markdownが使えると見やすくなる
→ 「1回読んだAIがその通りに動けるか」を確認基準にする
→ 内部リンク：Markdownとは？AI時代に全員が使うべき理由を実務視点で解説（markdown-basics）

## READMEとGitを組み合わせると変わること
→ READMEを更新するたびコミットすれば「マニュアルの変更履歴」が残る
→ 「いつルールが変わったか」が記録に残る＝運用の経緯を追えるようになる
→ 内部リンク：Gitとは？AI時代の『変更履歴管理』を非エンジニア向けに解説（git-basics）

## 私が実際に使っているREADME（CLAUDE.md）の構成
→ このブログ運用で使っているCLAUDE.mdの設計思想を実務視点で解説
→ トンマナ・禁止事項・CTAの置き方・シリーズの定義など、実体験ベースで語る
→ 「AIへのプロンプトとREADMEは似ている」という接続
→ 内部リンク：プロンプトとは？AIに仕事を依頼する設計書の考え方（prompt-design-basics）

## READMEは「完成させる」ものではなく「育てる」もの
→ 最初から完璧なREADMEを書こうとしなくていい
→ 使いながら気づいたことを追記していくサイクルが属人化を防ぐ
→ 「業務が変わったらREADMEも変える」が習慣になると、ルールが生きたまま動き続ける
