## 構成（H1・H2・H3の骨格）

```markdown
# ルールファイルとは？AIを安定運用する指示書の考え方

<!-- GEO対応：H2より前に直接回答を配置 -->
ルールファイルとは、AIに常に守らせたいルール（トンマナ・禁止事項・判断基準）をまとめて
固定しておくファイルのことです。CLAUDE.mdのようにAIが自動で読み込む形にしておくことで、
毎回同じ指示を繰り返さなくても、同じ基準で判断・出力させられるようになります。

前回「テンプレートとは？AI業務で再現性を作る設計の考え方」では、作業の型をテンプレートに
することで再現性が生まれると書きました。ただし型だけでは「何を守るか」までは決まりません。
今回はその「守るべき基準」を固定するルールファイルの話です。

## ルールファイルとは何か。指示書という言葉の実務的な意味
→ 定義：口頭・チャットで毎回言うのではなく、ファイルに固定して常時読ませるもの
→ Claude Codeの例：プロジェクトルートにCLAUDE.mdを置くと自動で読み込まれる仕組み
→ 外部リンク：Claude Code公式ドキュメント「How Claude remembers your project」
　　（https://code.claude.com/docs/en/memory）を根拠として添える
→ 読者メリット（①反映）：「毎回同じルールを書き直さなくてもよくなることが、ルールファイル最大の価値です。」
　　という一文を定義の直後に入れる
→ 内部リンク：READMEとは？（readme-basics）
　　README＝前提を共有するもの／ルールファイル＝判断基準を固定するもの、と一言で役割を分け、
　　詳細な比較はreadme-basics側に委ねる（ここでは深掘りしない）

## ルールファイルがないと何が起きるか
<!-- 段落数リスク：4段落想定。まずブロック要素で圧縮。超える場合のみH3を1個検討 -->
→ 一般化した現象から入る（1〜2文）：AIは毎回同じミスを繰り返す／修正したはずなのに次回また戻る、という
　　誰もが経験しうる現象を先に提示する（②レビュー反映：実体験だけで始めると「自分には関係ない」と
　　感じられるリスクがあるため、一般論→実例の順にする）
→ 実体験フック：このメディアでも同じことが起きていた、として機械チェックスクリプトの穴の実例へつなぐ
　　（同じ種類の指摘＝文字数超過の見落としを何度も繰り返してしまった。2026-08-03、M-02執筆時に発覚）
→ 原因は「AIの精度不足」ではなく「チェックすべき基準がルール化・スクリプト化されていなかった」こと
→ この体験から言えること：ルールファイルは「賢く指示する道具」ではなく「同じ失敗を二度させない仕組み」

## ルールファイルに書くべきことの分類
<!-- ③レビュー反映：進行中タスクは独立分類にせず「運用ルール」の例に格下げ。5分類に整理 -->
<!-- ②2回目レビュー反映：「なぜ必要か」の理由列を追加し、応用しやすくする -->
→ 表で5分類を整理（理由列つき）：

| 分類 | 役割 | なぜ必要か | 例 |
|---|---|---|---|
| 目的 | なぜこのルールがあるかの軸 | 判断に迷わないため | メディアの方向性・トンマナ |
| 判断基準 | 迷ったときにどう判断するか | 人によって答えがブレないため | 優先順位・文体判断 |
| 禁止事項 | やってはいけないこと | 勝手な判断を防ぐため | 誇張表現・根拠のない断定 |
| 運用ルール | 日々の運用で決めていること | 属人化を防ぐため | 進行中タスクの管理・引き継ぎ方法 |
| チェック項目 | 抜け漏れを防ぐ確認事項 | 完成の基準を揃えるため（最後に確認する内容） | 文字数・内部リンク・CTA |

<!-- 3回目レビュー①反映：チェック項目は最後に確認する内容のため運用ルールの後ろへ移動 -->

→ 全部を1つのファイルに詰め込むと肥大化し、AIも人も「今どのルールが有効か」を追えなくなる
→ 次のH2への接続：分類ができたら、次は「どう分けて管理するか」

## ルールファイルは1つでは足りない。階層で管理する
<!-- ③レビュー反映：3層構造を表で示す（この記事の独自価値なので図解優先） -->
→ 表で3層構造を提示：

| 階層 | 役割 | 例 |
|---|---|---|
| CLAUDE.md | 全体方針・絶対ルール | メディアの軸・最優先の禁止事項 |
| rules/ | 毎回の作業で使う判断基準 | 記事制作フロー・X投稿フロー |
| knowledge/ | 参照するだけの固定情報 | WP設定・料金・カテゴリー一覧 |

→ なぜ分けたか：1ファイルに全部書くと、使う頻度が違う情報が混在し、AIが優先順位を誤りやすい
→ 内部リンク：AIでブログ構成を安定させる運用フロー（ai-composition-operation-flow）
　　実際の運用フローの中でルールファイルをどう確認しているかは、そちらで詳しく解説している旨を誘導
→ 締めの一文（③反映）：「役割ごとに分けることで、AIも人も必要なルールだけを参照しやすくなります。」
　　（次のH2＝運用面の話への橋渡し）

## ルールファイルは「一度読んだ記憶」で運用しない
→ このメディア自身が定めている運用ルール：ルールファイルは一度読んでいても、対象の作業に着手する直前に
　　毎回読み直す（セッションの経過時間やターン数を言い訳にしない）
→ なぜ必要か：AIも人も「知っているはず」という思い込みで古い基準のまま動いてしまうため
→ **【ポイント】ブロック化**（2回目レビュー④反映：シリーズを代表するメッセージのため、地の文の締めではなく
　　ブロック要素に格上げする）：
　　「【ポイント】<br>ルールファイルは"知っている"ことより"毎回確認する"ことに価値があります。」

## まとめ：ルールファイルは判断基準を固定する仕組み
<!-- ⑤レビュー反映：冒頭の直接回答と対応する表現に統一 -->
→ 締めの一文：「ルールファイルとは、AIを賢くするためではなく、判断基準を固定し、同じ失敗を
　　繰り返さないための仕組みです。」（冒頭のGEO直接回答と呼応させる）
→ シリーズ総括への橋渡し（⑥レビュー反映）：「ここまで扱ってきたプロンプト・コンテキスト・Markdown・
　　README・テンプレート・ルールファイルは、実はすべて『情報整理』という1つの考え方につながっています。」
→ 最終文（2回目レビュー⑤反映・R-01〜R-09の総括として最も強く締める）：
　　「AI運用は『良い指示を書くこと』ではなく、『良い判断基準を維持すること』に変わっていきます。」
→ R-10への伏線回収（3回目レビュー②反映）：
　　「そして、その判断基準を支えているのが、ここまで見てきた『情報整理』という考え方です。」
→ 次回予告：「なぜAI活用は情報整理が9割なのか」につなげる一文（R-10）
```
