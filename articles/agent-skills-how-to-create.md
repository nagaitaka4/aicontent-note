# Agent Skillsの作り方。ブログ運用の手順書で使う8つのコツ

==Agent Skillsは、AIに渡す業務の手順書です。==
Claude Codeなら、フォルダとSKILL.md 1枚で作れます。
大事なのは書式より中身で、判断基準を書き、数える作業はプログラムに任せ、公開は人が確認し、失敗した所を直して育てます。

---

## Agent Skillsとは：AIが必要なときに読む業務の手順書

==毎回守ってほしい前提はCLAUDE.md、特定の作業の手順はスキル、と分けて置きます。==
同じ指示を何度も貼っているなら、スキルにする合図です。

| | CLAUDE.md | スキル（SKILL.md） |
|---|---|---|
| **いつ読まれるか** | 毎回の会話の最初 | ==**「いつ使うか」の説明は毎回、本体は関係する作業のときだけ**== |
| **書くもの** | **毎回守る前提**（文体・使わない表現） | **1つの作業の手順**と判断基準 |
| **ブログ運用の例** | 「完璧より継続」「煽らない」 | アイキャッチの指示を作る手順 |

（出典：[Claude Code Docs「Claude をスキルで拡張する」](https://code.claude.com/docs/ja/skills)）

## Agent Skillsの作り方：フォルダとSKILL.md 1枚から

==フォルダを作り、SKILL.mdを書き、呼び出して確かめれば1本できます。==
置き場所は、使う範囲で2つです。

・**1つの作業フォルダだけで使う**：その作業フォルダの中の`.claude/skills/`<br>
・**どの作業フォルダでも使う**：自分のパソコンのユーザー用フォルダにある`.claude/skills/`

### 見本：アイキャッチの指示を作るスキル

私の手順書の多くは、CLAUDE.mdと、そこから読ませる別のファイルにあります。
「/名前」で呼べる形にしているのは一部で、アイキャッチの指示はその1つです。

今も昔の形式（`.claude/commands/`に置くファイル）のままですが、呼び方はスキルと同じです。
その中身を、初めて作る人向けにSKILL.mdの形へ簡略化したのが下の見本です。

作るときは、ブログの作業フォルダをClaude Codeで開き、下の見本を貼ってこう頼みます。
「.claude/skills/eyecatch-prompt/SKILL.mdを作って、この内容を保存して。フォルダが無ければ作って」

```
---
name: eyecatch-prompt
description: 記事と参考画像をもとに、アイキャッチ画像の指示文を作るときに使う
---

# 手順

1. 記事と参考画像を確認する
2. 対象の記事が曖昧なときだけ聞く
3. 記事に無いことは書かない
4. 画像を作るための指示文を1つ出す
```

`---`で囲んだ所のnameが「/」の後ろに打つ名前、descriptionが「いつ使うかの説明」です。
試すときは、Claude Codeに記事の内容と参考画像を渡して「/eyecatch-prompt」と打ちます。
指示文が1つ出るか、記事に無い内容が入っていないかを見ます。

【メモ】<br>
スキルが表示されないときは、「/reload-skills」と打つか、Claude Codeを開き直します。

## 8つのコツと、手順書に書く4つ（①〜④）

元にしたのは、[風音屋TechBlog「AIエージェント向けの業務手順書（Agent Skills）の設計方法」](https://techblog.kazaneya.com/20261030-agent-skills/)です。
日程調整の例で書かれたコツを、ブログ運用の例に置き換えて並べました。

| コツ | ブログ運用での例 |
|---|---|
| **①判断基準を書き出す** | ==対象が曖昧なときだけ聞く・記事に無いことは書かない== |
| **②決まった計算はプログラムに** | ==Xの文字数は数えるプログラム、言い回しはAI== |
| **③出す先ごとに見せる物を決める** | 自分のサイトの数字は作業メモに書くが、Xには出さない |
| **④手順と資料を分ける** | 毎回の判断基準と、ときどき見る資料を別のファイルに |
| **⑤公開は人が確認してから** | ==下書きまではAI、公開ボタンは人== |
| **⑥直したら違反の例で確かめる** | 文字数などを測るプログラムを直したら、わざと引っかかる文を入れる |
| **⑦前の会話を知らないAIで試す** | 経緯を知らない別のAIに、ファイルと見方だけ渡す |
| **⑧失敗した理由を別の場所に残す** | 足した一文の理由は手順書の外に、手順書は短く |

### ①判断基準と「聞かずに進めてよいこと」を書き出す

手順だけ書くと、AIは迷うたびに確認しに来るか、勝手に決めてしまいます。
上の見本の手順2・3のように、**いつ聞くかと、迷ったときの決め方まで書いておくと、毎回の確認が減ります。**

### ②決まった計算は、プログラムに任せる

==数える・測る作業はプログラム、言い回しを選ぶのはAI==、と分けます。

Xは、日本語を2、半角の英数字を1と数えて上限が決まります。
AIに数えさせていた頃は、まだ入るのに下書きを削っていました。
今は文字数を数えるプログラムを手順書に書き、AIはその結果を見て直すだけです。

### ③出す先ごとに、何を見せるか決める

作業メモに残す数字を、そのままXに出すとは限りません。
私はサイトのクリック数を作業メモには書きますが、Xには出さないと決めています。

### ④手順と、ときどき見る資料を分けて読ませる

1つのファイルに全部書くと、AIも人も読めなくなります。
私は、毎回の判断基準と、カテゴリの一覧のような見るだけの資料を、別のフォルダに分けました。
スキルでも、SKILL.mdには「この資料を読む」とだけ書き、資料は別のファイルに置きます。

## 止めて、試して、育てる4つのコツ（⑤〜⑧）

### ⑤公開・投稿は、人が確認してから行う

記事は下書きを作るところまでAIに任せ、公開ボタンだけ私が押しています。
下書きの画面で全体を読み直してから出したいからです。

毎朝のXの準備の手順書にも、「候補を出すだけ。判断と実行は人がやる」と書きました。

### ⑥プログラムを直したら、わざと違反の例で確かめる

元の記事は、決めたルールをテストのプログラムで残しています。
私はテストのファイルまでは持っていません。
代わりに、文字数などを測るプログラムを直すたびに、わざと引っかかる文を入れて止まるか確かめています。

### ⑦前の会話を知らないAIで試す

作った会話のAIは、手順書に書いていないことまで知っています。
私は構成案を出す前に、会話を持たない別のAIに、構成案とレビューの見方だけ渡して読ませます。
「この稿で何を狙ったか」は渡しません。

【ポイント】<br>
スキルも新しい会話で試すと、前のやり取りに頼らず進めるか確かめられます。

### ⑧失敗したら、失敗した理由を手順書とは別の場所に残す

==一文を足したら、なぜ足したかを手順書の本文とは別の場所に残し、本文は短いまま保ちます。==
手順書を整理して短くしたときも、経緯は消さずに別のファイルへ移しました。

Xの投稿が、普段と違う口調のままチェックを通ったことがあります。
そのときは口調を調べる項目をチェックのプログラムに足し、経緯はプログラムの冒頭に書きました。

## 何からスキルにするか：よく繰り返す、手間のかかる作業から1つ

==よく繰り返す、手間のかかる作業を1つ選び、手順書1枚から始めます。==
例えば、記事ごとのアイキャッチの指示や、毎朝のSNSの準備です。
8つのコツは、うまくいかなかった所に1つずつ足せば十分です。
