# ブログ運用はどこまで自動化できたか。人に残った2つの仕事

ブログの入稿作業を、AIに任せられるようになりました。
4ヶ月前は無理だと書いていた工程で、ログインのあと下書きが仕上がるまで人が触りません。
==それでも人には、決めることと確かめることが残りました==。

## 4ヶ月前に「ここは任せられない」と書いていた

このメディアでは、2026年4月に同じテーマで一度書いています。
そのときの結論から始めます。

【本】<br>
これらはブラウザ上の操作を伴うため、Claude Codeには任せられません。

当時の切り分けは、はっきりしていました。**ブラウザを触る「操作」は任せられない。文章を組み立てる「処理」は任せられる。**

だから操作そのものではなく、その前後を設計しようという話でした。

詳しくは[入稿・整形・公開はどこまで効率化できるか【Claude Code実践】](https://aicontent-note.com/claude-code-entry-publish/)にまとめています。

この判断は、当時の条件では正しかったと思っています。

## 8月28日、ログインのあとは人が触らずに終わった

先に条件の違いを書いておきます。
ここが抜けると、話が別のものになります。

【アラート】<br>
変わったのはAIの賢さではなく、使える経路が増えたことです。

4月の記事はClaude Code単体で動かす前提でした。今回はChrome拡張ごしにブラウザを操作しています。**道具は同じでも、使える経路が違います。**

8月28日に公開した記事の入稿は、こう分担しました。人がやったのは、最初のログインと最後の公開ボタンだけです。

| 工程 | 担当 |
|---|---|
| 記事の新規作成・タイトル・スラッグ | Claude Code（WordPressのAPI経由） |
| 本文の装飾ブロック・区切り線・CTA・関連記事 | 変換スクリプト |
| カテゴリー・タグ | Claude Code（API経由） |
| アイキャッチのアップロード・alt・記事への紐付け | Claude Code（Chrome拡張ごし） |
| 検索結果に出る説明文 | Claude Code（Chrome拡張ごし） |
| **ログイン** | **人** |
| **公開ボタン** | **人** |

ここから言えることは1つです。==操作か処理かで分ける切り方が、成り立たなくなりました==。

【メモ】<br>
SWELLなので入稿までは無理だと思っていました。初めて試したときの下書きの仕上がりが、思っていたよりずっと良かったです。

動いた理由の大きいところは、経路が増えたことです。

ただ、それとは別に、試さないまま置いていた期間もありました。できないと決めていたので、確かめていませんでした。

ただし、ここで人に残ったのはログインと公開ボタンの2つだけ、という話は**入稿という1工程の中での話**です。

## それでも、人に残った2つの仕事

ここからは記事1本の流れ全体を見ます。
ネタを決めるところから公開までを並べると、景色が変わります。

| 工程 | 担当 |
|---|---|
| 記事ネタのストック化 | 仕組み |
| **どのネタを書くか決める** | **人** |
| **書く順番を決める** | **人** |
| 構成案の作成 | 仕組み |
| 機械チェック（一文の長さ・読点・禁止表現） | 仕組み |
| 執筆 | 仕組み |
| **構成と本文の確認** | **人** |
| 入稿用ファイルへの変換 | 仕組み |
| WordPressへの入稿（下書き保存まで） | 仕組み |
| **公開の判断** | **人** |

太字の行だけを見ると、==残っているのは決めることか、確かめることのどちらかです==。

このうち、いま一番時間がかかっているのは構成と本文の確認です。

「処理は任せられても判断は残る」という話は、[AIでサボろうとしたら、思ったよりサボれなかった。でも今は回っている。](https://aicontent-note.com/ai-content-operation-experience/)で一度書きました。

今回はその先、何をどう確かめているかを書きます。

## 確認は「気をつける」ではなく「どこを見るか」を決めた

確認が残ると書くだけでは、感想で終わります。
実際に起きたことを2つ出します。

| 起きたこと | 当時のチェックで見つからなかった理由 | 足したこと |
|---|---|---|
| 7日間、公式ページ1本だけを見て事実を取り違えた | 出典は開いていた。**どこを何本開くかを決めていなかった** | 発表記事・更新履歴・ヘルプセンターの3面を開くと決めた |
| 入稿の変換でリンクの中に改行が入り、記事タイトルが途中で切れた | 機械チェックは原稿を見る。**公開後の画面を見ていなかった** | 公開したら実物の画面を開くと決めた |

どちらも、当時走らせていたチェックでは見つかりませんでした。そして直し方はどちらも「もっと気をつける」ではなく、**どこを見るかを具体的に決める**ことでした。

【メモ】<br>
決めただけで、再発しないかどうかはまだ分かりません。同じ種類の作業を重ねてから判断します。

この運用では、手順を自動化しても誤りは残りました。

事実の取り違えは7日ぶん進んでから止まり、リンクの崩れは公開まで進みました。どちらも、人が見た時点で止まっています。

## 自動化率ではなく、止まらない設計を見る

最後に、いま決めていることを書きます。
どれも今回の記録から出たものです。

【チェック】<br>
・任せられないと思っている工程を、定期的に試し直す<br>
・人が担う工程を、最初から工程表に入れておく<br>
・自動化率ではなく、その形のまま続けられるかを見る

2つ目が、今回いちばん変わったところです。以前は人の作業を「自動化できなかった残り」として見ていました。いまは工程表の一部として、最初から時間を取っています。

環境そのものの作り方は[AIに仕事を任せる人が最初に整えるべき環境。土台を作る5ステップ](https://aicontent-note.com/ai-work-environment-setup/)に書きました。

==任せられる範囲は、また動くと思っています==。そのときに組み替えやすいのは、人の工程まで工程表に入れてある運用だという気がしています。
