# プロンプトはマークダウンで書くべき？基本で足りる理由と3つの例外

目的・条件・資料を分けたい指示なら、==プロンプトはまずマークダウンで十分です==。
1文で済む頼みごとには要りません。
ただ、返事を**プログラムで読み取りたい・ツールが形を決めている・ルールが増えた、の3つの場面では、マークダウンだけでは足りません**。

---

## プロンプトをマークダウンで書くと何が良いのか

良いのは、書く人とAIの両方に「どこからどこまでが何か」が伝わることです。

| 誰にとって | 良い点 |
|---|---|
| **書く人・直す人** | 見出しで「目的」「条件」「資料」を分けると、うまくいかなかったときに==直す所がすぐ見つかる==。[OpenAIの公式](https://developers.openai.com/api/docs/guides/prompt-engineering)も、プロンプトが読みやすくなることがあると書いている |
| **AI** | 見出しで、**目的・条件・資料のまとまりの区切り**を伝えやすい |

基本の型はこれだけです。
［　］の所を書き換えて使えます。

```
# 目的
［例：ブログ記事の導入文を3案ほしい］

# 条件
- ［例：読者はブログを始めたばかりの人］
- ［例：1案は3文まで］

# 資料
［ここに記事の見出しを貼る］
```

マークダウンの記号の書き方は、[Markdownとは？AI時代に全員が使うべき理由を実務視点で解説](https://aicontent-note.com/markdown-basics/)にまとめています。

## XMLタグのほうがいい？3社の公式と研究の答え

ChatGPT・Claude・Geminiの公式は、どれも区切りをはっきりさせるように書いています。
マークダウンだけを指定してはいません。

| AI | 公式の書き方 | あわせて書いていること |
|---|---|---|
| **Claude**（[Anthropic](https://platform.claude.com/docs/ja/build-with-claude/prompt-engineering/claude-prompting-best-practices)） | 指示・資料・例が混ざる複雑なプロンプトでは、それぞれを**XMLタグ**（`<context>`〜`</context>`のように、始まりと終わりを挟む印）で囲むと誤解が減る。順番が大事なら番号つきの箇条書き | ==プロンプトの書き方が、返事の書き方にうつることがある== |
| **ChatGPT**（[OpenAI](https://developers.openai.com/api/docs/guides/prompt-engineering)） | **マークダウンの見出しと箇条書き**は、区切りと階層を伝えるのに役立つことがある | 参考資料は、始まりと終わりをXMLタグで囲むと分かりやすい |
| **Gemini**（[Google](https://ai.google.dev/gemini-api/docs/prompting-strategies?hl=ja)） | **XML風のタグか、マークダウンの見出し**が効果がある | 1つのプロンプトの中では、どちらかにそろえる |

2024年の[研究](https://arxiv.org/abs/2411.10541)では、同じ中身を普通の文・マークダウン・JSON・YAMLで渡して比べ、書き方で結果が変わりました。
タスクによっては大きな差も出ましたが、==どの形が一番良いとは決まりませんでした==。

ChatGPTとGeminiの公式が見出しで区切る書き方を挙げているので、まずは見出しで分けるだけの上の型で足ります。

ChatGPTで貼った資料との境目をはっきりさせたいときは、資料の始まりと終わりをタグで囲む方法もあります。
Claudeで指示・資料・例が混ざるなら、見出しの代わりにそれぞれをタグで囲むのも手です。

【チェック】<br>
文章で返してほしいのに箇条書きばかり返ってくるなら、プロンプトの見出しや箇条書きを減らしてみます。

## マークダウンだけでは足りない3つの場面

チャットに打って返事を読むだけなら、3つともほぼ関係しません。

| 場面 | 分け方 | 例えば |
|---|---|---|
| **AIの返事をプログラムで読み取りたい** | 指示はマークダウンのまま、返事の形を**JSON**（項目名と値を{ }で囲んで並べる形）で指定する | Xの投稿案をAIに読者の立場で採点させるとき、返事は「JSONだけ」と項目を決め、合否はプログラムが出す |
| **ツールが指示書の形を決めている** | ツールが決めた形で書く | Claude Codeでは、よく使う指示をファイルに保存して「/名前」で呼び出せる。何をするコマンドかを冒頭の欄に書くときは、[Claude Codeが決めた形](https://code.claude.com/docs/ja/skills)（YAML：項目名と内容を決まった書き方で並べる形）で書く（例：`description: アイキャッチのプロンプトを作る`）。本文はマークダウンのまま |
| **守らせたいルールが増えた** | 測れるルールは、文章ではなく==チェックのプログラムに移す== | 次の見出しで |

参考にしたのは、noteの「[プロンプトはMarkdownでいいと思っていた｜使い分けが必要になる3つの場面](https://note.com/green_donguri/n/nedc603e42a8e)」です。

### 返事をプログラムで読み取る頼み方

下の型のようにJSONを指定しても形が崩れることはあるので、プログラムで使うなら返事の形もチェックします。

```
# 依頼
［例：下の投稿案を、ブログを始めたばかりの人として読んでください］

# 見てほしいこと
- 分からない言葉：［例：意味が分からない言葉を挙げる］
- 読みたくなるか：［例：1〜5で］

# 返事の形
JSONだけを1つ返してください。前後に文章を書かないでください。
返事の例：{"分からない言葉": ["OGP"], "読みたくなるか": 3}

# 投稿案
［ここに貼る］
```

## 守らせたいルールが増えたら、文章で書くだけでは守られにくくなる

AIに記事を書かせるときの私の指示書は、失敗のたびに書き足して350行・4万字を超えました。
「省略禁止」と書いた所も30か所以上ありました。
書くだけでは守られず、何度も指摘したルールもあります。

| ルール | 文章で書いていたとき | 今：プログラムがチェックする |
|---|---|---|
| **冒頭の文** | 「冒頭で答える」と決めていたが、長さの決まりもチェックも無く、400字を超える冒頭もあった | ==3文・150字を超えたらNG== |
| **表の強調** | 「表には強調を入れる」と書いていたが、何度も指摘することになった | **強調の無い表はNG** |
| **英語のページへのリンク** | 「日本語版にリンクする」と書いていたが、AIのレビューでも見落とされた | **日本語版が無いと確かめていない英語のリンクはNG** |

【ポイント】<br>
私の指示書では、文章で残すのは測れない原則だけにしました（体験していないことを書かない、など）。

AIに同じ指摘を何度もしているルールが、字数や有無で測れるものなら、チェックに回す候補になります。
チェックのプログラムも、私はClaude CodeのようなAIに書いてもらっています。
