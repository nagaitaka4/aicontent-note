# アイキャッチ画像の管理ルール

## 基本ルール

- 画像フォルダ：`images/`
- 命名規則：`eyecatch_XXXX.png`（記事のfrontmatter`no`と完全一致・4桁ゼロ埋め）。シリーズ・種別にかかわらず`no`で統一管理し、形式はすべてPNG
- 記事確定後、`image_XX.png`などの仮名ファイルを`eyecatch_XXXX.png`にリネームするのはCCの作業。リネームはBashで実行する
- **番号変更前に必ず画像の中身をReadで確認する**。WP上の実態（ユーザー認識）をリポジトリの数字より優先する
- **出力サイズはプロンプトで「1200×630px」と直接指定する（2026-08-13変更）。**16:9は比率1.778、1200×630は比率1.905で一致しない。16:9で生成させると必ずトリミングが発生し、そのぶん構図が崩れる。**サイズのズレは切って直すのではなく、生成の指定で防ぐ**
- **プロンプトに「16:9」の語を出さない。否定形も書かない**（「16:9では出力しない」もNG）。出したいサイズだけを書く。禁止の言い回しを入れると、かえってその比率を意識した構図で出てくる
- **⚠️ リサイズ・トリミング・リネームはCCが行う。GPTに任せない**（2026-08-13確定）
- **それでも1200×630で出てこなかった場合のトリミング**：位置を目視で決めず実測する。**削る前に、白文字・ピンク・濃色のピクセルからコンテンツのバウンディングボックスを求め、コンテンツが天地中央に来る位置で切る**（PIL＋numpy。上下どちらから削るかは画像による）。切り出し後に上下の余白が揃っているか数値で確認し、最後に画像をReadで開いて欠けがないか目視する
- **切り出す辺は比率で決める**：元画像が1.905より横長なら左右を、縦長なら上下を削る。切り出し範囲が元画像の外にはみ出すと、PILは黒で埋める。保存後に四辺の画素値を確かめる
- リサイズは`Image.LANCZOS`。保存時にICCプロファイルを引き継がない（WPの「サーバーが処理できません」エラーの予防。出たときもICCプロファイルの除去で直す。JPEGには変換しない）
- 仮名ファイル（`ChatGPT Image ....png`等）は`eyecatch_XXXX.png`を書き出したあとに削除する
- **ユーザーが「画像をアップした」「ダウンロードにある」と言ったら、まず`ls -lt images/ ~/Downloads`で最新ファイルを確認する**（下の凍結したフロー4）。Desktop等の全体探索は行わない。ほかの場所を探すのは、どちらにも見当たらずユーザーに保存先を確認した後の最終手段
- **`eyecatch_XXXX.png`として保存する前に、そのファイル名が既存かどうか`ls images/eyecatch_XXXX.png`で必ず確認する**（2026-07-28〜。no.の決め打ちで既存の公開記事の画像を上書きした事故があった）。存在する場合は絶対に上書きせず、正しいno.を`articles/*.md`の`no:`一覧から再確認する

2. CCが`/eyecatch-ref`を実行する：このファイルを読み直す → 直近2〜3枚のアイキャッチを見て配色が続かないようにする → 構成案から対象記事の題を取る → 参考画像の文字の場所をすべて洗い出して差し替える → プロンプトを1案出し、`operations/structure-drafts/<slug>-eyecatch-prompt.md`に保存
2.4 **CCが、プロンプトの中身を`operations/review-packs/no<記事番号>-eyecatch-prompt.txt`にも書き出し（送り先は同じ名前の`.to`に「新しいチャット（添付する画像のファイル名）」）、`~/.local/bin/cb no<記事番号>-eyecatch-prompt`でクリップボードに入れる。提示では、このコマンドを`bash`のコードブロックで1行出す**（Runボタンで入れ直せるように。2026-11-06 no.64でプロンプトのファイルだけ作って`cb`の行を出さず、ユーザー指摘「なんでRUNボタンやブロックで出してないの？」。`cb`は`review-packs/`の`.txt`しか探さない）
2.5 **CCが、GPTに添付する参考画像を`~/Desktop/アイキャッチ添付/`にコピーする**（2026-10-19 ユーザー指示「パスが深くて探すのが一苦労。デスクトップでいい」）。ファイル名は`no<記事番号>_<順番>_<役割>_<出どころ>`（例：`no75_1_組み方_カオナビ.jpg`）。GitHubには入れない。参考画像の集め方は`operations/eyecatch-sampler.py`（集めた一覧は`eyecatch-samples/<日付>/`＝gitignore）
3. ユーザーが`~/Desktop/アイキャッチ添付/`の参考画像を添付して、プロンプトと一緒にGPTへ送る
4. ユーザーが「ダウンロードにある」「アップした」と言う → CCは`~/Downloads`と`images/`の最新を見る → 比率を測って1200×630に整え、`eyecatch_XXXX.png`で保存（上の基本ルール）

**プロンプトの型**（見本：`operations/structure-drafts/claude-code-permission-modes-eyecatch-prompt.md`）
- 1行目：「添付の画像を参考に、ブログ記事のアイキャッチを1枚作ってください。サイズは横1200px×縦630pxです。」
- ■取り入れるもの（参考画像のいい所）：組み方・背景のあしらい・人物の見せ方・品質は参考画像と同じ水準以上・フォントの雰囲気
- **■取り入れるものに、余白と配置の1行を毎回入れる**（2026-09-30 ユーザー了承で型に追加。no.72の確定画像の実測値。2026-11-10 ユーザー了承で守らせ方を追加・no.80）：「・余白と配置：文字とイラストを合わせたかたまりは画面の高さの6割前後に収め、上下は端から約110px、左右は約50〜60px空ける。上下・左右の余白には、あしらいも含めて何も置かない。帯や色面も端から伸ばさず、余白の内側から始める。片側に寄せない」
  - **px指定だけでは守られない**（2026-11-10 no.80の1回目：かたまりが高さの約86%・帯の高さ21%・四隅の波形が端に触れた。ユーザー「いつも画面いっぱいで余白が少ない」）。そのため「余白には何も置かない」「端から伸ばさない」を同じ行に書き、文字の大きさの1行（下）も毎回入れる
  - **決めているのは割合だけ。組み方（左に文字・右に絵／中央に文字など）は決まっていない**。組み方は参考画像に合わせ、その置き方をこの1行の前に書く（2026-11-10 ユーザー指摘「そもそも中央とか、左に文字とか決まってません。だいたいの割合は以前決めていた」）。11/2に足した「中央に文字・下に絵の組み方は測った値に書き換える」と、11/9に足した「中央に文字・左右に絵は使うたびに測り直す」は、組み方ごとに値を持たせる形だったので外した。もとの1行にあった「横幅をほぼ半分ずつ使い、上下の中心をそろえる」も左右に分ける組み方の話なので外した
- **■取り入れるものに、文字の大きさの1行を毎回入れる**（2026-11-10 ユーザー了承で型に追加。no.80）：「・文字の大きさ：帯（帯が無ければタイトルの1行）の高さは画面の高さの約12%（約75px）。文字のかたまりは高さ約220pxに収める。文字を大きくしすぎず、周りに広い余白を残す」
- **■取り入れるものに、絵のタッチの1行を毎回入れる**（2026-10-15 ユーザー了承で型に追加。no.23）：「絵のタッチ：人物と物の描き方（輪郭線の有無・頭身・顔の描き込み・影・効果線）は参考画像と同じにする。変えるのは人物の性別・髪型・服装だけ」。**CCは参考画像の実物を見てタッチを書き、実物と違う形容を書かない**
- **■取り入れるものに、仕上がりの目標の1行を毎回入れる**（2026-10-27 ユーザー了承で型に追加。no.77。2026-11-10 ユーザー了承で書き換え・no.80）：「・仕上がりの目標：デザイナーが作ったような、すっきりと見やすい、おしゃれで今どきのデザインにする。部品は絞り、地の色を広く見せる。フラットでよいが、さびしくはしない」。**旧「部品や色は参考画像より多くなってもよい。シンプルにしすぎない」と「部品と色の数に上限は設けない」は外した**（no.80の1回目で部品を増やす方へ働いた。ユーザー「イラストがゴチャゴチャしすぎ」「もっとデザイナーっぽく、スッキリ見やすいほうが好き」）。部品の数は決めない。地の色が広く見え、何の絵か一目で分かるところまで絞る。**フラット（べた塗り・影なし）はそれで良い。洗練をグラデーション・影・斜めの奥行きで出そうとしない**。**「ごちゃごちゃ」と言われて直すときは、一気に削り切らず、1回目と2回目の中間をねらう**
- ■変えるもの：人物（位置ごとに性別・髪型・服装を具体的に）／人物が持つ物・画面の中身を記事のテーマに／背景の部品を記事のモチーフに
- **画面の中身を描かせるときは、人物との向きをそろえる**（2026-11-02 ユーザー了承で型に追加。no.78）。人物がパソコンの奥に座る構図で「画面をこちらに向ける」と書くと、本人からは裏側しか見えない絵になる（no.78の1回目「裏蓋なのに画面が表示されていて、ありえない」）。画面を見せたいなら、人物を手前か横に置くか、画面ではなく紙やカードで見せる
- ■文字（この◯か所だけ。そろえ方は参考画像に合わせて書く〔例：字面の左端を1本の縦線にそろえる／左右の中心にそろえる〕）：場所ごとに一字一句、大きさの比（ジャンプ率）、色のHEX、太さ、強調する語と下線（2026-11-10 ユーザー指示：そろえ方は決まっていない。旧「字面の左端を1本の縦線にそろえる」は左に文字を置く組み方が前提だった）
- **タイトルは太め（中〜太）にする。参考画像が細い書体でも、タイトルだけは太くする**（2026-09-28 ユーザー了承で型に追加。no.71で細く出て「タイトル感が薄い」→太くして作り直した）
- ■配色：主役の色・差し色・人物と枠の色・背景をHEXで
- **背景に真っ白（#FFFFFF）は使わない。白に限りなく近いグレー・ベージュなど（例：#F7F7F5・#F8F5EF）にする**（2026-09-30 ユーザー指示・型に追加。ブログの背景の白と同化するのを避けるため。斜めの2色分けなど「白」を使う部分も、この近い色にする）
- 最後の1行：「画像内の日本語テキストは、上に指定した文言だけにしてください。」

## プロンプト提案・生成タイミング

- **構成が確定したら、ユーザーの依頼を待たずにCCが参考画像を選び、プロンプトを提示する**（2026-11-05改訂。旧「ユーザーが参考画像を添付した後」は10/30のno.78から実態と違っていた）。順序は`rules/article-flow.md`の「構成確定 → CCが参考画像を選ぶ → CCがプロンプト1案作成 → 生成・アップ → リサイズ・リネーム → 執筆開始」が正。**構成が確定する前に先回りしてプロンプト文を出さない**
- 参考画像なしで作る方式は2026-09-17に終了（`operations/lessons.md`）
- 提案は1パターンのみ（複数案を並べない）
- 生成はGPT推奨（Firefly非推奨）
- シリーズ記事で統一バッジ・統一デザインをすでに採用している場合は、そのバッジ仕様をプロンプトで毎回書き下さない（シリーズ開始時に統一デザインとして先にまとめて確定させる運用のため）

## デザインの方向性（毎回のプロンプトで固定する要素）

- クオリティ基準：デザイン会社が作ったようなミニマル・シンプル・スタイリッシュ
- 余白：**🔒凍結した型の「余白と配置」（確定画像の実測値＝かたまりは高さの6割前後・上下約110px・左右約50〜60px・余白には何も置かない）と「文字の大きさ」を正にする**（2026-10-29に旧「全体の4割程度」から置き換え。組み方を問わずこの割合・2026-11-10）
- **文字は、ピル1つ・タイトル（2〜3行）・サブタイトルくらいまで。帯・吹き出し・段階の並び・丸バッジを1枚に重ねると「情報を詰め込みすぎの悪い典型」**（2026-10-15 no.23の旧画像へのユーザー判断）。リライトで旧画像がこの形なら、文字だけ差し替えず作り直す
- テキスト量：最小限

## デザインの方向性（記事ごとに可変させる要素）

構成・テーマに応じて、CCがそのつど適切なものを選び、プロンプト文に明記する。

- **配色**：ネイビー・グレー・ホワイトに固定しない。記事テーマと参考画像に合わせて選ぶ（例：Claude Code関連記事はオレンジ×グレーなど）。**原色を使ってよい。差し色・ポイントとして効果的に入れるのはむしろ歓迎**（2026-09-28 ユーザー指示。旧「原色的な派手さはNG」は撤廃）
- **レイアウト**：**CCが参考画像を見て、左テキスト・右イラストか、テキスト中央かを判断してプロンプトに書く**（2026-09-28 ユーザー指示。GPTは毎回新しいチャットで生成するので「3記事に1回」のような頻度は伝わらない。旧ルールは撤廃）
- **フォント**：**参考画像のフォントに近づける。特殊なフォント（極太・丸ゴシック・手書き風・装飾書体など）でも、形・太さ・字幅・角の丸さを言葉で書いて寄せる**（2026-09-28 ユーザー指示）。明朝／ゴシックの二択で決めない
- **ジャンプ率**：**テーマ（タイトル）には基本的にジャンプ率をつける**（大きく見せる語と小さく添える語を分け、何倍の差かまで書く）。これまで付いていないことが多かった（ユーザー指摘）。**参考画像がジャンプ率をつけていなくても、CCが設計する**（2026-11-13 ユーザー了承で例外を外した。no.83は参考画像に合わせて題の2行を同じ大きさにし「タイトルをもう少し良くできた」と言われた）
- **図形の位置関係は「接する」「中央が触れる」まで書く**：正円とバウンディングボックスなら「正方形の一辺＝円の直径、円の上下左右の端が各辺の中央に触れる」。「囲む」だけだとずれて出る（2026-09-15 no.68「パスのマルと正方形がズレてる」）
- **モチーフ・あしらい**：**数は参考画像に寄せる**（1〜2点に限らない。2026-09-28 ユーザー指示）。記事テーマを表すものにし、過剰には入れない

## 濃色ベタは「面積」で判断する（2026-08-05〜）

紺・黒などの濃色ベタは、**小さいバッジ（見出し下の紺ピル等）でのみ成立する**。同じ色・同じ角丸でも、全幅のキャプションバーなど面積の大きい要素に使うと、淡いトーンの画面から浮いて最初に目に入る要素が入れ替わってしまう。

- 色と形が既存デザイン（0053〜0055の紺ピル）と同じでも、**役割と面積が違えば別物**として判断する
- 淡いパステル＋線画の画面に濃色を足す前に、その要素が画面の何割を占めるかを見る
- 大きい面はパレット内の色（クリーム・オフホワイト＋細い輪郭線）で処理し、濃色は小面積のアクセントに留める

## 禁止事項

- キャラクターの誇張表現の多用（背景の真っ白・指定外の日本語は凍結した型、黒猫は「マスコットキャラクターは使用しない」、吹き出し・丸バッジの詰め込みは「デザインの方向性」に書いた）
