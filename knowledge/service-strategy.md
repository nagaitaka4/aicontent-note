# 結論：本命は「環境構築」。ブログ運用は主力ではない

## 決定的な非対称

**ブログ運用はAIが進むほど単価が下がり、環境構築はAIが進むほど需要が増える。**追い風の向きが逆になっている。

| | ブログ運用代行 | 環境構築 |
|---|---|---|
| 継続収益 | 強い（月額） | 弱い（売り切りになりやすい） |
| 価格決定力 | 弱い。相場が既にある | 強い。比較対象がない |
| 競合 | 多い。AIで参入障壁が下がり続ける | 業務特化はほぼいない |
| 3年後 | コモディティ化して値崩れ | AIが強くなるほど需要が増える |
| 参入 | 実績ゼロでも始められる | 実績と信頼が要る |

## 両輪ではなく1商品にする

「ブログ代行もやってます、環境構築もやってます」は提案が2つに割れて弱い。
**「環境を作って、最初の3ヶ月はうちが回す」を1つの商品**にする。構築の単価と運用の継続収益を両方取れて、クライアントから見ても「渡されて終わり」にならない。

## 環境構築を売るための2つの設計

1. **継続収益**：構築費だけだと毎月ゼロから営業になる。ただし**モデルが変わるたびに環境は腐る**（Sonnet 5→Opus 5の移行を実体験済み）。構築費＋保守月額でストック化できる
2. **実績**：環境構築は「渡した後に回ったか」でしか価値が測れない

[生成AI環境構築・導入支援サービス14選](https://www.aspicjapan.org/asu/article/40901)。こちらも汎用で、**業務特化がない**。

## デザイン系（ロゴ・制作会社向け）：空白

- **ロゴ**：出てくるのはAIロゴ生成ツール（Brandmark・Renderforest等）だけ。**環境構築サービスは1件も存在しない**
- **デザイン制作会社向けのAI内製化支援**：特化サービスなし
- **Web制作**：[生成AIデザイン代行7選](https://www.aidma-hd.jp/ai/design/)は「代行」であって環境構築ではない。LIG等は法人向け

## 追い風：業界は既にAIを使い始めている

中小規模のWeb制作案件で**生成AIにより制作時間を最大50%削減**でき、AIの生成物を人がブラッシュアップするワークフローが**一般的になりつつある**（[C&Pストラテジー](https://cp-strategy.jp/insights/1409)）。

**「AIを使いましょう」という説得が不要**で、話が「どう環境を整えるか」に進んでいる。

# ターゲット仮説：ハローワークに求人を出す制作会社（未検証）

## 仮説の根拠

- 新卒がほしい＝案件はある
- ハローワークで求人＝制作系の有料求人サイトに金をかけたくない
- 今の時代にHPを軽視している
- **AIで作れるのにデザイナーを募集している**
- 比較対象が明確：**デザイナー1人=年400万円** vs 環境50万円。数字で語れる

既存の営業インフラ（`sales/target-criteria.md` のスコアリング・`lead_generator.py`）がそのまま流用できる。地方・新着に絞れば毎週まとまった数が出る。

## 未検証のリスク（推測では決まらない。送って確かめる）

1. **「デザイナー募集」の読みが逆かもしれない。**needのシグナルではなく「人でやりたい」という意思表示の可能性。制作会社は同業なので、AIへの置き換え提案が逆撫でになりうる
2. **ハローワークを使う理由が「金をかけたくない」ではなく「金がない」かもしれない。**ただし予算がない会社ほど、人を雇う代わりの選択肢に反応する可能性もある
3. **出力品質にシビア。**制作会社はプロなので、ロゴ・サイトの出力が実務レベルでないと即座に見抜かれる。記事より厳しい

# 3種類の環境（記事・ロゴ・サイト）

## 共通構造がある

どれも「指示ファイル ＋ チェックの仕組み ＋ 成果物の管理」。**1つの型を完成させれば、残り2つは当てはめるだけ**になる。

## 順序：1つ完成させてから広げる

記事制作の環境ですら、2026-08-18時点で往復が多いという問題が残っている。ここが解けない状態で3つに広げると、3つとも中途半端になる。

## ロゴが最初の実績になりうる

**ロゴシステムは自分でも運営できる。**売れなくてもロゴ事業として回るので、失敗時のコストが営業の時間だけになる。

これは当初の想定（ブログ代行で実績→環境構築）を更新する。**ロゴで自分が運営すれば、ブログ代行を挟まずに実績が作れる。**

## ロゴ環境の差別化課題

AIロゴ生成ツール（買い切り・商用利用可）が既にある。「なぜツールではなく環境を買うのか」の答えが必要。
現時点の想定：Recraft向けプロンプト生成という設計（`operations/article-backlog.md` の2026-05-20エントリ）で、ツールの汎用出力とは別物であること。

# 技術判断：記事制作の1本化

## なぜ1本化が必要か

環境として渡す以上、「ClaudeとChatGPTを両方契約して手で受け渡し」はクライアントに要求できない。
**現行の「CC構成 → GPT Work執筆 → CCレビュー」は、そのままでは渡せない。**

GPT Workは執筆器であって環境ではない。選択肢は **Claude Code** か **Codex**（OpenAIの環境）。

## Codexの検証結果（2026-08-18）

`operations/codex-test-plan.md` に詳細。

| 項目 | 結果 |
|---|---|
| `AGENTS.md` を読む | ○（`CLAUDE.md` と1行違いで同内容。移行コストほぼゼロ） |
| `constraints.py` 実行 | ○ |
| `article-self-check.py` 実行 | ○ NG 0件まで完走 |
| `git log` / `git push` | ○ 13コミットを反映。認証も通った |
| **初稿のNG件数** | **6件**（Claude Codeは10件） |

**Codexは環境として成立する。**フォルダを渡せば同じ環境になることが実証された。

## 未解決

- **Codex cloud にブラウザから入れない**（アプリのDLに飛ぶ）。「インストール不要」という導入ハードルの優位が成立しない可能性がある。成立しないなら、1本化の判断基準は「執筆品質」と「契約が1つで済むか」の2つに戻る
- Codex cloud のプラン要件・Workspace共有の条件

## GPT1本化の論拠

ロゴ・サイト・記事・環境をすべてGPTで揃えれば、**クライアントに契約させるサービスが1つで済む**。非エンジニア相手にはこれが大きい。

# 説明できない、という制約の扱い

**手順書やAIサポートで埋めるものではない。**環境が動く前のセットアップでは、聞く相手がまだいない（鶏と卵）。

**正しい解き方は、説明が要る要件を設計から外すこと。**

ただし士業・制作会社では、チーム共有・同時更新・ログ管理のためにgit相当が要る（2026-08-18にユーザーが指摘。一人運用とは前提が違う）。Codex cloudならGitHub連携がUIに統合されており、**gitコマンドを教えずに要件を満たせる可能性がある**（ブラウザから入れない問題が解決すれば）。

# 商品構成：4つの環境を切り売りする（2026-08-18）

## 商品candidates

| 環境 | 完成度 | 実体験 | 備考 |
|---|---|---|---|
| **ブログ記事制作環境** | `constraints.py`＋precheck＋self-check＋AGENTS.md が2026-08-18に揃った | 公開68記事 | **固有情報を抜くだけで商品の形になる。**Codexで動作も実証済み |
| **ロゴ制作環境** | 作成中 | あり | **自分でも運営できる**＝売れなくても事業として回る |
| **サイト制作環境** | 構想段階 | まだ | |
| **士業（弁護士・行政書士）環境** | 実装ゼロ | **前職での業務体験あり** | 記事は「当てはめた」ものであって実装記録ではない。ただし**業務理解があるため要件定義は書ける**（外注エンジニアには書けない部分）。ユーザー本人が「一番面白い」と評価 |

## この構成が強い理由

1. **在庫を持たない。**一度作れば複製コストがほぼゼロ。ブログ代行の労働集約と根本的に違う
2. **商品開発と集客が同じ作業になる。**環境を作る過程がそのまま記事になり、メディアの軸（環境構築→実際に動かす実況）に乗る
3. **販路が3つある。**note販売／メディア（士業記事が既に公開済みで導線を置ける）／ハローワークの営業リスト
4. **組み合わせて売れる。**ブログ記事制作環境＋ブログ代行のセットなど

## 最大のリスク：「あとはやってください」

切り売りは、**動かなかったときに逃げ場がない。**

- noteで「買い切り・サポートなし」と明記すれば取引としては成立する
- ただし「動きませんでした」というレビューが1件つくと売れなくなる
- そしてユーザー自身は説明ができない

**→ 売る前に、第三者の環境でセットアップが最後まで通ることを確認する。**自分の端末で動くのは当然で、他人の端末で通るかが商品の分かれ目。ここは省略できない。

## 着手順（根拠つき）

1. **ブログ記事制作環境** — 新しく作るものがない。固有情報を抜くだけ
2. **ロゴ制作環境** — 売れなくても自分で運営できる。ダウンサイドが最小
3. サイト制作環境 / 士業環境

**士業だけは先に1件の実装が必要**（`service-rules.md` の着手条件）。実装記録なしに売ると `feedback_no_fabrication` に反する。

ただし2026-08-18に前提が更新された。**士業業務の理解は前職の体験としてある。**分けて扱う。

| | 状況 |
|---|---|
| 士業業務の理解 | **あり**（前職）。要件定義・構成が書ける |
| 士業向けAI環境の実装 | なし。1件は必要 |

業務が分かっていることは、外注エンジニアには作れない差別化になる。また**本人が一番面白いと感じている**点は、完遂率に効くため順序判断の材料にしてよい。

## 商品の標準形：環境構築＋3ヶ月運用（2026-08-18）

構築して渡すだけでなく、**最初の3ヶ月は提供側が回す**のを標準とする。

## 先に決めるべき3点

1. **3ヶ月後、クライアント側で誰が回すのか。**3ヶ月運用は引き継ぎ期間であり、**橋の向こうに人がいなければ4ヶ月目に止まる。**Web担当がいない会社が対象なので、ここは事前に確認する
   → **ヒアリングフォームに「運用担当者は誰か」を入れる。**いない場合は運用継続の提案に切り替える

   **ただし「止まる」と「使えない」は別物**（2026-08-18に整理）。

   | 種類 | 責任 | 対処 |
   |---|---|---|
   | 環境の欠陥で動かない | **提供側** | 第三者の端末でのセットアップ検証で潰す |
   | 運用する人がおらず、やらなくなった | クライアント側の事情 | 提供側の品質問題ではない |

   後者は、ジムの会員が来なくなるのと同じ構造。**ユーザー自身も「環境を入れたのに手間で止まりかけた」が、環境が悪かったわけではない。**

   ただし**外から見るとこの2つは区別がつかない。**そこで、引き渡し時点で「動く状態で渡した」ことを記録に残す（納品物リスト・動作確認の記録）。責任追及のためではなく、事実の記録として。
2. **3ヶ月終了時点の「引き渡し完了」の定義。**決めていないと「まだできていない」と揉める
3. **3ヶ月後の選択肢**：保守月額／運用継続／卒業。モデル変更で環境は腐るため、保守の継続理由は構造的に存在する

# 営業と商品開発が同じ作業になる（2026-08-18）

ハローワークのリストに対して、**1本本気で記事を書いて送る**（`sales/README.md` の営業メール形式）。この記事が2つの役割を同時に果たす。

- ブログ代行の営業材料
- **環境の性能証明**（「この記事はこのシステムで作りました」）

制作会社が相手なら成果物の質が唯一の説得材料になるため、これ以上の見せ方はない。**「AIで作った」を隠さずに出せる**のが強い。

# 想定する反応と、フィルターとしての扱い

**既にAIで制作している会社**と、**人の手にこだわる会社**からは煙たがられる。ただしどちらも顧客ではない。

反応しないことが早く分かれば営業効率は上がる。残るのは**「困っているが、AIに手が出ていない会社」**で、これが狙う層。織り込み済みとして進める。

# メディア運用・X投稿は止めない

環境構築へ舵を切っても、メディアとXは並行して継続する。理由は2つ。

1. **商品開発の過程がそのままコンテンツになる**（メディアの軸「環境構築 → 実際に動かす実況」に一致）
2. **士業記事が既に公開済み**で、士業環境への導線を置く場所がある

# 未決定：価格

制作会社が買うロゴ環境と、弁護士事務所が買う業務環境では支払い能力が違う。同じ値付けはできない。
**noteで売る前に「どれをいくらで売るか」を決める。**後から上げるのは難しい。

## 未確認：noteでの配布方法

環境の実体はファイル群。noteで配布できる形（zip添付／GitHubリンク／手順書のみ）を確認していない。`note/strategy.md` と併せて検討する。

# 導入手順（2026-08-18確定）

## クライアント側の手順は4つ

| # | やること | 難易度 |
|---|---|---|
| 1 | ChatGPT Plus に登録 | 低い。既に契約済みの可能性も高い |
| 2 | **GitHubアカウントを作る** | **ここだけ重い** |
| 3 | Codexの開始画面で「**GitHub に接続する**」を押す | ボタン1つ |
| 4 | リポジトリを選ぶ | 選択のみ |

**アプリのダウンロードもCLIも不要。**開始画面に並ぶ3枚のカード（CLI／アプリ／IDE拡張）は**ローカル作業用の選択肢**で、クラウド経路は画面下部の「GitHub に接続する」。

## ⚠️ 案内で最も重要な一点

**開始画面は「アプリをダウンロードする」だけが強調色のボタンになっている。**放っておくとそこを押し、ローカル経路（ターミナル・セットアップ）に入ってしまう。

→ 手順書に「**下の『GitHub に接続する』を押してください。上の3つは押さないでください**」と明記する。ここの成否で導入率が変わる。

## GitHubは招待方式にして、2の負担を下げる

```
提供側：クライアント用リポジトリを作る
   ↓
提供側：クライアントをコラボレーターとして招待
   ↓
クライアント：GitHubアカウントを作り、招待を承認
   ↓
クライアント：Codexで「GitHub に接続する」→ そのリポジトリを選ぶ
```

**クライアントはリポジトリの作成も設定も一切やらない。**招待を受けるだけ。

## プラン要件（提案時に明記する）

| プラン | 料金 | 用途 |
|---|---|---|
| Plus | $20/月 | **1人で使う場合** |
| Business | $20/ユーザー/月（2座席以上・年額） | **2人以上で使う場合**。管理者コントロール付きの共有ワークスペース |

提案文では「**1人で使うならPlus、2人以上で使うならBusiness以上の契約が必要です**」と書けば足りる。**クライアント負担なので、隠さず先に明示する。**

## サポート範囲

**メールのみ。**面談・通話なしという既存のサービス設計（`service-rules.md`）と同じ。押す場所を間違えさせない案内を事前に用意することで、問い合わせ自体を減らす。

# コピー・横流しへの対応（2026-08-18整理）

## 前提：完全には防げない

クライアントの手元にファイルがある以上、テキストは書き換えられる。難読化しても手間が増えるだけ。**電子書籍・フォント・素材集と同じ構造。**

**防ぐのではなく、コピーの価値を下げる方向で解く。**

## いま入れる（コストがゼロ）

| 施策 | 効果 |
|---|---|
| **契約に「1事業者1ライセンス・第三者への複製/再配布/譲渡を禁止」** | 抑止力。フォント・素材集も同じ方式で回っている。1条追加するだけ |
| **渡す前に社名を焼き込む**（ロゴ提案URL・納品フォーマットの署名） | 横流しされた側に消す手間が発生。**消し忘れると他社名の提案書を客に出す事故**になる。DRMより怖い |
| **更新を保守契約に紐づける** | モデルが変わるたび環境は腐る。**コピー品は自動的に劣化する。**「環境構築＋3ヶ月運用」の設計と噛み合う |

## 署名の目的は「防ぐ」ではなく「見つける」

消せなくするのは無理だが、**消したことを検出できる状態**にはできる。生成物に社名が入る仕様なら、他社名で流通しているのを見つけたとき**契約違反の証拠になる**。

## 売れてから考える

| 施策 | 判断 |
|---|---|
| ロゴ提案URLの発行を提供側サーバーで握る | **売れてから。**実現可能だが「環境を売る」から「環境＋発行サービス」に性質が変わり、維持コストが出る |
| 難読化 | **不要。**効果が薄い |

**顧客がゼロの段階でコピー対策に時間を使うのは早い。**出回るほど売れたなら、その時点で発行サーバーを作れば間に合う。

## B2Bには構造的な抑止がある

横流しが起きやすいのは「渡しても自分が損しない」商品（音楽・素材）。**業務環境は違う。**制作会社が競合の制作会社に渡せば、自社の優位を手放すことになる。士業も同じ。**渡す動機がない。**

## 作り込みはしない方針で問題ない

重いカスタマイズは工数が増え、パッケージ商品の利点が消える。**渡す前の軽い固有化（社名の焼き込み）で足りる。**

# 検討の経緯（2026-08-18のセッション記録）

方向が変わった過程と、**CCが出して撤回した見解**を残す。同じ楽観・同じ確認不足を繰り返さないため。

## 出発点と、話が動いた順

1. **メディア名に「AI」が入っているのはブレーキか** → 据え置き。ドメイン移転コストは記事数に比例しないので急ぐ理由がない。判定条件（営業で「AIで書くんですか」が3件出たら再検討）を設定
2. **差別化は価格やサービス内容ではない** → 資産は「記事が書けること」ではなく**環境を組めること**、しかも非エンジニアが、と整理
3. **環境を売る案** → ユーザーが「自分ですら自動化できていない」と指摘し一度撤回
4. **ワークフローのレビュー**（本来の目的）→ 制約が6箇所に手書きされ矛盾していることが判明し、`constraints.py` へ一元化
5. **環境構築サービスの再浮上** → 士業・ロゴ・サイト・記事の4環境を切り売りする形へ

## CCが出して撤回・訂正した見解

| 見解 | 実際 | 原因 |
|---|---|---|

## ユーザーのアイデアで、CCが特に評価した点

- **制作会社をハローワークで拾う読み**：既存の営業インフラを流用でき、比較対象が「デザイナー1人＝年400万円」と明確
- **見本記事が環境の実演を兼ねる**：1つの作業がブログ代行の営業材料と環境の性能証明の両方になる
- **ロゴは自分でも運営できる**：売れなくても事業として回る。ダウンサイドが最小
- **切り売り**：在庫を持たない。複製コストがほぼゼロ
- **煙たがられるのはフィルター**：反応しない層が早く分かれば営業効率が上がる
