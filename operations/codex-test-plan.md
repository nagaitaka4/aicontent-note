# 手順（2段階）

**第1段階：テスト1〜3をまとめて実行 → 結果をCCに貼る → CCが確認**
**第2段階：テスト4を実行 → 書かれたファイルをCCが判定**

1回ずつ止めない。テスト1〜3の間に判断は要らない。ただしテスト4の前には一度止める。
テスト2が落ちた場合、テスト4の進め方が変わるため。

Codexでこのリポジトリを開き、下のプロンプトを貼る。

## テスト1：環境を認識するか

```
このリポジトリの AGENTS.md を読んで、記事制作の絶対ルールを3つ挙げてください。
```

**見るポイント**：AGENTS.md を自分で見つけて読むか。ファイル名を教えないと読まないなら、環境として渡したときに同じことが起きる。

## テスト2：スクリプトが動くか

```
以下を順に実行して、出力をそのまま見せてください。
1. python3 operations/constraints.py
2. python3 operations/article-self-check.py articles/llms-txt-geo-effect.md
```

**見るポイント**：1で制約一覧が出るか。2で「NG 0件」が出るか。ここが動かなければ、品質チェックが回らない環境になる。

## テスト3：gitが使えるか

```
git log --oneline -5 と git status を実行して、出力を見せてください。
```

**見るポイント**：履歴が読めるか。読めればコミットも通る見込みが高い。

## テスト4：執筆品質（本命）

```
operations/structure-drafts/llms-txt-geo-effect.md が確定済みの構成案です。
この構成案に沿って、記事の初稿を書いてください。

制約は `python3 operations/constraints.py` を実行して確認し、その全項目を守ってください。
文体の見本は articles/claude-cowork-usage-data.md です（構成や内容は真似しない）。

出力先は operations/codex-test/llms-txt-geo-effect.md にしてください。
既存の articles/llms-txt-geo-effect.md は上書きしないでください。

**書いたら、そこで止めてください。**自己チェックも修正もしなくて構いません。
```

**見るポイント**：**初稿のNG件数**。Claude Codeは10件だった。

**NG判定はCodexにさせない。**「NG 0件でした」と報告されても、実際に走らせたか確認できないため。
書かれたファイルをCC側で読み、こちらで `article-self-check.py` を回して数える。

この設計なら、**テスト2が落ちてもテスト4は実行できる**（判定がCC側で完結するため）。

## 第1段階の結論（2026-08-18）

**Codexは記事制作の環境として成立する。**スクリプト実行・git・push がすべて通り、

# 判断の目安

- **初稿NGが10件を大きく下回る** → 執筆品質でCodexが優位。1本化はCodex側が有力
- **10件前後** → 差はない。移行の理由が薄いので現状維持でよい

## 最大の発見：「事実の扱い」の1行が擬似引用を止めた

`constraints.py` に「引用は原文どおりに書く」を追加しただけで、**2回続いていた擬似引用が解消した。**

- v1（ルール未提供）：原文の要約を `【本】` ブロックに入れ、引用として提示
- v2（ルール提供）：**80字制限に収まる原文を選んで逐語引用**

Claude Code版（no.60）は、同じ問題を「ブロックを外して地の文へ逃がす」形で回避し、その結果リード文チェックに抵触した（CASCADE-2）。**v2は正面から解いている。**

## Codexの一貫した弱点：H2直下リードの超過

**v1もv2も3件ずつ**発生。Codexは systematically リードを長く書く傾向がある。

ただし修正は3箇所のリードを削るだけで、内容に触らない。**修正コストは小さい。**

## 結論

**記事執筆はCodexが優位。**測れる軸（NG件数・文長・引用の忠実性・類似度）すべてで上回った。

環境としても第1段階で成立を確認済み（スクリプト実行・git・push がすべて動作）。

→ **記事制作の1本化は Codex 側が有力。**
