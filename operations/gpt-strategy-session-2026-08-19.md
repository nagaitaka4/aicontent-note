# サービス事業プロジェクト 引き継ぎプロンプト
## Claude Codeによるプロジェクト管理 × GPTによる戦略・企画判断

このプロジェクトは、**Claude CodeとGPTを往復させながら構築・推進する**運用にする。
Claude Codeだけで方向性まで決めるのではなく、役割を明確に分ける。

# 1. Claude CodeとGPTの役割分担

## Claude Codeの役割

- プロジェクト全体の状態管理／リポジトリ・ファイル・ドキュメントの管理
- 決定事項・未決定事項・検証結果の記録
- 実装／スクリプト作成／自動化
- 営業リスト生成・スコアリング等の仕組み作り
- サイト制作環境・ブログ制作環境・ロゴ制作環境の構築
- テスト／実測／再現性確認／技術的な実現可能性の確認
- GPTで決まった戦略を実装可能な形へ落とす
- 「この案を進めるには何を検証する必要があるか」の整理
- 既存ドキュメントとの矛盾検出

## GPTの役割

- 事業方向の相談／商品企画／営業戦略／営業フック／顧客心理の検討
- 商品構成／価格設計／アイデア出し／戦略上の比較
- Claude Codeのアウトプットのレビュー
- 次に何を検証すべきかの判断
- ユーザーと対話しながら方向性を決めること

## 基本フロー

```text
ユーザー
↓
GPTと事業・企画・方向性を相談
↓
方向がある程度固まる
↓
GPTとの会話をClaude Codeへ共有
↓
Claude Codeが記録・実装・検証
↓
Claude CodeのアウトプットをGPTへ共有
↓
GPTでレビュー・判断
↓
必要なら再びClaude Codeへ返す
```

### Claude Codeへの重要な指示

**事業方向や商品戦略を、Claude Codeだけで勝手に確定しない。**

技術的・実務的な問題が見つかった場合は、

```text
現在の案／問題／実測・根拠／考えられる選択肢／Claude Codeとしての推奨
```

まで整理する。最終的な戦略判断はGPTとの相談に戻す。

# 2. ユーザーの状況

- 個人事業／1人で運営／非エンジニア
- Claude Code、Codex、ChatGPT等のAIを使って事業環境を構築している
- ブログメディア「AIコンテンツ運用ノート」を運営（公開記事57本・2026-08-19時点）
- 記事制作環境を自分自身で構築・実運用している（ルールファイル／品質チェックスクリプト／自動リサーチ／制約管理／記事チェック／GitHub／AIエージェント）
- エンジニアではないが、AIとClaude Code等を使って自分の環境を構築すること自体はできる

# 3. 絶対に外してはいけない制約

## 3-1. 技術説明ができない

**「自分で環境を作れるが、その技術を人に説明する能力はない」**

したがって、ターミナル操作を教える／Gitコマンドを説明する／口頭でセットアップ支援／Zoom画面共有／複雑な手順書を読ませる、という商品設計は不可。

**説明が必要なら説明を増やすのではなく、説明が不要になるように商品・工程を変える。**これを基本原則とする。

## 3-2. サポートはメール／フォームのみ

面談・電話・Zoom・Google Meetなし。必要事項はフォームで取得し、非同期で完結させる。

「伴走型」という言葉を使う場合も、定例ミーティング・オンライン相談・研修は行わない。サービス説明上はむしろ**「打ち合わせ不要」「フォームとメールだけで完結」「丸投げ可能」**の方が実態に合う。

## 3-3. 1人で数をさばく

受注単価最大化よりも、**AIで原価・工数を大幅に下げて多くの案件を処理する**方向を重視。フルオーダー／長時間ヒアリング／毎回ゼロから要件定義／複雑なカスタム開発／長期間の個別サポートは避ける。

# 4. 現在の既存サービス

**ブログ運用代行**（月4本・月8〜10万円程度・面談通話なし・メール／フォーム完結）。

ただし主力事業にはしない。AIが進歩するほど単純な記事制作の価格は下がる可能性が高い。一方で**AIを業務で使うための環境を構築する需要は、AIの能力が高くなるほど増える**という仮説を持つ。

# 5. 現在の大きな事業仮説

本命は**業務特化型のAI制作環境／業務環境**。候補は①ブログ記事制作環境 ②ロゴ制作環境 ③サイト制作環境 ④士業向け業務環境。**4つ同時に作らない。1つずつ実運用しながら完成させる。**

# 6. 過去に検討した商品形態

## A案：環境構築パッケージ販売

懸念はリポジトリのコピー・横流し。ただし現在は**コピーの完全防止は優先しない**方針。対策：契約に再配布禁止／1事業者1ライセンス／顧客企業名の焼き込み／生成物・提案フォーマットの固有化／更新を保守契約に紐づける（AIモデル更新で古い環境が劣化するため、正式更新版に価値を持たせる）。作り込みすぎない。

## B案：公開販売せず直販

note等では売らず、**営業対象企業を特定してB2Bで直接販売**。契約相手が分かる／社名固有化が意味を持つ／横流しへの抑止が強い／顧客ごとに軽いセットアップができる。

現在の方向では、**Aの商品をBの方法で売る**組み合わせが有力。

## C案：サイト無料＋ブログ年間契約 →【否決】

サイト制作無料＋月4本ブログ運用（月10万・最低1年・保守別途・ロゴはオプション）を考えたが、**120万円の年間コミットは狙っている顧客層には重すぎる**と判断。そのまま採用する可能性は低い。

# 7. 現在かなり有力になっている新しい事業モデル

**ハローワーク新卒求人を起点に、地方中小企業へサイトリニューアルを直接営業するモデル。**

これはSEOのプル型事業ではない。検索順位を上げて問い合わせを待つのではなく、**ハローワークの求人データから継続的に営業対象を抽出し、こちらから直接営業する。**

# 8. ハローワーク営業リストが大きな強み

営業リストは**新しい求人が出る限り継続的に補充される**。「営業リストが枯れる」という一般的なアウトバウンド営業の問題が比較的小さい。重要なのは単なる企業リストではなく、**「今まさに採用需要が発生している企業」を見つけられること**。

# 9. 狙う企業

**地方の中小企業で、新卒をハローワークで募集している会社。**

仮説：新卒を採用したい／人材不足／大手求人媒体へ大きな広告費を出すほど潤沢ではない／採用広報のリテラシーが追いついていない／会社自体は動いている／しかしWebサイトが古い／スマホ対応できていない／採用ページが弱い／NEWSやブログが止まっている。

特に**新卒募集と会社サイトの状態が矛盾している企業**を狙う。

# 10. 営業対象のスコアリング候補

「サイトが古い」だけでは判定しない。営業前にAIで精査する。

候補指標：新卒採用中か／求人の掲載時期／従業員数／地方中小企業か／自社サイトの有無／スマホ対応・レスポンシブ・横スクロール・文字サイズ／スマホで採用情報を探しやすいか／デザインの古さ／SSL／問い合わせフォーム・導線／採用ページの有無・更新状況／NEWS・ブログの最終更新日／会社情報の更新状況／社員の雰囲気・仕事内容が伝わるか／写真の古さ／求人票の魅力がサイトでも伝わっているか／SNS更新状況／会社自体は活発か。

特に**会社は動いているのに、HPだけが止まっている会社**は有力候補。

# 11. 営業の中心フック

**「新卒採用をしているなら、応募者は求人票だけでなく必ず会社サイトを確認する」**

```text
新卒を採用したい
↓
学生・応募者は会社名を検索する
↓
企業サイトを見る
↓
サイトが古い／スマホで見づらい／更新されていない
↓
給与や条件を見る前に候補から外れる可能性がある
```

Web制作そのものを売るのではなく、**採用時の第一印象を改善するためのサイトリニューアル**として営業する。

# 12. NEWS／ブログも営業フックに使う

**NEWSやブログが数年間止まっていると「この会社は今もちゃんと動いているのか？」と感じられる可能性がある**という視点を使う。サイトを綺麗にするだけでなく、**更新が続いている会社にする**ことまで提案する。

ブログ運用を「SEO記事を月4本作ります」とは売らない。**「会社サイトを止めないための運用」**として位置づける。内容は会社NEWS／社員紹介／仕事紹介／プロジェクト紹介／実績紹介／採用向け記事／社内制度／インタビュー／通常ブログ／SEO記事などを混ぜられる。

名称は「ブログ代行」より**「サイト更新・採用広報運用」**のような見せ方も検討余地あり（未確定）。

# 13. サイト制作サービスの現時点の価格イメージ（実制作テスト前・仮説）

- **サイト単品：20万円前後**（一括・分割可。地方中小企業には分割も相性が良い）
- **ブログ／サイト更新運用：＋月8万円程度**（サブスクリプション形式。年間契約を必須にはしない方向）

# 14. サイト制作単品20万円の考え方

高単価フルオーダーWeb制作会社を目指さない。**AIで制作工程を大幅自動化し、制作原価を下げ、20万円程度でも十分利益が出る構造**を狙う。1案件の実制作（クライアント確認待ち等を除いた制作側の実工数）を**1〜3日程度**まで短縮したい。とにかく数をさばく。

# 15. 現在想定しているサイト制作フロー

1. **フォーム入力**（要望・会社の特徴・ターゲット・採用・好み・機能・写真・残す内容・不要な内容・競合など。面談はしない）
2. **既存HPをAIで自動解析**（全ページ・文章・会社情報・サービス・採用・NEWS・ブログ・問い合わせ・画像・構成・問題点を抽出）
3. **内容整理**（重複・古い情報・不要情報・不足情報・採用上の問題・スマホ上の問題・導線・ページ構成）
4. **構成再設計**（そのまま移植せず、ユーザー／採用候補者に分かりやすい形へ再構成）
5. **デザイン参考サイトを決める**（1つ程度。完全コピーではなく雰囲気・レイアウト・情報密度・写真使いの参考。著作権・模倣リスクに注意）
6. **AIでサイト作成**（下記2案を実測して決める）

### 案A
フォーム → 既存HP解析 → 構成設計 → **ChatGPT Workでデザイン／ページ制作 → CodexでWordPress化**

### 案B
フォーム → 既存HP解析 → 構成設計 → **Codexで最初からWordPressテーマとして制作** → ブラウザ検証 → 公開

大量生産が目的のため、**往復が少なく、壊れにくく、再利用しやすい方を採用する。推測で決めず、実測する。**

# 16. WordPressでの標準化

毎回完全自由設計にはしない。標準範囲の例：トップ／会社情報／事業・サービス／採用／NEWS／ブログ／問い合わせ／プライバシーポリシー／スマホ対応／WordPress／基本SEO設定。**5〜8ページ程度＋NEWS・ブログ**が標準商品の候補（未確定）。

# 17. 追加機能

標準を超えるものはオプション：EC／予約／会員機能／多言語／大量商品登録／外部API連携／特殊検索／複雑なフォーム／独自DB／複雑な管理画面。

# 18. EC／ショップ機能

**独自ECをゼロから作らない。**「作れる」と「大量処理事業で作るべき」は別。WordPressなら**WooCommerce等の既存EC基盤**を使い、Codexはデザイン統合・商品ページ・テンプレート・UI・テストを担当。決済・注文・在庫等の基幹機能は既存基盤に任せる。

# 19. 予約システム

同様に原則ゼロから作らない。既存のWordPress予約プラグイン／WooCommerce系／外部予約サービスをCodexで統合する。

基本原則：**既存サービスがある機能は既存サービスを使う。AIはデザイン・設定・接着・自動化を担当する。**

# 20. ロゴ制作

サイトリニューアル時にロゴも確認し、ロゴがない・古い・低解像度・新サイトと合わない場合に**追加提案**する。最初の営業メールで全部売り込まず、受注後またはサイト診断時に自然なアップセルとして提案する。

# 21. サイト制作環境を将来的に販売する可能性（二層構造）

一般中小企業に「サイト制作環境そのもの」を売るのは難しい可能性がある（ドメイン・DNS・サーバー・公開・保守などがあり「環境を渡したから後は自分で」が成立しにくい）。

- **一般中小企業 → 完成したサイトを売る**
- **制作会社 → サイト制作環境そのものを売る可能性がある**（ドメイン・サーバー等の知識があるため）

この二層構造が有力。

# 22. サイト制作事業と環境販売事業をつなげる

サイト制作環境は最初から外販商品にする必要はない。まず**自社の製造設備**として使う。

営業→受注→AI環境で制作→実案件で改善→速度向上・問題減・実績増→完成度が上がる→制作会社へ**「実運用済み環境」として販売可能になる**。

# 23. 最終的に目指したい製造ライン

```text
ハローワーク求人取得 → 企業抽出 → 企業HP取得 → サイト自動診断 → 営業優先度スコアリング
→ 営業文面生成 → 営業 → 受注 → フォーム回答 → 既存サイト全抽出 → 内容整理 → 新構成作成
→ デザイン方向決定 → WordPress自動制作 → PC/スマホ品質チェック → ステージング
→ クライアント確認 → 公開 → NEWS/ブログ環境導入 → 月額サイト更新 → 必要ならロゴ提案
```

1案件ごとに人間がすべて考えるのではなく、**例外だけ人間が判断する。**

# 24. この事業の本当の強み候補

表面的には「20万円の格安サイト制作」に見えるが、本当の競争力候補は**営業から制作までの一連のAI製造ライン**。

営業＝ハローワーク求人という継続的な需要シグナル／精査＝求人情報＋企業HPのAI自動分析／フック＝新卒採用とWebサイト状態の矛盾／制作＝AIで工数大幅削減／継続＝NEWS・ブログ・採用広報運用／アップセル＝ロゴ／将来＝制作環境そのものを制作会社へ販売。

# 25. 価格競争について

安くすること自体を目的にしない。20万円で成立する理由は**人間の制作工数をAIで大幅に減らすから**。ただし現時点ではこの方法でサイト制作を1件も完走していない。**20万円／1〜3日はまだ仮説。必ず実測する。**

**推測で確定しないこと。**

# 27. 営業フックについての現状

中心フックは1つにする。全部を営業メールに詰め込まない。

現在の中心候補：**「新卒採用をしている今、応募者から見える会社サイトを整えませんか」**

個別企業に対しては、その会社固有の問題を1点だけ添える（スマホ表示／更新停止／採用ページ／NEWS最終更新／問い合わせ導線など）。

# 28. 「サイトが綺麗なら採用しやすくなる」について

「サイトを綺麗にすれば採用が必ず成功する」とは断定しない。採用には給与・仕事内容・勤務地・福利厚生・企業規模・知名度等の他要因もある。営業表現としては**「応募者に候補から外される理由を減らす」**くらいが安全。

# 29. ハローワークを使う企業について

「大手求人媒体に大金をかけるほど予算はないが、新卒は欲しい企業」を想定。ただし**ハローワーク利用＝予算がないとは断定しない**。実際の企業反応で検証する。

# 30. コピー問題

環境販売ではコピーされるリスクがある。しかし現時点では**コピー対策より商品が売れるかを先に検証する**。基本対応：契約／1社1ライセンス／再配布禁止／社名焼き込み／軽い固有化／正式アップデート／保守。完全DRMは作らない。

# 31. 記事制作環境

現在最も実績がある環境（公開57本・実運用中・constraints.py／precheck／self-check／AGENTS.md等。Codexで動作確認済み）。

ただし現在でも熟練ユーザー自身の制作で、機械チェック後の大量修正・事実確認修正・同時編集事故等が発生した。**他社販売前に工程自体をもっと簡単にする必要がある。**

# 32. ロゴ制作環境

構築中。自社でもロゴ制作サービスとして使える／環境自体が売れなくても制作事業として使える／実案件を通じて改善できる／将来制作会社へ環境販売できる可能性。サイトリニューアルとのアップセル相性も良い。

# 33. 士業環境

候補として存在する。前職で士業業務への理解がある。ただし機密情報・個人情報・正確性・責任・AI出力・セキュリティなどの問題が重い。**今すぐ最優先にはしない。**

# 34. 当面の事業構造候補

## 一般中小企業向け：AI高速サイト制作
入口＝新卒採用をきっかけにしたサイト改善／単価＝約20万円／追加＝ロゴ／継続＝NEWS・ブログ・採用広報運用 月8万円程度

## 制作会社向け（将来）
ロゴ制作環境・サイト制作環境・記事制作環境そのものを販売。

**一般企業には完成物、制作会社には製造環境**という二層構造。

# 35. Claude Codeに今後求める姿勢

- **確認せず断定しない**（過去の誤判断：競合がいない／Codexでできない／Codexはブラウザ不可／士業実績がない等）。実機・コード・公式情報・実測を優先する
- **既存ドキュメントと矛盾させない**。`service-strategy.md` を現時点の戦略記録として扱い、更新は「どの記述をどう更新すべきか」を示す（勝手に上書きしない）
- **「できるか」ではなく「大量処理に向くか」を評価する**。判断基準：工数／再現性／安定性／問い合わせ発生率／メンテナンス／1人で回せるか／20万円の商品に載せられるか／1〜3日制作に収まるか

# 36. 当面の最重要検証

**サイト制作環境を実際に1件完成させること。**議論だけで商品化しない。

テスト候補：①自分の既存サイトの複製／リニューアル ②架空の地方中小企業サイト ③実在企業を参考にした非公開テストサイト

目的：工数計測／AIへの指示回数／人間修正時間／WordPress化時間／スマホ対応／フォーム／NEWS／ブログ／公開／品質／修正回数を測ること。

# 37. 最初の実制作テストで記録するもの

```text
既存HP取得：／情報抽出：／構成設計：／コピー整理：／デザイン決定：／トップ制作：
下層制作：／レスポンシブ：／WordPress化：／フォーム：／ブログ・NEWS：／ブラウザ確認：
人間修正：／公開準備：／総工数：／AI指示回数：／大きな手戻り：
```

これが**20万円・1〜3日モデルが成立するかの判断材料**になる。

# 38. このプロジェクトで避けたいこと

4商品を同時開発／技術的に面白いだけの機能追加／顧客ゼロなのに重いDRM／独自EC／独自決済／独自予約システム／高度な個別カスタマイズ／長いZoom商談／毎回の完全オーダーメイド／説明が必要なセットアップ／推測だけで価格決定／推測だけでターゲット変更／GPTまたはClaude Code単独で事業方針を確定。

# 39. 成功イメージ

「AIでサイトを作れる人」ではなく、**「営業対象発見から制作・継続運用までをAIで仕組み化して、大量処理できる事業」**を作る。その製造環境自体も将来的に商品化する。

```text
制作事業で環境を鍛える → 環境が制作事業の利益率を上げる → 実績が増える
→ 完成した環境をB2B販売する → 環境販売からも利益を得る
```

# 40. 今後のClaude Codeからの報告形式

戦略に関わる問題を見つけた場合：

```text
■確認したこと
■実測／事実
■現在案への影響
■問題がある場合の選択肢 A./B./C.
■Claude Codeとしての推奨
■GPTと相談すべき判断点
```

技術実装だけで完結するものはそのまま進めてよい。ただし商品価格／ターゲット変更／営業フック変更／サービス内容変更／新事業追加／大きな技術基盤変更は、勝手に最終決定せずGPTとの相談事項として返す。

# 41. この時点の最重要テーマ

**「20万円程度・実工数1〜3日で地方中小企業のWordPressサイトをAI中心で制作できる標準環境を作れるか」**

まだサイト制作サービスの仕様・価格・営業方法を正式凍結しない。まずは実制作で検証できる状態を作ることを優先する。
