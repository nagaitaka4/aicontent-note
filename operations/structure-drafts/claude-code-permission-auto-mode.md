## タイトル・スラッグ・description

**タイトル（33字）**：`Claude Codeの許可、どこまで自動でいいか。確認に残す操作`

**スラッグ**：`claude-code-permission-auto-mode`

**description（案）**：
Claude Codeの許可は、auto modeにすると多くが自動になります。ただしauto modeでも残る狭いシェルの許可は、分類器より先に効き、壊す操作を通すことがあると公式は書いています。確認に残す操作と、許可の狭め方を4つの手順で整理します。

**メインKW**：`claude code 許可`（サジェスト：めんどくさい／許可不要／設定／自動／許可リスト）

## ① どこまで自動でいいかは、4つの手順で決まる
→ 答えを最初に置く。各手順は分岐で次へ進む形
→ 読者1〜6が全員どこかに着く。⑥の確認リストと行き先を一致させる

手順1：画面の表示を見る
・手動（Manual）と出る → 主な理由は次のとおり（公式）
  新規インストール直後、またはauto既定を入れた版に更新した直後の最初のセッション／ホームかプロジェクトの設定ファイルで手動などのモードを決めている（プロジェクトの設定ファイルに書いたautoは効かない）／設定で auto mode を無効にしている（disableAutoMode）／claude -p や Agent SDK で動かしている／機能フラグの取得を切っている（テレメトリーのオフなど）／Bedrock・Google CloudのAgent Platform・Microsoft Foundry・Claude Platform on AWS 経由／デスクトップアプリはフォルダごとに前回選んだモードを覚えている／Enterprise・APIキー／バージョンが古い（macOS・Linux・WSLは2.1.228より前、Windowsは2.1.233より前）／auto modeに対応していないモデル（Haikuなど）を選んでいる
  → 切り替えるなら：ターミナルはShift+Tab、デスクトップアプリは送信ボタン横のモード選択。既定にしたいなら ~/.claude/settings.json の defaultMode → 手順2
  → 確認画面の「Yes, and switch to auto mode」でも切り替えられる（v2.1.247以降）
  → Enterprise・APIキーは、分類器の判定が使用量に数えられる。ただしサーバー側で判定される場合は別に数えない（9/25のドキュメント。②のインフォと同じ）。管理者がauto modeを無効にしていて選べないなら、手順3・4だけ使う
・auto modeと出て、特に聞かれない → 手順2
・auto modeと出ているのに聞かれる → ②へ（聞かれる操作は決まっている）
→ 読者1・2・3・6は手順2へ。読者4は②へ

手順2：その作業は、auto modeに任せてよい作業か
・機密の作業、見慣れないコード → 手動から始める（公式の目安）。auto modeは作業の方向を任せられるときに使い、機密の操作の確認の代わりにはしない（公式）。本番インフラへの重大な変更は「今も自分で見ることを勧める」（公式ブログ）
・手動が効くのは、1回ずつ見られる短い作業。確認が数十回を超える作業は、③のとおり止めにくくなる（50回以上で約5%）。長い作業なら、本番に触る手順だけを切り出して手動で見る。準備の部分はauto modeに任せる
・denyは、どのモードでも効く補助（Bashのdenyは別の呼び出し方には当たらないことがあるので、これだけを歯止めにしない。手順4）
・会社の場合：機密データの場所と、共有してよい相手を分類器の設定（autoMode.environment）に書くと、分類器はその場所を機密データとして扱い、アクセスや持ち出しを既定の保護ルールで判断する（公式。permission-modesの既定で止める一覧には「機密データの場所へのアクセス・持ち出し」がある）。書く場所は ~/.claude/settings.json・管理者の設定・--settings。プロジェクトの設定ファイルに書いても読まれない
・auto modeのまま、会話で「デプロイの前に止まって」と言うと、分類器はそれを止める合図として扱う（公式）。ただし会話の圧縮で消えることがあるので、確実に止めるならdeny（手順4）
・手動にしても、作業フォルダ内の読み取りは聞かれない（公式）。秘密情報や顧客データの読み取りを止めたいなら、どのモードでもdeny（手順4）
・それ以外 → auto modeを基本にする。何が止まるかは②の表で、任せて大丈夫かは③の数字で判断できる
・bypassPermissions（ほぼすべての確認を飛ばす）は、コンテナやVMの中だけ（公式）
→ 読者5は「本番・顧客データに触る手順は手動で見る。それ以外はauto mode」に着き、手順3・4へ（どちらのモードでも効く）
→ 読者1・2・3・6はauto modeに着き、手順3へ

手順3：確認を考える前に、貯めた許可（allow）の扱いを決める
・ルールを何も書いていない人は、ここは飛ばして手順4へ → 読者1はそのまま「何も書かない」に着く
・貯めた許可の場所：~/.claude/settings.json（全体）と、各リポジトリの .claude/settings.local.json（「今後は聞かない」で貯まった分）。両方を見る
・なぜ先か：自分のルールは、原則として分類器より先に判定される。残っている許可に当たると、分類器を通らない操作がある（公式）。例外は、保護された場所への書き込み・rmで重要な場所を消す操作・ドメイン付きのコマンド（許可があっても分類器へ）と、auto modeで外れる広い許可
・許可は3つに分けて見る
  ①何でも実行できる広い許可（Bash(*)、Bash(python*)など）→ auto modeでは外れるが、手動に戻すと効き直す。手動でも使うなら消す
  ②分類器が止める操作まで含みうる許可（Bash(git *)・Bash(git push *)・Bash(gh *)・Bash(curl *)・Bash(mv *) など）→ 公式の「外れる許可」の一覧（Bash(*)・広いインタプリタ・パッケージマネージャのrun・Agent・Monitor）に入っていない。外す基準は「何でも実行できるか」なので、git が外れるかは公式に書かれていない（C-3）。残っていれば、force push・git stash drop・PRのマージ・外部への送信が分類器を通らずに実行されうる。手動に戻すと、どちらにしても聞かれずに通る。git add・git commit のように狭くする
  ③狭い許可（Bash(npm test)など）→ 残してよい。ただし公式は「狭い許可も、想定外のフラグや引数を分類器に見せずに通しうる」と書いている
・auto modeの人の選択肢：~/.claude/settings.json に autoMode.classifyAllShell: true を書くと、Bash・PowerShellの許可（allow）ルールがauto modeの間だけ一時停止し、すべてのシェルコマンドが分類器に回る（ask・denyは止まらない）（公式・v2.1.193以降）。待ち時間と判定の回数は増える。手動に戻すと許可はふつうに効くので、手動でも使う人は狭める作業も要る
→ 読者3は、手順3で許可を狭める（またはclassifyAllShell）→ 手順4で確認を見直して着く
→ 読者5（手動）も、広い許可があると本番の作業で聞かれずに通るので、ここを通る

手順4：確認（ask）と拒否（deny）に書く操作を決める
・書きたいものがなければ、何も書かなくてよい（分類器に任せる）→ 読者1・2はここで着く
・分け方の表（本文では短い表1つ）
  | 分け方 | 例 |
  | 確認（ask）に残す | git push・gh pr create（公式の例。毎日何度もする人は向かない） |
  | 拒否（deny）に書く | .envや鍵ファイルの読み取り |
  | 書かずに分類器に任せる | force push・git reset --hard・本番デプロイ（手順3で許可を狭めたうえで。手動なら、許可に当たらない操作は毎回聞かれる） |
・書く場所：/permissions の画面か、~/.claude/settings.json
・必ず自分で判断したい操作 → 確認（ask）。候補は、分類器が既定で通す操作から選び、鳴る回数が少ないものに絞る
  例：作業中のリポジトリへのpushやPRの作成（公式が、人を入れたいときの例に挙げている。毎日何度もする人は、③の97%と同じ状態になるので向かない）
・Bashルールの書き方に左右されない方法（公式）
  コマンドの全文を検査して確実に止めたい → PreToolUse フック
  プロジェクトの方針としてClaudeと分類器に伝えたい → CLAUDE.md に「never force push」のように書く（伝える方法で、止める仕組みではない）
・絶対に通さない操作 → 拒否（deny）。確認と違い、どのモードでも聞かずに止まる
  例：.env（パスワードやキーを置くファイル）の読み取り。分類器は「.envを読んで、対応するAPIへ送る」を既定で通す（公式）
  Readの拒否は、Bashのcatなど、Claude Codeが見分けられる読み取りコマンドにも効く。grep -r のようにファイル名を書かない読み取りや、Pythonなどのスクリプトが自分で開く読み取りには効かない（公式）
・Bashのaskとdenyは、Claude Codeが解析したコマンドの形に当たる。別の呼び出し方には当たらないことがある（公式：プログラムを囲む安全の境界ではない）。Bash(git push *) は git -C . push origin main に当たらない。当たらなかった書き方は、手順3の許可とモードで決まる。だから手順3が先
・分類器が既定で止める操作（force push・git reset --hard など）は、手順3で許可を狭めていれば、askに書かなくても分類器が止める（確実ではない）。askに書くと、止まる代わりに聞かれて、押せば通る
・askは、普段の作業に出てこない語で書く。rm -rfのように日常の片付けにも出る語で書くと、毎日鳴る（⑤）
→ 読者3（auto modeに切り替えた場合）も、手順3のあとここに着く

## ② auto modeで、自動になる操作・止まる操作・聞かれる操作
→ 手順の次に読者が知りたいこと（GPTの指摘で③から繰り上げ）。読者4の答えで、この記事の中心。「何を自分で書くか」が分かる章
→ 表1つ（公式ドキュメント permission-modes・2026-09-25取得）

| 操作 | auto modeでの扱い |
|---|---|
| 作業フォルダ内のファイルの読み取り・編集（.git・.claudeなど保護された場所を除く） | 原則自動。編集は通常、分類器を通らない。サーバー側の判定が有効なセッションでは、読み取り専用のコマンドも判定を待つことがある |
| 作業中のリポジトリへのpush（productionやgh-pagesなど、デプロイ先の名前のブランチを除く） | 分類器が既定で通す（自分のallowに当たれば、分類器も通らない） |
| .envを読んで、対応するAPIへ送る | 分類器が既定で通す |
| force push・git reset --hard・git clean -fd | 分類器が既定で止める |
| セッション前からあったファイルを戻せない形で消す | 分類器が既定で止める |
| 本番デプロイ・秘密情報を外部へ送る | 分類器が既定で止める |
| .git・.claude・.zshrcなどへの書き込み、rmで / や ~ や作業フォルダ（とその親）を消す | 許可ルールがあっても自動にならず、分類器が判定 |
| 作業フォルダの外を初めて読むとき | 1回だけ聞かれる |
| 自分で書いた確認（ask）に当たるもの、フック（PreToolUse）が確認を返した操作 | 必ず聞かれる |
| 確認必須の印が付いたアプリ・MCPのツール、Claudeからの質問 | 必ず聞かれる |
| 分類器が3回続けて、または1セッションで20回止めた後 | 手動の確認に戻る。その確認を承認するとauto modeに戻る（公式・変更不可） |

→ 分類器が止めたとき：通知が出て、Claudeは別の方法を探すか、直接聞いてくる。止めた理由はルール名で出る（例：[Data Exfiltration]）
→ 自分で通したいとき：会話の中で、操作と対象を名指しして許す（例：どのブランチへのforce pushか）。または /permissions の「Recently denied」で r を押して再実行。解除できない止め方もあり、そのときはauto modeを出て自分で承認する（秘密情報を外部へ送るなど）
→ 分類器が答えを返せなかったとき：「cannot determine the safety」と出て、その操作は実行されない。多くは一時的（公式）
→ 既定のリストは claude auto-mode defaults で全部見られる（公式）
→ 自分のaskが原因で聞かれているなら、手順4へ戻る
→ 【インフォ】分類器の費用：Pro・Max・Teamは課金しない（8/7から）。Enterprise・APIは使用量に数える（9/25のドキュメント。サーバー側で判定する場合は別に数えない。公式ブログは8/7時点で課金をやめる予定と書いている→公開直前に確かめ直す）

## ③ 人の確認は、どのくらい効いているか
→ 読者2の不安に答える章。「確認を残すほど安全」とは限らないことを公式の数字で
→ 表1つ（公式ブログ 2026-08-07・原文で件数まで確認済み）

| 公式の数字 | 中身 |
|---|---|
| 97% | 許可の確認に「許可」と答えた割合（プランの承認は39%が却下） |
| 約17%→約5% | 危険なコマンドを人が止めた割合。セッションの始め→50回以上確認した後 |
| 13.6%と89% | 危険なコマンドを止めた割合。人（143/1,053）とauto mode（937/1,053） |
| 6.3%と2.4% | 安全パイプラインがレビュー対象として抽出したセッションの中で、頼んでいない本番レベル（深刻度7以上）の害のある操作を含んだ割合。手動とauto mode |

→ 条件を2文：17%→5%と13.6%は同じ実験。研究用の環境で、途中の確認1回だけを危険なコマンドに差し替えて測り、参加者は評価されていると知っていた。6.3%と2.4%は2026年5〜6月、データ利用に同意したアカウントで、安全チェックが要確認とした実際のセッションの数字
→ 表の後に言えること：確認は回数が増えるほど止められなくなる。確認を「必ず自分で判断したい所」に絞ることが、安全にも効く
→ 但し書き1文：公式はauto modeでも「リスクがなくなるわけではない」と書いている

## ④ 自分で書くルール（allow・ask・deny）は、分類器より先に効く
→ 読者3・4の答えの仕組み。手順3が「確認より先」である理由
・判定の順番（原則）：①自分のルール → ②作業フォルダ内の読み取り・編集 → ③分類器。ルール同士は deny → ask → allow の順
・例外：保護された場所への書き込み・rmで重要な場所を消す操作・ドメイン付きのコマンドは、許可があっても分類器へ回る
・auto modeに入ると、何でも実行できる広い許可は一時的に外れる。設定ファイルは書き換わらず、別のモードに戻すとすぐ効く
・外れるのは「何でも実行できる」広い許可（公式の一覧：Bash(*)・広いインタプリタ・パッケージマネージャのrun・Agent・Monitor）。Bash(git *) は一覧に無いが、外れるかの明記もない（C-3）。公式は「狭い許可も、壊す引数を分類器に見せずに通しうる」と書いている。全部を分類器に回すなら classifyAllShell。/auto-mode-setup は保存後、「auto modeが無視する許可」と「壊す操作を自動で通す許可」を分けて、消すよう提案する（公式）
・Bashのaskとdenyは、コマンドの形に当たる。askで止めたつもりの操作も、書き方が違えば当たらず、ほかの許可と分類器で決まる
・askは、auto modeでも必ず聞く。denyは、どのモードでも止める
→ 核の1文：Bashの確認ルールはコマンドの形に左右される。だから確認に何を残すかと一緒に、貯めた許可が何を通しうるかを見る

## ⑤ 例：残したforce pushの確認は11日間鳴らず、鳴ったのは片付けの rm -rf だった
→ 本人の環境の実測。記事の核心ではなく、手順3の例として1章だけ
→ 体験は圧縮する。表1つ＋短い地の文

・2026年8月12日にauto modeへ。それまでに押した「今後は聞かない」は331件で、このリポジトリのローカル設定に今も残って効いている
・全体の設定：許可80件／確認6件（sudo・rm -rf・git push --force・git push -f・git reset --hard・git clean）／拒否6件（.env・鍵ファイルの読み取り）
