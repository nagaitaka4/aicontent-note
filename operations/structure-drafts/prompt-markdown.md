# 構成案：プロンプトはマークダウンで書くべき？基本で足りる理由と3つの例外（no.87）

## 書き方（この記事で守ること）

- 見やすく・誰が読んでもわかる・為になる・堅い表現なし。そのうえで端的に、要所だけ
- 言いたいこと（1文）：**プロンプトは基本マークダウンで足りる。ただし、返事の項目をそろえたいとき・ツールが形式を決めているとき・守らせたいルールが増えたときは、別の形に分ける**
- 読者がどこを見れば答えか：リード、H2①の表（良い点）、H2②の表（3社の公式）、H2③の表（3つの場面）
- 「マークダウンで書けば精度が上がる」と書かない。公式は「役立つことがある」、研究は「形式で結果が変わることはあるが、大きいモデルほど差は小さい」まで
- 筆者のやり方を正解として言い切らない（「私の指示書では」と主語を出す）
- 制作の記録（記事番号・日付・ファイル名・コミット）を本文に出さない。行数・字数は読者の判断の根拠になる所（H2④）だけ、概数で
- 英語のリンク（OpenAI・Google・arXiv）は、本文で中身を日本語で説明し、`operations/en-link-allow.tsv`に登録する
- 写す元の整理（3つの場面）を借りるので、本文で元の記事を紹介してリンクする。文章は写さない

## プロンプトをマークダウンで書くと何が良いのか
→ リード（2文）：良いのは、人とAIの両方に区切りが伝わること。記号の書き方はMarkdownとはの記事（no.35）にまとめた（1行リンク）
→ 表（2列：誰にとって／良い点）※3行
　 　**書く人・直す人** ／ 見出しで「目的」「条件」「禁止」を分けると、どこを直せばいいかすぐ見つかる。プロンプトは一度で終わらず、読み返して直すもの
　 　**AI** ／ 見出しと箇条書きで、どこからどこまでが条件かが伝わる（OpenAIの公式ガイドも、区切りと階層を伝えるのに役立つことがあると書いている）
　 　**ツールを替えるとき** ／ ただの文字なので、ChatGPTにもClaudeにもGeminiにもそのまま貼れる
→ 地の文（2文）：検索の上位には「マークダウンで書くと精度が上がる」という記事が多い。2024年の研究（arXiv・リンク）では、同じ中身でも書き方（普通の文・マークダウン・JSON・YAML）で結果が変わることはあったが、大きいモデルほど差は小さく、どの書き方が勝つかもタスクで違った

→ 【メモ】1文で済む頼みごとなら、見出しを立てるほど分ける中身が無い。普通の文でいい
→ ⚠️ 研究はGPT-3.5とGPT-4（2024年）。今のモデルの数字として書かない。「最大40%」は書くなら「古いモデルで、コードの書き換えのタスクで」と条件をつける

## ChatGPT・Claude・Geminiの公式は何と言っているか
→ リード（1文）：3社とも「区切りをはっきりさせる」ことを勧めていて、マークダウンだけを指定してはいない
→ 表（3列：AI／勧めている区切り方／気をつけること）※3行
　 　**Claude（Anthropic）** ／ XMLタグ（<instructions>などで囲む）。順番が大事なら番号つきの箇条書き ／ ==プロンプトの書き方が返事の書き方にうつる==。マークダウンを減らすと、返事のマークダウンも減る
　 　**ChatGPT（OpenAI）** ／ マークダウンの見出しと箇条書き。参考資料の始まりと終わりはXMLタグ ／ 長い資料をJSONで渡すと結果が悪かった（以前のガイド）
　 　**Gemini（Google）** ／ XML風のタグか、マークダウンの見出し ／ 1つのプロンプトの中ではどちらかにそろえる
→ 【チェック】返事を文章で受け取りたいのに箇条書きばかり返ってくるなら、プロンプトの見出しや箇条書きを減らしてみる
→ ⚠️ Claudeは日本語版の公式（platform.claude.com/docs/ja/…）にリンク。OpenAI（現行のガイド＋GPT-4.1のガイド〔アーカイブ・時点を書く〕）とGoogle（?hl=jaでも本文は英語）は英語のリンク＝en-link-allow.tsvに登録

## マークダウンだけでは足りない3つの場面
→ リード（2文）：noteの記事が「基本はマークダウンで合っていて、苦しくなる場面だけ切り替える」と整理している（リンク）。私の指示書で、実際に別の形に分けたのは次の3つ
→ 表（3列：場面／分け方／例えば）※3行
　 　**返事の項目を毎回そろえたい** ／ 指示はマークダウンのまま、返事の形をJSONで指定する ／ Xの投稿案をAIの読者役に採点させるとき、返事は「JSONだけ」と項目を決め、合否はプログラムが出す
　 　**ツールが形式を決めている** ／ そのツールの形に従う（YAML・JSONなど） ／ 記事ファイルの冒頭の題・スラッグ・説明文はYAMLの形で、WordPressに入れるプログラムがそこを読む。Claude Codeの設定はJSON
　 　**守らせたいルールが増えた** ／ 測れるルールは、文章ではなくチェックのプログラムに移す ／ 一文の長さや見出しの字数は、プログラムがNGを出す（次の見出しで）
→ H3：返事の項目をそろえる頼み方
　 　→ 地の文（1文）：自由に書かせると、項目が抜けたり言い方が揺れたりして、毎回人が読んで判定することになる
　 　→ コードの欄（そのまま使える型・マークダウン＋返事はJSON）
　 　 　# 依頼
　 　 　［例：下の投稿案を、ブログ運営を始めたばかりの人として読んでください］
　 　 　# 見てほしいこと
　 　 　- ［例：意味が分からない言葉］
　 　 　- ［例：最後まで読みたくなるか（1〜5）］
　 　 　# 返事の形
　 　 　JSONだけを1つ返してください。前後に文章を書かないでください。
　 　 　{"unknown": [], "read": 3, "comment": ""}
　 　 　# 投稿案
　 　 　［ここに貼る］
　 　→ ⚠️ 型は［例：〜］を埋める形（メモリ feedback_howto_template_over_example）。実物（x-review-pack.py）の項目名はそのまま写さず、読者が使える例に
→ ⚠️ 元の記事の「大量のデータはCSVで分ける」は、私の指示書に実物が無い＝表に入れない（書くなら元の記事の紹介の中で触れるだけ）

## ルールが増えたら、マークダウンの指示書は効きにくくなる
→ リード（2文）：AIに守らせたいルールを全部マークダウンの指示書に書き足していったら、守られないルールが増えた。ルールは増えるほど1つずつが薄まる
→ 地の文（2文）：私の記事の書き方の指示書は、失敗のたびに書き足して350行・4万字を超え、「省略禁止」が30か所以上あった。それでも、同じ指摘を何度も受けた
→ 表（3列：ルール／前：指示書に文章で書く／今：プログラムがチェックする）※3行
　 　**一文の長さ** ／ 「一文は短く」と書くだけ ／ 60字を超えたらNG
　 　**表の強調** ／ 「表には強調を入れる」と書くだけ ／ 強調の無い表はNG
　 　**引用の記号（>）** ／ 使ってよいかが3つの指示書で食い違っていた ／ 1か所で決め、プログラムがNGを出す
→ 【ポイント】マークダウンの指示書に残すのは、測れない原則だけ（体験していないことを書かない、など）
→ 1行リンク：ルールファイルとは？AIを安定運用する指示書の考え方
→ ⚠️ 「350行・4万字超」「30か所以上」は実数（357行・42,726字・33行）を越えない概数。日付・ファイル名は出さない
→ ⚠️ 「プログラムに移したら同じ指摘がゼロになった」とは書かない（記録に無い）
→ ⚠️ 締めの決めゼリフを置かない
