# このファイルの位置づけ

**次の記事1本だけの診断ログ。恒久ルールではない。**運用に組み込むかどうかは、この1本の結果を見てから判断する。`lessons.md` にも `article-flow.md` にも、現時点では何も追記しない。

**工程は一切変更しない。**現在のルールのまま1本作り、記録だけを取る。工程を変えながら測ると、何が効いたのか分からなくなる。

## 何を判定するのか

ボトルネックが **初稿生成（WRITE）** にあるのか、**初稿を完成稿へ収束させる工程（EDIT＋CASCADE）** にあるのかを分離する。ここが未確定のまま何を直しても当てにならない。

**注意：EDIT＋CASCADEが多かったとしても、「初稿から制約を外す」案が支持されるわけではない。**支持されるのは「ボトルネックは収束工程にある」という診断まで。そこから「制約を減らす／干渉を解消する／チェックの位置を変える」のどれが正しいかは、**CASCADEの中身**を見ないと決まらない。だからCASCADEログが本体。

- **通常の新規記事**にする。リライト（`article-flow.md` §6）は工程が別なので対象外
- シリーズ記事は前回記事との接続作業が乗るため、可能なら避ける
- 特殊フォーマット（ハウツー・インタビューあり）も避ける

# 記録ルール

記録は**3つの独立した軸**で取る。混ぜると二重計上になる。

## 軸1：時間の位置（初稿完成時刻で切る）

**初稿が完成した時刻を1点だけ打つ。**それより前が「初稿生成」、それ以降が「収束工程」。

タグで切らず時刻で切る。FACTは初稿後だけに発生するものではない（執筆中にURLを確認する作業もFACT）ため、タグで前後を分けると必ずズレる。

## 軸2：活動タグ（相互排他・合計100%）

| タグ | 定義 |
|---|---|
| **WRITE** | まだ存在しない本文を書く |
| **FACT** | 事実・出典・ファイルとの整合性を直す |
| **EDIT** | 文長・平易化・重複・文体・読点・表・ブロックを直す |

**この3つで100%になる。**CASCADEはここに入れない（下記・軸3）。

構成・インタビュー・アイキャッチは**執筆工程の外**として別枠で記録し、分母に入れない。

## 軸3：CASCADEフラグ（時間分類ではなく発生原因）

**各作業ブロックに「これは直前の修正が引き起こしたものか」のフラグを立てる。**

CASCADEを時間分類の4つ目にすると、同じ5分が EDIT にも CASCADE にも計上されて合計が100%を超える。**CASCADEは活動の種類ではなく、その修正がなぜ発生したかの属性。**

集計時は「CASCADE由来の時間が執筆関連総時間の何%か」を出す。

## 時間の取り方

CCはターン単位でしか時刻を取れないため、**各作業ブロックの開始時と終了時に `date` を実行して記録する**。

**ユーザーの確認待ち時間は WAIT として分離し、分母に入れない。**これを混ぜると、CCの処理時間ではなく往復回数を測ることになる。

## CASCADEの検出方法（主観に頼らない）

**修正のたびに `article-self-check.py` を実行し、修正前には無かったNGが出たら CASCADE 1件として記録する。**

これで「何を直した結果、何が壊れたか」が機械的に取れる。目視で気づいた分（スクリプトが検出しない種類の破壊）は、検出方法の欄に「目視」と書いて同じ表に足す。

**集計時に機械検出と目視検出を分ける。**両者は次に見るべき場所が違う。

- 機械検出が中心 → `.py` の閾値・修正方法・原則3/4の関係を重点調査
- 目視検出が中心 → 散文ルール同士の干渉を重点調査（例：「1文に主題を複数入れない」で短文化した結果、機械的な文章になり「AIっぽさ」の修正が必要になる。この種の干渉はどちらもNGを出さないので機械差分に現れない）

# 判定ライン（事前に固定・後から解釈を変えない）

| 実測 | 判定 |
|---|---|
| 初稿完成までが70%以上 | 収束工程は主因ではない。生成そのもの・資料取得・実行待ちなど初稿生成側を調べる |
| 初稿完成後が50%以上 | ボトルネックは収束工程。**ここから先はCASCADEログの中身で対処法を決める** |
| CASCADE由来の時間が30%以上 | ルール間の相互作用が主要因。**CASCADEログから原因ルール対を特定する** |
| CASCADEが多い＋機械検出が中心 | `.py`の閾値・修正方法・原則3/4との関係を重点調査 |
| CASCADEが多い＋目視検出が中心 | 散文ルール同士の干渉を重点調査 |

## 判定は3段階で読む（順番を守る）

1. **時間位置** — 初稿前か初稿後か
2. **活動** — WRITE / FACT / EDIT のどれか
3. **修正連鎖** — CASCADEがどれだけ占めるか

**「初稿完成までが70%以上＝生成そのものが遅い」と直結させない。**初稿完成前にはWRITEだけでなくFACTも存在する。たとえば「初稿まで75%／WRITE 30%／FACT 45%」なら、ボトルネックは生成ではなく**初稿を作るための事実確認**。活動タグを残しているのはここを切り分けるため。

**「CASCADEが多い＝原則3・4が原因」と決めつけない。**原則3は影響範囲を見るルールであって、最初の破壊を起こしているとは限らない。「60字上限 × 短文化という直し方 × 段落連続基準」のような**ルール対の組み合わせ**が原因で、原則3はそれを発見しているだけの可能性がある。原因の特定はCASCADEログの実データで行う。

# 判定結果（2026-08-17）

| 判定ライン | 実測 | 該当 |
|---|---|---|
| 初稿完成までが70%以上 → 収束工程は主因ではない | 31.7% | 非該当 |
| **初稿完成後が50%以上 → ボトルネックは収束工程** | **68.3%** | **該当** |
| CASCADE由来の時間が30%以上 → ルール間相互作用が主要因 | 14.4% | 非該当 |
| CASCADEが多い＋機械検出が中心 | 3件・全て機械検出 | 件数が少なく判定保留 |

**結論：ボトルネックは収束工程。ただしCASCADEは主要因ではない。**

収束工程437秒の内訳を見ると、最も大きいのは**初稿がNG 10件を出したこと自体**（その一括修正に152秒）。次が**通し読み**（106秒）。CASCADEは92秒で3番目。

つまり「1つ直すと別が壊れる」よりも、**初稿の段階で10件の違反が残ること**の方が時間を使っている。

## 想定と違った点

- **WRITE（初稿生成）は約67秒しかかかっていない。**「執筆に時間がかかる」の実体は、生成ではなく初稿を基準に合わせる工程だった
- **FACT（執筆前確認）が136秒でWRITEの2倍。**一次情報を原文で開く作業が効いている。ただしこれは記事の質に直結するので、削減対象とは限らない
- **通し読み1回で、機械が原理的に検出できない問題が出た**（原文でない文を引用として提示していた）。これは事実性の問題で、放置すれば公開後に効く

## 発見したルール間の矛盾（今回は変更せず記録のみ）

**`>`（Markdown引用）の扱いが、2つのルールファイルで逆になっている。**

| ファイル | 記述 |
|---|---|
| `operations/wp-block-guide.md` | 引用ブロックは「Markdownの `>` をそのまま使う」 |
| `rules/article-flow.md` §5 | ブロック記法は`【ブロック名】<br>`。「`>`もHTMLコメントも使わない」 |
| `operations/article-self-check.py` | `>` の使用を **NG判定** |

初稿でGoogle公式を`>`で引用したところNGになった。**外部からの引用を正しく書く方法が、現状のルールでは定義されていない。**CASCADE-2（擬似引用 → ブロック削除 → リード文膨張）の起点はここ。
