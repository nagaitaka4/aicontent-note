# WPブロック活用ガイド（SWELL）

記事制作時にどのブロックをどう使うかの運用基準。
MDファイル上では`>`（Markdown引用記法）を使わず、`【ブロック名】`を1行目に単独で書く形式で記載する（2026-07-22〜）。WP入稿時に差し替える。

行を分けたい箇所は`<br>`を使う（空行ではなく`<br>`。2026-07-22再訂正）。

```
【ポイント】<br>
内容
```

複数項目を列挙する場合も、各項目の末尾に`<br>`を付けて改行する（最後の項目には不要）。

**この`<br>`ルールは【ブロック名】の中に限らない（2026-07-23〜）**：本文中の`・`箇条書き（ブロックに入っていない、地の文の中の箇条書き）でも、複数項目を並べる場合は空行ではなく`<br>`で改行する。空行区切りは段落として扱われWP上で余白が大きく空くうえ、コピペ後の編集が大変になるため使わない。

```
【インフォ】<br>
見出し<br>
・項目1<br>
・項目2
```

**理由**：
- `>`（Markdown引用）を使うと、WPにコピペした際に各行が個別の引用ブロックとして認識され、ユーザー側で1行ずつ`>`マークを消す作業が発生する
- 単純な改行（空行なし）はMarkdown上で無視され、行が連結されて1行の文章になってしまう
- 空行を入れると別々の段落として扱われ、WP上で段落間の余白が大きく空いてしまう
- `<br>`を使うと、1つの段落のまま・余白を作らずに・行だけを分けられる。この3点を同時に満たすのは`<br>`のみ

## 入稿は変換スクリプトで行う（2026-08-26新設・手作業は廃止）

```
python3 operations/md-to-wp.py articles/<slug>.md
```

出力された `operations/wp-output/<slug>.wp.txt` を**全文コピー**し、
WPの記事編集画面 → 右上「⋮」→**「コードエディター」**に貼り付ける
（ビジュアルエディタに貼るとブロックにならない）。

先頭には、WPの入力欄に写す情報（タイトル・スラッグ・説明文・カテゴリー・タグ・アイキャッチ）が
frontmatterから転記されている。**これも段落ブロックなので、各欄に写したらブロックごと削除する。**
（プレーンテキストで出すとWPが「クラシックブロック」として扱い、貼り付け後に編集も削除もできない）

これで次が自動で入る。**手で1つずつブロックを作る作業はしない。**

- 【ブロック名】→ SWELLのスタイル付き段落
- 区切り線（各H2直前・CTA直前・記事末尾＝合計7本前後）
- 表・H2・H3・内部リンク・箇条書きの装飾
- CTAボタン（`loos/button`）・関連記事（`loos/post-link`・記事IDは公開APIで自動取得）
- 2文以上の段落の句点改行（`<br>`）

⚠️ **figcaptionに属性を足さない**（2026-09-16・no.68で事故）。画像ブロックのcaptionはfigcaptionの中身だけを見るため、
`style`や`class`を足すとエディターで「想定されていないか無効なコンテンツが含まれています」になる。
**キャプションの左揃えは、投稿ごとのカスタムCSS（SWELLの「カスタムCSS & JS」）で行う。**
SWELLが`.wp-block-image figcaption`で中央寄せしているので、**同じ強さのセレクタ＋`!important`**が要る：

```
.wp-block-image figcaption,
.wp-element-caption {
  text-align: left !important;
}
```

⚠️ **投稿ごとのCSSは編集画面には効かない**（テーマのeditor_style.cssが中央寄せのまま）。
左揃えになったかは**プレビュー（フロント側）で確認する**。編集画面でもそろえたい場合は、サイト全体のカスタムCSSに入れる（ユーザーの判断）

**変換しないもの**（記事ごとに人が判断して付ける装飾）：`is-style-stitch` などの段落装飾、
画像・キャプションボックス。

⚠️ **リード1文目のマーカーは、スクリプトが変換する**（2026-09-16に実測で訂正）。
`==〜==`はリードも含めて`swl-marker`に変換される。no.68の出力でリード＋本文3件＝4件を確認した。
以前ここに「リード1文目のマーカーは変換しない」と書いていたが、実物と違っていた。

### 強調の記法（2026-08-26追加）

| MD記法 | 変換後 | 使いどころ |
|---|---|---|
| `[text](url)` | `<a href="url"><strong>text</strong></a>` | リンクは**自動で太字**。`**`を付けない |
| `**text**` | `<strong>text</strong>` | 重要な部分 |
| `==text==` | `<strong><span class="swl-marker mark_yellow">text</span></strong>` | 最重要。1記事3〜5箇所まで |

実測（公開20本）：アンカー61件中53件が太字（87%）／マーカーは97件すべて`swl-marker mark_yellow`で、うち73件（75%）が`<strong>`と併用。1記事あたり1〜13件・中央値4件。

`article-self-check.py`は字数を数えるとき`**`と`==`の記号を外す（`strip_decoration`）。

## ⚠️ 本番の記事に「試しの値」を書かない（2026-09-17・no.68で公開まで残った）

**no.68で、抜粋（excerpt）に「x」が入ったまま公開された。**原因はCC。9/16 12:11、本文のPOSTが`Failed to fetch`で失敗した原因を切り分けるために、`POST /wp/v2/posts/948 {excerpt: 'x'}`を「小さい送信なら通るか」のテストとして送り、戻さなかった。ユーザーが公開後に編集画面のサイドバーで「アイキャッチの下のx」に気づいた。

- **通信の切り分けは、記事の中身に触れない方法でする。**`GET /wp/v2/posts/<id>?context=edit`（読むだけ）か、**いま入っている値をそのまま送り返す**（`{excerpt: cur.excerpt.raw}`）
- 試しに値を書き換えたら、**同じ呼び出しの中で元に戻し、戻ったことを実測する**
- **入稿を報告する前に、`excerpt.raw`が空であることを確かめる**（このサイトの公開記事は抜粋が空。SWELLはリード文から自動で要約を作る。抜粋に何か入っていると、トップページの記事カードにそのまま出る）
- 抜粋の履歴は`/wp/v2/posts/<id>/revisions?context=edit&_fields=id,modified,excerpt`で、いつ変わったか分かる

## ⚠️ 下書きを直す前に、WP側の本文とMDの差分を取る（2026-09-16・no.68で発生）

**ユーザーはWPの編集画面で本文を直し、太字や表の列幅を付ける。** 下書きを見せた後にCCがブロックを置き換えると、その修正を消してしまう。**ブロックを置き換える前に、必ず差分を取る。**

手順（no.68で実際に使った方法）。

1. `?context=edit`で`content.raw`を取り、`\n\n`でブロックに分ける
2. MDから生成した`wp.txt`の本文も同じように分け、**各ブロックのSHA-256（先頭8桁）**をブラウザに渡す
3. ハッシュが一致しないブロックの番号だけを出す（no.68では87ブロック中10件）
4. さらに**タグを除いた素のテキスト**でも突き合わせ、「本文が変わった」のか「装飾だけ付いた」のかを分ける
5. 本文が変わっていたらMDに取り込み、装飾だけならそのブロックには触れない

**MDで表せない装飾は、そのブロックを置き換えない。** no.68では表の1列目の幅（`{"swlCell1Width":"180px"}`）がこれに当たる。太字は`**〜**`で書けるのでMDに取り込む。

**誰がいつ直したかは`/wp-json/wp/v2/posts/<id>/revisions`で分かる**（`?context=edit`を付けないと`content.raw`が返らない）。2つのリビジョンをブロックに分けて差集合を取れば、変更点だけが出る。

## ページ内リンク（表から各見出しへ飛ぶ・2026-09-18・no.69）

一覧表の項目から本文の見出しへ飛ばすときは、MDで次のように書く。`md-to-wp.py`が見出しに `id` を付ける。

```
| 1 | [思っていた答えと違うのは、プロンプトのせい？](#q1) | … |

### Q1. 思っていた答えと違うのは、プロンプトのせい？ {#q1}
```

- `{#q1}` は見出しの末尾に半角スペースを空けて書く。**見出しの直後の空行は消さない**（消すと次の段落が見出しに吸い込まれる。no.69で一度起きた）
- 飛び先の見出しが無いリンクは、`article-self-check.py`の「リンク記法が崩れていない」でNGになる
- SWELLの目次も、この `id` をそのまま使う（目次のリンクが `#index_id◯` から `#q1` に変わるだけで、動きは同じ）
- 押すとSWELLのスムーススクロールで、見出しが固定ヘッダーのすぐ下に止まる（プレビューで実測：ヘッダー下端96px・見出し上端104px）
- ⚠️ Chrome拡張で裏のタブを操作して確かめると、スクロールのアニメーションが止まって「動かない」ように見える（`document.visibilityState` が `hidden`）。リンクが壊れているわけではない

## セクション区切り線（2026-08-20確定・省略禁止）

WP入稿時、**区切り線ブロック（`wp:separator`）を次の3箇所に入れる**。

1. **各H2見出しの直前**（最初のH2の前・CTA直後のH2の前も含む）
2. **CTAブロックの直前**（途中CTA・末尾CTAとも）
3. **記事末尾**（末尾CTAボタンの後に1本）

マークアップは既存記事と同一：

```
<!-- wp:separator -->
<hr class="wp-block-separator has-alpha-channel-opacity"/>
<!-- /wp:separator -->
```

**経緯**：no.55までは各H2の前に区切り線が入っていたが、no.59・no.60で抜けたままユーザー確認まで進み、2026-08-20に指摘された（no.60はユーザー判断でそのまま公開）。パターンはno.55（rule-file-basics）の実測が基準。

## 使用頻度の目安

- **多用するブロック**：ポイント・チェック・バツ印
- **ときどき使うブロック**：アラート・グッド・バッド・メモ
- **特定の場面だけ使うブロック**：吹き出し・インフォ・アナウンス・はてな
- **スタイル・ボーダー**：1記事に多くても2〜3か所。使いすぎると見た目がうるさくなる

### ⚠️ ブロック要素を連続で並べない（2026-08-13追加）

**`【】`の強調ブロックは「そこだけ目立たせる」ための箱。3個以上を連続で並べると強調が機能しなくなり、箱が並んだだけの別の壁になる。**手順や項目の列挙は`・`箇条書き（各行末`<br>`）か表で書く。

- **`【ステップ1】`のような記法は存在しない。**`【】`に入れるのは上の一覧にあるブロック名だけ。手順を番号付きで見せたい場合はSWELLの構造ブロックを使い、MDには`<!-- ステップブロック -->`とメモする
- **ステップブロックの用途は「設定・ハウツー系」。**実測の記録・体験の流れを書く記事で使うと、記事の立場（記録）と見た目（マニュアル）が食い違う。記事がHowToかどうかを先に決めてから選ぶ
- 経緯：no.57で`【ステップ1】`〜`【ステップ5】`を並べたが、記法がガイドになく、かつ「HowToにしない」という記事方針と逆の見た目になっていた

## 本文HTMLをWPへ運ぶ方法（2026-09-22・no.70で確立）

**このサイトは画像以外のアップロードを拒否する。**`.txt`も`.csv`も「このファイルタイプをアップロードする権限がありません」で失敗した（9/22実測）。
クリップボード経由（`pbcopy`）も、CCのシェルからは書き込めない（`pbpaste`が0バイト）。

**運び方**：本文HTMLを**PNGの画素に詰めて**メディアにアップし、WPの画面内で読み戻す。全文をトークンに載せずに済む。

1. `md-to-wp.py`の出力から、先頭の入稿情報ブロック（最初の`<!-- /wp:paragraph -->`まで）を落とす
2. PILで、先頭4バイト＝本文のバイト長（ビッグエンディアン）＋本文バイト列をRGBの画素に詰めてPNG保存（可逆なので完全に戻る）
3. `media-new.php?browser-uploader`でアップ →
   `document.querySelector('#async-upload').form.querySelector('#html-upload').click()`
4. ページ内のJSで、そのPNGを`createImageBitmap`→`OffscreenCanvas`→`getImageData`で読み、
   RGBを並べ直して`TextDecoder('utf-8')`で本文に戻す。**SHA-256をPython側と突き合わせて一致を確認する**
5. `POST /wp/v2/posts`で下書きを作る（`content`に本文・`status:'draft'`）
6. **運び役のPNGは`DELETE /wp-json/wp/v2/media/<id>?force=true`で必ず消す**

**⚠️ RESTで本文を送ったあとに、エディターで`savePost()`を呼ばない**（2026-09-22・no.70で本文が巻き戻った）。
エディターは前のセッションのローカル自動保存を復元することがあり、その状態で保存すると古い本文が書き戻される。
**順番はSSPの説明文 → 本文のREST送信 → RESTとリビジョンで検証**。検証でエディターを開かない。

**REST APIのnonce**：`media-new.php`には`wpApiSettings`が無い。
`/wp-admin/admin-ajax.php?action=rest-nonce`で取れる（どの管理画面でも可）。

**説明文（description）の入れ先**：`excerpt`ではなく**SEO SIMPLE PACKの`ssp_meta_description`**。
公開済み5本の`excerpt`はすべて空で、`<meta name="description">`はSSP側から出ている（9/22実測）。
テキストエリアに値を入れて「下書き保存」を押すとメタボックスごと保存される（RESTでは触れない）。

**タグ**：無ければ`POST /wp/v2/tags`で作ってからIDで渡す。
**アイキャッチ**：先にメディアへアップし、`featured_media`にIDを渡す。altは`POST /wp/v2/media/<id> {alt_text}`。
