# 記事制作フロー・ルール

記事を書く・編集するすべての作業で参照する。

- **測れるルールはスクリプトが正**：執筆前=`operations/article-precheck.py`／提示前=`operations/article-self-check.py`。文字数・一文の長さ・表の数・CTA・記法などの数値基準はスクリプトにのみ存在し、このファイルには書かない
- このファイルに置くのは**手順**と**機械化できない判断基準**だけ
- ルールの由来・失敗の経緯は`operations/lessons.md`（運用には読まなくてよい）

## 4原則（最優先）

1. **執筆前に確定できることを、執筆後に直さない**
   着手前に`python3 operations/article-precheck.py <slug> "KW"`を実行し、出力①〜⑥（適正分量・内部リンク候補・自社情報の照合・外部出典・制約・提示基準）をすべて潰してから書き始める。
2. **数値のために内容を削らない**
   **文字数に上限・目標値は設けない。**適正な分量は記事の検索意図とKWによって決まる。判断の優先は「正確 → 分かりやすい → 検索意図 → 冗長削除」で、削ってよいのは冗長だけ。削る順序は：言い換え・二重説明 → 水増し表現 → 不要な但し書き → 長文説明のブロック化 → セクションごと削除。長すぎると感じたら字数を削るのではなくセクション単位で必要性を問い直し、**削った後は必ず通し読みする**。
3. **1箇所直したら、影響範囲まで直して初めて「修正」**
   指摘された箇所だけを直して終わらせない。修正のたびに次の3点を確認し、必要な直しをすべて済ませてから提示する。
   - **同じ問題が他にないか**（表現・断定・記法など同種の誤りを記事全体で探す）
   - **他の箇所と矛盾していないか**（前後の説明・表・description・見出し・結びが、直した内容と食い違っていないか）
   - **二重説明になっていないか**（追記した内容を、別のセクションが既に言っていないか）
   入稿済み・入稿予定の記事では、**どの範囲を差し替える必要があるかを`git diff`で確認して伝える**（セクション外に変更が及んだ場合は必ず明示する）。
4. **NG 0件になるまで提示しない**
   `article-self-check.py`の出力を最後まで読む（grep/headで絞らない）。NGは「記事を直す」か「スクリプトを直す」で必ず0にする。誤検知を「無視」で済ませない。検出ロジックを直したら、意図的に違反を作って検知されることを検証する。問題は全部洗い出して一度に直す（1件ずつの往復をしない）。「入稿できます」と言えるのはNG 0件＋読者視点の通し読み後のみ。

## 常時原則

- **事実以外を書かない**：実体験のないことを「試みた」と書かない。作り話厳禁
- **AIと人は対等な目線**：「AIはこういうもの」という断定を避ける（メディアの根幹思想）
- **一般論と自社サービスを分離**：業界の一般論を自社の強みのように書かない
- **ファイルにある情報は必ずファイルから読む**：内部リンクタイトル・CTA文言・料金・数値を記憶で書かない
- **出典**：統計・製品・公式の仕組みには一次情報へのハイパーリンクを貼る。URLは実在確認してから使う（推測禁止）。数値には出典と調査時期（公開日/更新日を区別）を添え、別調査の数値をレンジに混ぜない。プラットフォームの相場ガイドは発注者向けの目安であり実勢と区別する。WebFetchの要約で書かず原文を開き、条件・但し書きまで反映する
- **推測を断定しない**：公式が理由を説明していない事象は「背景として考えられるのは〜」と推測を明示。数字・事実・比較を述べるときは根拠（ファイル・URL・実測コマンド）を併記する

## 1. 着手前

- 優先順位はメディア視点（読者に今何が必要か）で決める。J系（運用代行系）は「問い合わせを増やすか」を検証してから着手
- メインKW・検索意図を確認し、既存記事との重複をgrepで確認する
- タイトル：KWの語彙をそのまま（言い換え禁止）前方に配置。字数はBashで実測（理想30〜33・上限35字）
- スラッグ：英語・ハイフン区切り・KW網羅を優先（3〜5語目安）。H2にも関連語を自然に含める
- no.は全記事の採番状況を実測してから決める（決め打ち禁止・画像ファイルの存在も確認）

## 2. 構成

- H1・H2・H3の骨格のみ。1つのMDドキュメントで提示（コードブロック内にH2直下の構成意図を`→`で記載。①②は構成案のみで執筆時の見出しに入れない）
- 内部リンク設計を構成に含める（優先：J系・外注タイミング・サービスページ）。リンク先は必ずMDを読んで内容確認
- シリーズ記事は前回記事を読んで接続し、「体験→構造の言語化」まで昇華。営業導線を埋め込む
- 修正フィードバック後は「修正済み構成案の再掲 → ユーザー確認 → 執筆」の順
- **アイキャッチ完成フロー**：構成確定 → ユーザーが参考画像添付 → CCがプロンプト1案作成（`knowledge/eyecatch-rules.md`）→ 生成・アップ → CCがリサイズ・リネーム → **完了後に執筆開始**（参考画像なしの記事はプロンプト提示のみで並行可）

## 3. インタビュー

- 体験・実況がメインの記事は構成案の**前**に実施。回答は`operations/interview-notes/[slug].md`に保存
- 用語解説・AI事情などCC先導の記事は不要（Rシリーズは R-04以降不要・概念記事スタイル。ただし抽象論に浮かないこと）
- 迷ったらユーザーに確認

## 4. 執筆前確認

- 最新published記事で文体を目視確認し、CTA文言をそのままコピーして手元に置く
- `operations/wp-block-guide.md`でブロック要素の使いどころを確認
- 内部リンク先の`title:`をgrepで確認。製品名・数値は公式ソースで確認

## 5. 執筆中の判断基準（機械化できないもの）

- **記事の流れ**：①体験・失敗から入る（圧縮して）→②構造の説明→③変えたこと→④現在のフロー→⑤まとめ（押しつけない）
- **リードは1文目で答える**：H1直下のリードは検索意図への直接回答から始める。背景・前置き・体験から入らない（AI検索に拾われるのは冒頭の直接回答）。リードで説明しきろうとせず、詳細は本文に渡す
- **長い文は分けて直す**：一文が上限を超えたら、削るのではなく句点で切る。「〜が効き、」「〜であり、」の連用中止でつないだ節は、そこが分割点になっていることが多い
- **体験談は主役にしない**：導入フックに徹し全体の3割上限。「〇〇×職種」記事の主役は環境
- **平易に書く**：小難しい言い回し・論文調の抽象表現を使わない。読者が自分の状況をそのまま想像できる具体形で、端的に書く（例：「名称と範囲は必ずしも一致せず」→「同じ『運用代行』でも、SEOまで含むものもあれば入稿は対象外のものもある」）。迷ったら「誰が読んでも一度で分かるか」で判断する
- **1文に主題を複数入れない**：連用中止（〜が効き、／〜であり、）で節をつなぐと主語が入れ替わったまま文が続き、読者が追う対象を切り替え続けることになる。対比は文を分けて「AはX。逆に、BはY。」の形にする。あわせて①「効く」「変わる」など効果を表す動詞は**何に効くのか**を書く②「逆になります」等の指示表現は**何が逆なのか**が一意に決まるか確認する（例：「ブログ運営はルールを手元に残せるかが効き、一方で散った数字をまとめる作業は逆になります」→「ブログ運営で効いてくるのは、トンマナや禁止事項を手元のファイルに残せることです。逆に、複数のツールに散った数字を1枚にまとめる作業では、この強みが活きません」）
- **文体**：断定を避ける（「〜気がしています」）／本音を出す（「正直に言うと」）／軽い自虐は1〜2箇所・短文で落とす／ネガティブの後は前を向く一文／「〜しましょう」の指示形は使わず体験の共有として書く
- **H3見出し**：読者の感情・状況を言語化（「あ、それ自分だ」）。H2内の段落が4つ以上になったら1〜2個
- **箇条書き・表・ブロック**：構造の整理には積極的に使い、体験の流れは文章で書く。長文説明より視覚要素を優先
- **読点**：文頭の接続語（ただし・しかし・また・なお・さらに・一方・逆に・つまり・そのため・例えば）と、主題を示す「〜は」（当サービスは、このメディアは 等）のあとには読点を打つ。例：「ただし、記事を書くだけのサービスと〜」「当サービスは、入稿・公開まで月額に含みます」。ただし目的語（〜を）や短い副詞の直後には打たない（読点過多で読みにくくなるため）
- **ブロック記法**：`【ブロック名】<br>`＋内容。`>`もHTMLコメントも使わない。`・`箇条書きは各行末`<br>`、項目内の列挙は`A / B`（`・`を重ねない）。改行は句点基準・1行40字目安
- **AIっぽさ**：「真面目すぎる」と感じたら感情・オチ・「でも正直〜」を差し込む
- **シリーズ別CTA**：副業検証=なし／Rシリーズ=末尾のみ／士業=紹介型（「＼　ブログ運用代行を行っています　／」）を末尾のみ。通常記事=途中＋末尾の2回
- **ハウツー記事**：外部サービスの画面項目名はたたき台扱いにし、公開前にユーザーへ実画面との一致確認を依頼。導入文はユーザーの経緯を聞いてから書く
- 記事MDはメインリポジトリの`articles/`に作成（worktree禁止）。本文はチャットに貼らずパスのみ提示

## 6. リライト（既存記事の改修）

対象選定はGSC実データ（`operations/site-status.md`）に基づく。**11〜20位に滞留し表示回数がある記事**を優先し、受注距離が近いものをさらに優先。

1. GSCで当たっているクエリ・順位・表示を確認 → 狙うKWの本文出現数をgrepで実測
2. 競合上位を実際に検索し、自記事にない要素を洗い出す
3. **自社ページ同士のカニバリ確認**（同じクエリを受けているページがあれば住み分けを決める）
4. 構成案（`articles/no{番号}_rewrite_composition.md`）→ ユーザー確認
5. タイトル変更時は**既存アイキャッチをReadで開いて**文言焼き込みを確認（差し替えはデザイン維持・文言のみ）
6. 書き換え前にコミット → **既存MDを直接書き換え**（新規MD禁止・URL/スラッグ/no.は変えない）→ `updated:`追加
7. `git diff`で差分提示 → WPは全文貼り替え → `operations/rewrite-log.md`に記録（翌月GSCで効果検証）

## 7. 提示前

1. `article-self-check.py`をNG 0件まで（4原則の4）
2. スクリプト末尾に出力される**判断チェック**（👁）を目視で確認
3. 初見の読者のつもりで通し読み（指摘への対応は原則3のとおり影響範囲まで直す）
4. 大きな構造変更をした場合：description・見出し・結び・次回予告に削除内容の残骸がないか全文再読
5. 統計を扱う記事は公開直前に一次情報で最終ファクトチェック（`research/`配下も孫引きの可能性があるため無条件に正としない。誤りはリサーチファイル側も訂正）

## 8. 公開時（「入稿しました」の報告で自動実行・確認不要）

1. MD：`status: published`／`date:`記入
2. `operations/article-md-workflow.md`に追記
3. `operations/article-backlog.md`：`[x]`＋次回確定マーク移動
4. GitHub issue #2 更新
5. `~/Documents/GitHub/tasks/README.md`更新
6. WP同期（WPを正としてMDを合わせる。ズレ指摘時はユーザーに確認）
7. X投稿キューへネタ抽出3本（`rules/x-post-flow.md` 3.5章）
8. GSCインデックス登録リクエストを案内し、`tasks/README.md`常時掲載に確認タスクを追加
