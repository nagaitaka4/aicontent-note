# 記事制作フロー・ルール

記事を書く・編集するすべての作業で参照する。

- **測れるルールは`operations/constraints.py`が唯一の正**：閾値と執筆者に渡す文言をここだけに書く。`article-self-check.py`（提示前の判定）・`article-precheck.py` ⑤（執筆前の告知）・`operations/gpt-writing-prompt.md`（外注時）はすべてこの定義を参照する。**数値基準をこのファイルに書かない**（2026-08-18：6箇所に手書きされていた制約が食い違い、事故が2件起きたため一元化した）
- このファイルに置くのは**手順**と**機械化できない判断基準**だけ
- ルールの由来・失敗の経緯は`operations/lessons.md`（運用には読まなくてよい）

## 4原則（最優先）

1. **執筆前に確定できることを、執筆後に直さない**
   着手前に`python3 operations/article-precheck.py <slug> "KW"`を実行し、出力①〜⑥（適正分量・内部リンク候補・自社情報の照合・外部出典・制約・提示基準）をすべて潰してから書き始める。
2. **数値のために内容を削らない**
   **文字数に上限・目標値は設けない。**適正な分量は記事の検索意図とKWによって決まる。判断の優先は「正確 → 分かりやすい → 検索意図 → 冗長削除」で、削ってよいのは冗長だけ。削る順序は：言い換え・二重説明 → 水増し表現 → 不要な但し書き → 長文説明のブロック化 → セクションごと削除。長すぎると感じたら字数を削るのではなくセクション単位で必要性を問い直し、**削った後は必ず通し読みする**。
3. **1箇所直したら、影響範囲まで直して初めて「修正」**
   指摘された箇所だけを直して終わらせない。修正のたびに次の3点を確認し、必要な直しをすべて済ませてから提示する。
   - **同じ問題が他にないか**（表現・断定・記法など同種の誤りを記事全体で探す）
   - **他の箇所と矛盾していないか**（前後の説明・表・description・見出し・結びが、直した内容と食い違っていないか）
   - **二重説明になっていないか**（追記した内容を、別のセクションが既に言っていないか）
   入稿済み・入稿予定の記事では、**どの範囲を差し替える必要があるかを`git diff`で確認して伝える**（セクション外に変更が及んだ場合は必ず明示する）。
4. **NG 0件になるまで提示しない**
   `article-self-check.py`の出力を最後まで読む（grep/headで絞らない）。NGは「記事を直す」か「スクリプトを直す」で必ず0にする。誤検知を「無視」で済ませない。検出ロジックを直したら、意図的に違反を作って検知されることを検証する。問題は全部洗い出して一度に直す（1件ずつの往復をしない）。「入稿できます」と言えるのはNG 0件＋読者視点の通し読み後のみ。

## 常時原則

- **事実以外を書かない**：実体験のないことを「試みた」と書かない。作り話厳禁
- **AIと人は対等な目線**：「AIはこういうもの」という断定を避ける（メディアの根幹思想）
- **一般論と自社サービスを分離**：業界の一般論を自社の強みのように書かない
- **ファイルにある情報は必ずファイルから読む**：内部リンクタイトル・CTA文言・料金・数値を記憶で書かない
- **出典**：統計・製品・公式の仕組みには一次情報へのハイパーリンクを貼る。URLは実在確認してから使う（推測禁止）。数値には出典と調査時期（公開日/更新日を区別）を添え、別調査の数値をレンジに混ぜない。プラットフォームの相場ガイドは発注者向けの目安であり実勢と区別する。WebFetchの要約で書かず原文を開き、条件・但し書きまで反映する
- **推測を断定しない**：公式が理由を説明していない事象は「背景として考えられるのは〜」と推測を明示。数字・事実・比較を述べるときは根拠（ファイル・URL・実測コマンド）を併記する

## 1. 着手前

- 優先順位はメディア視点（読者に今何が必要か）で決める。J系（運用代行系）は「問い合わせを増やすか」を検証してから着手
- メインKW・検索意図を確認し、既存記事との重複をgrepで確認する
- **`git log` で直近のコミットを確認する**（grepだけでは、別セッションで進行中の記事を検出できない。2026-08-18にno.59とテーマが完全重複しかけた。コミットメッセージには「no.59はChatGPT無料/有料記事」と書かれていたが、記事MDが未作成のためgrepに出なかった）
- タイトル：KWの語彙をそのまま（言い換え禁止）前方に配置。字数はBashで実測（理想30〜33・上限35字）
- スラッグ：英語・ハイフン区切り・KW網羅を優先（3〜5語目安）。H2にも関連語を自然に含める
- no.は全記事の採番状況を実測してから決める（決め打ち禁止・画像ファイルの存在も確認）

## 2. 構成

- H1・H2・H3の骨格のみ。1つのMDドキュメントで提示（コードブロック内にH2直下の構成意図を`→`で記載。①②は構成案のみで執筆時の見出しに入れない）
- **材料がない枠を作らない。**体験セクションはその体験が実在すると確認してから置き、確認の結果が「体験なし」なら枠ごと削る（触っていない事実は但し書き2文で足りる）。表は全行が埋まる列だけ指定する。**「埋まらなければ空欄で可」という指示は効かない**——枠が空いていると推測で埋まる（経緯は`operations/lessons.md`）
- **執筆を外に出す場合、記事に出す表の全セルぶんの材料をプロンプトに書き出す。**片側の製品情報しか渡さずに比較表を指定すると、もう片側は未提示の断定で埋まる
- **構成案の整理軸を、記事の目的として本文に書かない。**構成案には「どこで止まるか」「3種類の差」のような編集側の整理軸が入る。これは**構成を組むための道具**であって、読者が知りたいこと（何がどう違うのか）ではない。**description・H1直下リード・各H2のリード**は検索意図に答える場所なので、読者が検索に使う言葉で書く（経緯は`operations/lessons.md`）
- 内部リンク設計を構成に含める（優先：J系・外注タイミング・サービスページ）。リンク先は必ずMDを読んで内容確認
- シリーズ記事は前回記事を読んで接続し、「体験→構造の言語化」まで昇華。営業導線を埋め込む
- 修正フィードバック後は「修正済み構成案の再掲 → ユーザー確認 → 執筆」の順
- **アイキャッチ完成フロー**：構成確定 → ユーザーが参考画像添付 → CCがプロンプト1案作成（`knowledge/eyecatch-rules.md`）→ 生成・アップ → CCがリサイズ・リネーム → **完了後に執筆開始**（参考画像なしの記事はプロンプト提示のみで並行可）

## 3. インタビュー

- 体験・実況がメインの記事は構成案の**前**に実施。回答は`operations/interview-notes/[slug].md`に保存
- 用語解説・AI事情などCC先導の記事は不要（Rシリーズは R-04以降不要・概念記事スタイル。ただし抽象論に浮かないこと）
- 迷ったらユーザーに確認

## 4. 執筆前確認

- 最新published記事で文体を目視確認し、CTA文言をそのままコピーして手元に置く
- `operations/wp-block-guide.md`でブロック要素の使いどころを確認
- 内部リンク先の`title:`をgrepで確認。製品名・数値は公式ソースで確認

## 5. 執筆中の判断基準（機械化できないもの）

- **記事の流れ**：①体験・失敗から入る（圧縮して）→②構造の説明→③変えたこと→④現在のフロー→⑤まとめ（押しつけない）
- **リードは1文目で答える**：H1直下のリードは検索意図への直接回答から始める。背景・前置き・体験から入らない（AI検索に拾われるのは冒頭の直接回答）。リードで説明しきろうとせず、詳細は本文に渡す
- **長い文は分けて直す**：一文が上限を超えたら、削るのではなく句点で切る。「〜が効き、」「〜であり、」の連用中止でつないだ節は、そこが分割点になっていることが多い
- **体験談は主役にしない**：導入フックに徹し全体の3割上限。「〇〇×職種」記事の主役は環境
- **平易に書く**：小難しい言い回し・論文調の抽象表現を使わない。読者が自分の状況をそのまま想像できる具体形で、端的に書く（例：「名称と範囲は必ずしも一致せず」→「同じ『運用代行』でも、SEOまで含むものもあれば入稿は対象外のものもある」）。迷ったら「誰が読んでも一度で分かるか」で判断する
- **1文に主題を複数入れない**：連用中止（〜が効き、／〜であり、）で節をつなぐと主語が入れ替わったまま文が続き、読者が追う対象を切り替え続けることになる。対比は文を分けて「AはX。逆に、BはY。」の形にする。あわせて①「効く」「変わる」など効果を表す動詞は**何に効くのか**を書く②「逆になります」等の指示表現は**何が逆なのか**が一意に決まるか確認する（例：「ブログ運営はルールを手元に残せるかが効き、一方で散った数字をまとめる作業は逆になります」→「ブログ運営で効いてくるのは、トンマナや禁止事項を手元のファイルに残せることです。逆に、複数のツールに散った数字を1枚にまとめる作業では、この強みが活きません」）
- **文体**：断定を避ける（「〜気がしています」）／本音を出す（「正直に言うと」）／軽い自虐は1〜2箇所・短文で落とす／ネガティブの後は前を向く一文／「〜しましょう」の指示形は使わず体験の共有として書く
- **H3見出し**：読者の感情・状況を言語化（「あ、それ自分だ」）
- **箇条書き・表・ブロック**：構造の整理には積極的に使い、体験の流れは文章で書く。長文説明より視覚要素を優先
- **要所だけ端的に書く。同じ趣旨の文を重ねない**（2026-08-25追加）。**機械チェックの数値をすべて満たしていても間延びする。**一文が短く段落も規定内でも、前の文の言い換えが続けば読者は同じ話を何度も読まされる。書いた後に段落単位で読み返し、**次の文が前の文の言い換えになっていたら削る**。特に起きやすいのは①結論の直後に置く補足②譲歩の後の再説明③中身のないつなぎ文（「ここが出発点です」「この形にすると〜」）④地の文とブロック要素の重複。削る判断は字数ではなく「この文がないと伝わらないか」で行う
- **同じ形の文を地の文で並べない**（2026-08-26追加）。「Aは〜でした。Bは〜です。Cは〜でした。」のように、構文が同じで対象だけ入れ替わる文が3つ以上続いたら、**箇条書きか表に移す**。**一文60字・段落160字をすべて満たしていても読みにくくなる**（no.62初稿でR-01〜R-03の位置づけを地の文で3つ並べ、115字・全文60字以内のまま「長い」と指摘された）。`article-self-check.py`が4文以上の段落を[要確認]で出す
- **強調は3段階で付ける**（2026-08-26追加・`md-to-wp.py`が変換する）
  - **リンク**：`[text](url)` と書くだけでよい。**変換時に自動で太字になる**ので`**`を付けない
    （実測：入稿済み20本のアンカー61件中53件＝87%が太字だった）
  - **重要**：`**text**` → 太字
  - **最重要**：`==text==` → 太字＋黄色マーカー。**数で決めない。そこが読者に持ち帰ってほしい一節かどうかで決める**
    - **判定**：各H2で「ここだけ覚えて帰ってほしい」と言える一節か。言えないなら付けない
    - 同じH2に2つ付けるのは、**役割が違うとき**（片方が「発見」、もう片方が「誤読の防止」など）。
      同じ役割で2つ並べると、どちらも弱くなる
    - 実測：公開20本で1〜13件・中央値4件。97件すべて`swl-marker mark_yellow`の1種類。
      **中央値は参考値であって上限ではない**
    - ⚠️ **「多いから減らす」という減らし方をしない**（2026-09-01・ユーザー指摘）。
      no.64でCCが「7箇所は目安の3〜5を超えている」と数だけで報告したが、
      **中身で見ると7箇所のうち6箇所は残すべきもので、外すべき1箇所は数とは無関係の理由**
      （同じH2にすでに強い一節があり、抽象度が高いほうが弱かった）だった
  - マーカーは**文全体ではなく結論の核になる節に付ける**。文末の「です。」まで含めない
    （例：`==AI活用の成果を大きく左右するのは、渡す情報がどれだけ整理されているか==です。`）
  - 置き場所の目安：リード1文目の核／記事全体の結論／各H2で特に持ち帰ってほしい一節
- **表・ブロックに書いたことを、地の文で言い直さない**：表の各行を直後の段落が順番に説明し直す形が最も起きやすい。表の後に置くのは「そこから何が言えるか」だけで、表を読めば分かることは書かない。同じ趣旨の但し書き（「検証ではない」「因果は言えない」等）を3文並べるのも同じ冗長
- **読点**：接続語と定型の主題は`constraints.py`が判定する。**機械の検出対象外の主題（一般の長い「〜は」）は目視で見る**。読点過多も読みにくいので、目的語（〜を）や短い副詞の直後には打たない
- **ブロック内の改行**：句点基準・1行40字目安（記法そのものは`constraints.py`が正）
- **人が声に出して言わない言い回しを書かない。**AIっぽさの正体は語彙ではなく**動作を抽象名詞に畳む構文**にある。「待っても届かない差もある」「差に当たるかどうか」「取れる手が変わる」「課金の要否」「〜という状態です」「〜する形です」は、意味は通るが人の言葉ではない。**主語を人か物に戻し、動詞で書く**（「待っても届かない差もある」→「お金を払わないと使えないものもある」）。判定は**声に出して読んで、言いにくければ直す**（検出できる分は`article-self-check.py`の`NG_AI_PHRASES`にあるが、構文の問題なので機械では拾いきれない）
- **AIっぽさ**：「真面目すぎる」と感じたら感情・オチ・「でも正直〜」を差し込む
- **シリーズ別CTA**：副業検証=なし／Rシリーズ=末尾のみ／士業=紹介型（「＼　ブログ運用代行を行っています　／」）を末尾のみ。通常記事=途中＋末尾の2回。**ただし検証・整理系（一本の論証でつながる記事）は途中CTAを省略して末尾1回にしてよい**（2026-08-20・no.60で確定。論証の途中に営業が入ると流れが切れ、中立に切り分ける記事の説得力も薄まるため。途中CTAが効くのは体験談・Before/After型のように自然な区切りがある記事）
- **ハウツー記事**：外部サービスの画面項目名はたたき台扱いにし、公開前にユーザーへ実画面との一致確認を依頼。導入文はユーザーの経緯を聞いてから書く
- 記事MDはメインリポジトリの`articles/`に作成（worktree禁止）。本文はチャットに貼らずパスのみ提示

## 6. リライト（既存記事の改修）

対象選定はGSC実データ（`operations/site-status.md`）に基づく。**11〜20位に滞留し表示回数がある記事**を優先し、受注距離が近いものをさらに優先。

1. GSCで当たっているクエリ・順位・表示を確認 → 狙うKWの本文出現数をgrepで実測
2. 競合上位を実際に検索し、自記事にない要素を洗い出す
3. **自社ページ同士のカニバリ確認**（同じクエリを受けているページがあれば住み分けを決める）
4. 構成案（`articles/no{番号}_rewrite_composition.md`）→ ユーザー確認
5. タイトル変更時は**既存アイキャッチをReadで開いて**文言焼き込みを確認（差し替えはデザイン維持・文言のみ）
6. 書き換え前にコミット → **既存MDを直接書き換え**（新規MD禁止・URL/スラッグ/no.は変えない）→ `updated:`追加
7. `git diff`で差分提示 → WPは全文貼り替え → `operations/rewrite-log.md`に記録（翌月GSCで効果検証）

## 7. 提示前

1. `article-self-check.py`をNG 0件まで（4原則の4）
2. スクリプト末尾に出力される**判断チェック**（👁）を目視で確認
3. **H1直下のリードを、声に出して読む**（2026-08-31新設・省略禁止）。言いにくければ直す。**特に1文目**。
   - **なぜリードだけを分けたか**：no.64で「AIに任せられる範囲は、4ヶ月で動きました」という**動作を抽象名詞に畳んだ1文目**が、構成案の第1稿からWP入稿まで**7工程を素通り**した。5章の恒久ルール（人が声に出して言わない言い回しを書かない）は存在していたが、**判定方法が「声に出して読む」なのに、いつ読むかが決まっていなかった。**
   - **構成案に書いたリードは、そのまま本文になる。**構成案のレビューは事実と範囲を見るので、文言はここで初めて検査される
   - `article-self-check.py`の`NG_AI_PHRASES`は固定文字列9個だけで、**5章が挙げている6例のうち5例を検知できない**。構文の問題なので機械では塞げない
4. 初見の読者のつもりで通し読み（指摘への対応は原則3のとおり影響範囲まで直す）
5. 大きな構造変更をした場合：description・見出し・結び・次回予告に削除内容の残骸がないか全文再読
6. 統計を扱う記事は公開直前に一次情報で最終ファクトチェック（`research/`配下も孫引きの可能性があるため無条件に正としない。誤りはリサーチファイル側も訂正）
7. **構成案の言い回しが本文に流れ込んでいないか**、構成案とdescription・リード・各H2のリードを読み比べる（編集側の整理軸は読者の言葉に置き換える）

## 7.5 WP入稿用ファイルの作成（2026-08-26新設・確認不要で毎回実行）

**ユーザーが記事を確認し、入稿に進むと決まった時点で、指示を待たずに実行する。**

⚠️ **NG 0件になった直後には作らない**（2026-08-28変更）。**記事確認の前に作ると、
ユーザーから修正が出た時点で必ず捨てる出力になる。**それだけなら数秒の無駄で済むが、
問題は**「古い出力を渡す」事故の元がそこに置かれること**にある。**ファイルが存在しなければ、
その事故は起きない。**生成は数秒なので、確認が終わってから作れば足りる。

```
python3 operations/md-to-wp.py articles/<slug>.md
```

出力（`operations/wp-output/<slug>.wp.txt`）をユーザーに渡し、**全文コピー**してWPの
「コードエディター」に貼る旨を伝える。先頭には入稿情報（タイトル・スラッグ・説明文・カテゴリー・
タグ・アイキャッチ）が段落ブロックとして入っており、各欄に写したらブロックごと削除する。

- **手でブロックを組まない。**【ポイント】等のスタイル・区切り線・CTAボタン・関連記事カードは全部スクリプトが入れる
- ブロック名とSWELLクラスの対応・変換しないもの（マーカー等の装飾）は`operations/wp-block-guide.md`
- 記事を直したら**必ず作り直す**（古い出力を渡さない）

**経緯**：2026-08-26まで61本すべてWP上で手作業だった。「MDで書いてWP入稿時に差し替える」という
手順がルールに書かれていたため、CCもユーザーもその手順を実行するだけで、
**手作業が続いていること自体を直す対象として見ていなかった**（詳細は`operations/lessons.md`）。

## 7.6 WP入稿はCCが実行する（2026-08-28新設・V-05で確定）

**入稿用ファイルができたら、CCがChromeを操作して下書き保存まで済ませる。**ユーザーの作業は
**ログインと公開ボタンの2つだけ**。手でコピペしない。

⚠️ **「公開しない」と「保存しない」を混同しない。**押さないのは公開ボタンだけで、**下書き保存はCCが必ず行う**。
ユーザーが開いたときに、最終チェックと微調整だけで公開できる状態にしておく（2026-08-28ユーザー指示）。

### 下書きを作ったあとに記事を直したら（2026-09-01新設・省略禁止）

**MDを直したら、そこで止めない。**次の3つを**必ず1セットで**実行する。

1. `python3 operations/md-to-wp.py articles/<slug>.md` で入稿用ファイルを作り直す
2. **本文を全文差し替えてWPの下書きに反映する**
3. 反映後、**直した箇所が入り、直す前の記述が消えていることを検証する**

⚠️ **部分置換をしない。**「この見出しだけ」「この1文だけ」とWP側をパッチしていると、
**大きく直したときに送り忘れる。**全文差し替えなら、MDとWPがずれる余地がなくなる。

⚠️⚠️⚠️⚠️ **公開済みの古い記事に全文差し替えを使わない**（2026-09-02追加）。
**`md-to-wp.py`が作るブロックと、WP上の実際のブロックが違うことがある。**
差し替えると**元のブロックが別物に置き換わり、見た目と機能が壊れる**。

**実例**：no.56（`chatgpt-work-claude-code-comparison`）のFAQは、WP上では
**SWELLのFAQブロック（`wp:loos/faq` ＋ `wp:loos/faq-item`・アコーディオン）**で作られていた。
`md-to-wp.py`は【はてな】を段落スタイルに変換するため、**全文差し替えするとアコーディオンが消える**。
気づいたのは、差し替え直前に`class="...is-style-..."`を数えてWP側と突き合わせたとき。

- **古い記事に追記するときは、WP側の既存ブロックと同じ形で1件だけ挿入する**
- 挿入後は「**他のブロックが無傷か**」を数えて確認する（`is-style-`の出現数が変わっていないか）
- **全文差し替えが安全なのは、`md-to-wp.py`で入稿した記事だけ**（no.63以降）

⚠️⚠️⚠️ **RESTで本文を更新したら、開いているエディターを必ずリロードする**（2026-09-01追加）。
**RESTの更新は、開きっぱなしのGutenbergエディターには反映されない。**
その状態でユーザーが公開ボタンや保存を押すと、**エディターが持っている古い本文で上書きされ、CCの修正が消える。**

- CCが本文をPOSTしたら、**そのまま`location.reload()`でエディターを読み直し、反映されているか数える**
- 数えるのはマーカー（`.swl-marker`）・H2・表など。**POSTのレスポンスだけで確認を終わらせない**
- ユーザーに「公開してください」と渡す前に、**エディター側の状態が最新であることを確認してから渡す**

**経緯**：2026-09-01 12:37にCCがRESTでマーカーを6個に減らしたが、エディターは7個のまま開いていた。
翌9/2 08:42にユーザーが公開ボタンを押した時点で**7個の状態が保存され、そのまま公開された**。
リビジョン履歴に`12:37 → 6個` `09/02 08:42 → 7個`と残っており、原因が確定できた。
**POSTのレスポンスでは6個と返っていたので、CCは成功したと報告していた。**

⚠️⚠️ **ただし、全文差し替えの前に「WP側にCCが送っていない変更がないか」を必ず確認する**（2026-09-01追加）。
**ユーザーがWPで直接直していることがある。**そのまま全文差し替えすると、**その修正を消す**。
確認は`GET /wp-json/wp/v2/posts/<id>?context=edit`で本文を取り、
**MDから生成した入稿用ファイルと突き合わせる**（マーカー`swl-marker`の数・H2・表の数を数えるだけでも検出できる）。
**差分があったらWPが正**（`rules/article-flow.md` 8章6番）。**先にMDをWPに合わせてから**、全文差し替えに進む。

**経緯**：2026-09-01、no.64でユーザーがWP上でマーカーを3箇所足していた。
CCはMDのマーカー4個のまま全文差し替えを繰り返しており、**タイミング次第で3箇所を消していた**。
実際に消さずに済んだのは偶然（追加が差し替えのあとだった）。

⚠️ **frontmatterを直したときも忘れない。**タイトル・description・アイキャッチのaltは本文とは別に送る必要がある
（`POST /wp/v2/posts/<id>` のtitle、SSPのmetabox、`POST /wp/v2/media/<id>` のalt_text）。

**経緯**：2026-09-01、no.64で**WPの下書きがH2の書き直し前のまま止まっていた**。
見出しと重複の修正はWP側を部分置換で直していたのに、
**H2をまるごと書き直したときだけMDで止まり、送っていなかった。**
事実と違う表（「仕組み／人」の二択）が下書きに残ったままユーザーの確認に回っていた。
**部分置換に慣れたことが、送り忘れの原因。**

### 使うブラウザを間違えない（ここで1回止まった）

| | ログイン状態 | 使うか |
|---|---|---|
| **アプリ内ブラウザ**（Claude Codeの画面内・`mcp__Claude_Browser__*`） | 持っていない | ❌ 使わない |
| **Chrome**（拡張機能ごしに操作・`mcp__claude-in-chrome__*`） | いつものChromeなのでログイン済み | ✅ **こちらを使う** |

**2つはセッションが別。**Chromeでログインしていてもアプリ内ブラウザには引き継がれない。
**パスワード入力はCCができない**ので、Chrome側で操作するのが唯一の道。

### 手順

1. `wp-admin`を開き、ログイン済みか確認する（`#wpadminbar`の有無）
2. **同スラッグの記事がすでにないか確認する**（`/wp-json/wp/v2/posts?slug=...&status=any`）。二重作成の防止
3. タグを解決する（`/wp-json/wp/v2/tags?search=`）。無ければ`POST /wp/v2/tags`で作る
4. 本文をbase64にして2回に分けて`window`変数へ積み、ページ側で復元する（1回のJS呼び出しに入りきらない）
5. `POST /wp-json/wp/v2/posts`で**`status:'draft'`**として作る（タイトル・スラッグ・本文・カテゴリー・タグ）
6. アイキャッチを`media-new.php`のfile inputへ流し込む → `POST /wp/v2/media/<id>`でalt → `POST /wp/v2/posts/<id> {featured_media}`
7. **SEO SIMPLE PACKの説明文はRESTでは入らない。**エディターを開き、
   `textarea[name="ssp_meta_description"]`に値を入れて`input`/`change`を発火 →
   `wp.data.dispatch('core/editor').savePost()`
8. 入った内容を実測で確認して報告する（H2数・表数・区切り線・CTA・関連記事・マーカー・SSPの字数）
9. **記事を直したあとに送り直した場合は、直す前の記述が消えていることを検証する**（上の「下書きを作ったあとに記事を直したら」を参照）
10. **下書き保存まで実行して終わる。**未保存の変更を残さない。
   `wp.data.select('core/editor').isEditedPostDirty()`が**`false`になっていることを確認**してから報告する
11. **ディスカッションを「受け付けません」にする**（2026-09-02決定・**省略禁止**）
   `POST /wp-json/wp/v2/posts/<id> {comment_status:'closed', ping_status:'closed'}`
   ⚠️ **コメントとピンバックの両方を閉じる。**エディターの「ディスカッション」パネルのチェックを外すのと同じ。
   ⚠️ **確認まで含めて1セット。**レスポンスの`comment_status`と`ping_status`が両方`closed`であることを見る。
   **経緯**：2026-09-02にユーザーが指示し、CCが「ルールに追記します」と答えたが**どのファイルにも書かなかった**。
   その結果、2026-09-03のno.65で同じ指摘を繰り返した。**手順に書いていないものは実行されない。**
12. **公開ボタンは押さない。**公開判断は人に残す（2026-08-27決定・成否に関わらず自動化しない）

⚠️ **`media-new.php`ではREST nonceが取れない**（`wpApiSettings`が別物で403）。`upload.php`かエディターで取る。
⚠️ **REST APIの`meta`に無い項目は、POSTしても201が返って黙って無視される。**返り値の`meta`を必ず見る。

**経緯**：2026-08-28にno.63で検証（V-05）。全11項目のうち10項目をCCが実行できた。詳細は`operations/automation-log.md`。

### 本文中に画像を入れる（2026-09-03新設・no.65が初）

**公開62本まで、本文中に画像は1枚も入っていなかった。**no.65（AI Overviewの確認方法）で初めて2枚入れた。

**入れる基準：読者が「どこを押すか」で詰まる箇所だけ。**
データ（表・数値）は文字のままにする。画像を足すと表と競合して、どちらも読まれなくなる。

**手順**

1. スクリーンショットを撮る（**CCは撮れない**。拡張機能の`save_to_disk`はファイルを生成せず、
   `screencapture`は画面収録の権限がないため`could not create image from display`になる）
   → **ユーザーに撮ってもらい、`~/Desktop`か`images/`に置いてもらう**
2. **CCがトリミングする。**`ls -lt ~/Desktop`で最新を拾い、PILで切る
   - ⚠️ **記事に出していない数値を写り込ませない**（no.65では検索パフォーマンス上部の
     クリック数・表示回数タイルを避けた。2,580は記事から意図的に外した数字だった）
   - 幅1200pxに揃え、`Image.LANCZOS`・ICCプロファイル除去
3. ファイル名は `img_XXXX_NN.png`（`XXXX`は記事no.・`NN`は連番）
4. `media-new.php?browser-uploader`でアップ →
   `document.querySelector('#async-upload').form.querySelector('#html-upload').click()`で送信
5. `POST /wp/v2/media/<id> {alt_text}` でaltを入れる
6. **MDに `![alt](画像URL)` を単独行で書く。**`md-to-wp.py`が`wp:image`ブロックに変換する
   （メディアIDは公開APIで自動取得。**先にWPへアップしていないとIDが引けない**）
7. 反映後、画像ブロック数と`wp-image-<id>`を実測で確認する

⚠️ **`【】`ブロックの太字は自動化しない。**ユーザーが記事ごとに選んでいる
（実測：no.62は4個中3個・no.64は6個中3個・no.63は8個中0個）。
WP側で太字にされていたら、MDに`**`で記録して次の差し替えで消さないようにする。
