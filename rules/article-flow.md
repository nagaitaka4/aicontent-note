# 記事制作フロー・ルール

CLAUDE.mdの記事制作フローと、これまでCCのメモリにのみ存在していた関連ルールを統合したもの。記事を書く・編集するすべての作業でこのファイルを参照する。

## 0. 執筆全体を通じて守ること（省略禁止）

フローのどの段階でも共通して適用される原則。

- **事実以外を書かない**：実体験のないことを「試みた」「やった」と書かない。作り話は厳禁。気づき・反省は言われる前に保存する
- **同じ言い回し・結論の繰り返し禁止**：セクション内・記事間で同じ言い回しや結論パターンを繰り返さない。執筆前・執筆中・執筆後の各段階で確認する
- **AIと人は対等な目線**：「AIはこういうもの」という断定を避け、共同作業の視点で書く。メディアの根幹思想。記事・X投稿ともに適用
- **一般論と自社サービスの分離**：業界の一般論と、このサービスだから言える特徴を混同しない
- **ファイルに存在する情報は必ずファイルから読む**（CLAUDE.md絶対ルール）：内部リンクタイトル・CTA文言・製品名・数値は記憶で書かない
- **統計データは出典・調査時期を本文中に明記し、異なる調査の数値をレンジとして混ぜない**（2026-07-28〜）：`research/seo-insights.md`には同じテーマでも調査主体・時期が異なる複数の数値（例：CTR低下34.5%/58%/61%はそれぞれ別調査）が並存する。「◯〜◯%」と幅で示さず、各数値に出典・時期を添える。GEO観点でも出典付きの文章はAI引用率を高めるというデータ（omnibound.ai, 2026-07-20）がある
- **外部の統計・調査に言及する場合、出典名をテキストで書くだけでなく、可能な限り一次情報へのハイパーリンクを貼る（2026-08-03〜）**：M-02（geo-ai-citation-difference.md）で「引用元の明示（サイテーション獲得）」がGEO効果の高い施策だと書きながら、記事自体にも過去58記事にも外部一次情報への実リンクが1件もないという矛盾が発覚した。以後、Ahrefs・Google公式・学術論文・調査会社レポート等を引用する際は、該当ページのURLが確認できる限りMarkdownリンクとして貼る。URLが確認できない・一次情報にたどり着けない数値は、そもそも本文に使わない（出典名の文字表記だけで済ませない）
- **統計に限らず、製品名・機能・公式の仕組みに言及する場合も、可能な範囲で公式の一次情報にアウトバウンドリンクを貼る（2026-08-04〜）**：上記ルールは「統計・調査」に限定されていたが、GEO/AI Overviewでの引用可能性を高める施策としては、製品名・機能説明（例：Claude CodeのCLAUDE.md自動読み込みの仕組み）にも同様に公式ドキュメント等の一次情報リンクを添えるべきという指摘を受け一般化した。過去の記事の多くは外部リンクが0件だった実態がある。**URLは記憶で書かない**：WebSearch等で実在するURLであることを確認してから使う（存在しないURLを記載しない。CLAUDE.md冒頭の「URLを推測しない」絶対ルールが記事執筆にも適用される）
- **Google公式が理由を説明していない事象を、こちらの推測で断定しない**：新機能・仕様変更の「なぜ」を書く際、公式発表に理由の記載がない場合は「背景として考えられるのは〜」と推測であることを明示する。事実（何が追加されたか）と推測（なぜ追加されたか）を区別する

## 1. 着手前判断

- 記事制作の優先順位は**メディア視点**で決める。素材の有無・作業効率ではなく「読者に今何が必要か」「メディアとして何が欠けているか」で順番を決める
- **J系（コンテンツ運用代行系）記事**は着手前に必ず「この記事は問い合わせを増やすか」を検証する。article-backlog.mdのタイトルを鵜呑みにしない
- **キーワード確認**（構成作成より先・省略禁止）
  - メインKWを確認し、article-backlog.mdのキーワード軸と一致しているか確認する
  - 検索意図（情報収集・比較・購入検討）を確認し、記事の設計と合わせる
  - 既存の公開記事と内容・KWが重複していないかを`grep`で確認する
- **タイトル・見出しのSEO最適化**（構成案の提示より先・省略禁止。2026-07-28〜）
  - タイトルはメインKWの構成語彙（article-backlog.mdのキーワード軸の各単語）をそのまま含める。自分の言い換え・造語（例：「AI Overview」を「AI表示」と言い換える等）で実際の検索クエリの語彙からズレさせない
  - タイトルの主要KWはできるだけ前方に配置する
  - 文字数は理想30〜33字・上限35字。**目視カウントは禁止**。Bash/pythonで実測してから提示する（例：`python3 -c "print(len('タイトル文字列'))"`）
  - スラッグはメインKWの構成語彙をできる限り含める（3〜5語目安だが、語数を削るためにKWを削らない。KW網羅を優先する）
  - H2見出しにも可能な範囲でメインKW・関連語を自然に含める（曖昧な指示語だけの見出しにしない。例：「AI表示オプトアウトとは」ではなく「AI Overviewオプトアウト機能とは」）

## 2. 構成作成

- **新規記事のno.を決める前に、必ず実際の採番状況を確認する**（2026-07-28〜。決め打ち厳禁）：`for f in articles/*.md; do grep "^no:" "$f"; done | sort -n` 等で全記事のno.を確認し、次に使う番号が本当に空いているか（draft・published問わず重複していないか）を確認してから構成案・frontmatterに書く。「前の記事の次だろう」という推測でno.を決めて画像やfrontmatterを作らない
- H1・H2・H3の骨格のみを作成する
- **内部リンクの設計を構成に含める**（どのセクションからどの記事へリンクするかを明記）。優先リンク先：コンテンツ運用代行系（J系）記事・外注タイミング記事・サービスページ
- **シリーズ記事の場合**：前回記事を読んで接続し、「体験→構造の言語化」まで昇華させる。営業導線を埋め込む
- 構成案は1つのMDドキュメントで提示する（箇条書き+説明文の混在にしない）。コードブロック内に`#`記号を使いH2直下に構成意図を`→`で記載。番号（①②等）は構成案のみに使い、執筆時のH2見出しには入れない
- ユーザーからの修正フィードバック受領後は、修正済み構成案を再掲 → ユーザー確認 → 執筆開始、の順を守る
- **構成確定後〜執筆開始までのアイキャッチ完成フロー（2026-08-04〜・省略禁止）**：①構成確定 →②ユーザーが参考アイキャッチ画像を添付 →③CCがその参考画像を元に生成プロンプトを1パターン作成（`knowledge/eyecatch-rules.md`参照）→④ユーザーがGPT等で生成し`images/`にアップロード →⑤ユーザーから「画像をアップした」旨の連絡を受ける →⑥CCがリサイズ・リネーム（`eyecatch_XXXX.png`）→⑦執筆開始。**執筆は⑥の完了を待ってから開始する**（構成確定と同時に執筆へ進まない）。参考画像の添付がない記事（既存シリーズテンプレート踏襲等）ではこの限りではなく、構成確定と同時にプロンプト提示のみ行う

## 2.5 リライト（既存記事の改修）のフロー（2026-08-05新設）

新規記事とは別のフローで進める。対象の選定はGSC実データに基づく（`operations/site-status.md`の最新スナップショット）。

### 対象の選び方

**11〜20位に滞留していて、表示回数がある記事**を優先する。10位→5位の順位上昇はクリック率が数倍になる領域であり、新規記事を1本増やすよりクリック増加の効率が高い。受注距離が近い記事（代行・料金・外注系）をさらに優先する。

### 進め方（省略禁止）

1. **既存記事とGSCデータの突き合わせ**：対象記事に当たっているクエリ・順位・表示回数を確認する
2. **grepで原因を特定**：狙うクエリの語彙が本文に何件あるかを実測する（表記ゆれ・語彙の欠落は`grep -o "語" file | wc -l`で数える。目視で判断しない）
3. **競合確認**：狙うクエリで実際に検索し、上位記事が持っていて自記事にない要素を洗い出す
4. **自社ページ同士のカニバリ確認**：狙うクエリを他の自社ページ（記事・固定ページ）が既に受けていないかGSCのページ別データで確認する。受けている場合は住み分けを決め、H2で狙いにいかない
5. **構成案を作成**：`articles/no{番号}_rewrite_composition.md`として作成し、ユーザー確認を取る
6. **アイキャッチの確認（省略禁止）**：タイトルを変更する場合、**必ず既存アイキャッチをReadで開いて中身を見る**。画像内にタイトル文言が焼き込まれている場合は差し替えが必要。デザインは維持し文言のみ差し替える（ファイル名・no.は変えない）
7. **書き換え前にコミット**：変更前の状態をgitで確定させる
8. **既存MDを直接書き換える**（新規MDを作らない）：`articles/[slug].md`が常にWPの正であるべきで、同じ記事のMDが2つ存在する状態を作らない。変更前の全文はgit履歴に残るため失われない
9. **frontmatterに`updated: YYYY-MM-DD`を追加**（WPの更新日と揃える）
10. **`git diff`で差分を提示**：ユーザーは全文を読み直さず、変わった箇所だけを確認できる状態にする
11. **WPへ入稿**：改修量が大きい場合は全文貼り替え（部分修正はブロック構造が崩れやすい）
12. **リライト記録を`operations/rewrite-log.md`に追記**（下記）

### リライト記録（効果検証のために必須）

翌月のGSCで効果を検証するため、「何を・なぜ変えたか」を`operations/rewrite-log.md`に残す。記録がないと検証が成立しない。リライトを重ねるほど「何が効くか」のパターンが蓄積され、それ自体がメディアの資産（＝記事ネタ）になる。

### リライトで変えないもの

- **URL・スラッグ**：積み上げた評価を引き継ぐため。検索意図が根本的に違うクエリを狙う場合のみ新規記事を作る
- **no.**：記事番号は維持する（アイキャッチのファイル名も同じ番号のまま上書き）

## 3. インタビュー必要性の判断（省略禁止）

- ユーザーの体験・本音・実況がメインの記事（副業検証シリーズなど）→ インタビュー必要。構成案作成**前**に実施する
- 用語解説・AI事情などCC先導の記事 → インタビュー不要
- 判断に迷う場合はユーザーに確認する
- インタビュー回答は必ず`operations/interview-notes/[slug].md`に保存する（次セッションでも参照できる状態にする）
- インタビューが必要な記事の制作順序：インタビュー実施 → インタビュー素材をファイル保存 → 構成案作成 → ユーザー確認 → 執筆
- 構成OK後、**執筆前にCCがインタビューを行う**（省略禁止・インタビュー不要記事を除く）。ユーザーが答えた内容を素材として執筆に使う。インタビューなしに執筆開始しない
- **例外**：Rシリーズ（ai-ops-basics）はR-04以降インタビュー不要。概念記事スタイルで統一（R-04のトンマナが基準）。ただし実態から浮いた抽象論にならないよう注意する

## 4. 執筆開始前確認（省略禁止）

インタビュー完了後、執筆開始前に必ず以下を確認してから書き始める。

- [ ] 最新のpublished記事をReadし、**文体（丁寧体・常体の比率）を目で確認する**
- [ ] 同じ記事から**CTAの文言・形式をそのままコピーして**手元に置く
- [ ] `operations/wp-block-guide.md`を読み、ブロック要素の種類と使いどころを確認する
- [ ] 内部リンク候補記事の`title:`を`grep`で確認し、正式タイトルを手元にメモする
- [ ] 記事内に登場する製品名・プラン名・固有名詞・数値データは公式ソースで確認する

> 過去はこのチェックリストが誤ってX投稿ルールの見出し配下に置かれていた。記事執筆用として本ファイルに統合。

## 5. 執筆中に守ること

- 表記：Markdownの`-`は禁止、`・`（中点）を使う
  - `・`はMarkdown標準の箇条書き記号ではないため、項目間に空行がないと1行に連結されて表示される。**空行ではなく、各項目の末尾に`<br>`を付けて改行する**（2026-07-23〜。ブロック要素内かどうかに関わらず、本文中の`・`箇条書きすべてに適用。空行を入れるとWP上で段落間の余白が大きく空いてしまい、`<br>`ならその余白を作らずコピペ編集もしやすい。詳細・具体例は`operations/wp-block-guide.md`参照）
  - 1つの項目の中でさらに複数要素を並べたい場合は`・`を重ねず`A / B`を使う（`・`のネストは、項目の区切りと項目内の列挙の区別がつかなくなるため禁止）。これは箇条書きの項目ラベル部分に限らず、項目内のどこに`・`を書く場合も同様
- 表（テーブル）は比較・多列情報のみに使用。単純な列挙は箇条書きにする。1記事3個まで目安
- H2の最後に「まとめ」を使わない
- タイトル・見出しに「導入」「結論」「まとめ」などの言葉を入れない
- 一人称：主語は「私」、修飾・再帰的用法（「自分の体験」）は「自分」
- 「記事に書きます」ではなく「ノートに残します」
- URL（スラッグ）：英語・ハイフン区切り、メインKWを含める、3〜5語が目安
- 画像alt属性：キーワードを自然に含める（詰め込みNG）。ファイル名も英語・意味のある名前にする
- 内部リンクのアンカーテキストはキーワードを含む自然な文章にする
- 副業検証シリーズ（side-business）：CTAを入れない
- Rシリーズ（ai-ops-basics）：末尾CTAのみ。途中CTAは入れない
- **士業シリーズ（親記事→子記事）**：子記事の対象業種・順序は今の時点で固定しない。着手時に`operations/article-backlog.md`の想定シリーズ欄と、週次リサーチ（`research/market.md`）での実例の蓄積状況を確認し、根拠が揃っている業種から書く
- **士業シリーズのCTAは紹介型を使う（2026-07-22〜）**：通常の悩み訴求型CTA（「ブログ更新が止まっている方へ」）は読者（士業）の実情に合わないため使わない。「＼　ブログ運用代行を行っています　／」という紹介型フォーマットを使う。「Claude Codeを使った」等のツール名は前置きしない（サービスは「ブログ運用代行」であり「Claude Code活用コンサル」ではないため。詳細は`feedback-cta-placement`メモリ参照）
- **士業シリーズは末尾CTAのみ・途中CTAは入れない（2026-07-30〜）**：士業シリーズの記事本文は2,500〜3,000字程度と比較的短く、途中CTAの位置（体験→環境の効果の直後）はまだ読者が「具体的に何ができるか」「安全性」という実務情報を得ていない段階にあたる。専門職読者は情報収集に慎重な層が多く、早い段階での営業提示は警戒心を強めやすいと判断し、弁護士編・社労士編とも公開後に途中CTAを削除して統一した

## 6. 文体・表現の詳細ルール

実際の文章craft（言い回し・改行・構成）はここを見る。

### 改行・スペース
- 句点（。）を基準に改行し、1行40文字を目安にする。超える場合は読点の位置で調整する（読点で細かく切りすぎない）
- 「、」「。」の後に不要な半角スペースを入れない
- MDの改行はWPでスペースとして表示されるため、段落の区切りには空行を入れる（40文字改行によるスペースはWP公開後は自動で詰まるため削除作業は不要）

### 断定を避ける表現
「〜のような気がしています」「〜に近いと思います」「〜がほとんどです」「〜のだと思います」「〜かもしれません」

### 本音を出す表現
「正直に言うと〜」「やっぱり〜」「今思えば〜」「無理やり自分に言い聞かせていましたが」

### 軽い自虐・自己ツッコミ
- 記事全体で1〜2か所を目安に、過度にならない範囲で入れる（なければ無理に入れない）
- 短文でサラっと落とす。「・・・」を余韻として使うと自然になる
- 例：「思ったより全然うまくいかなかった。」「あの時間はいったい何だったのか・・・。」

### ワクワク感・前向きなトーン
ネガティブな体験・課題を書いた後は、必ず前を向く一文を入れる（導入の締め・課題セクションの後・まとめの締めが入れどころ）。「ワクワク」「楽しい」を無理やり文中に入れる／根拠のないポジティブ／課題の後に前向きな要素がないまま終わる、はNG。

### 読者への語りかけ方
「〜しましょう」の指示形は使わない。「〜と感じている方は」など柔らかく寄り添う形にし、命令ではなく体験の共有として書く。

### H3見出しの作り方
読者の感情・状況を言語化する。「あ、それ自分だ」と思えるものにする（断定より「気づき」のトーン）。H2内の段落が4つ以上になる場合にH3を1〜2個追加する目安。

### 箇条書きの使い方
体験・感情の流れを語る文章では多用しない（本文の流れで書けるなら文章にする）。一方、要素の列挙・手順・チェック項目など「構造を整理する」場面では積極的に使う。長文で説明するより箇条書き・表・ブロック要素にした方が伝わる内容は、迷わずそちらを使う。

### 記事はコンパクトにする（2026-08-05〜・文体ルールの最上位）

**「重要でないことは省く」が原則。書き足すのではなく、削って伝える。** ユーザーから繰り返し指摘されてきたが、従来のルールは段落（160字）とリード文（2〜3文）しか縛っておらず、**一文の長さと記事全体の総量には上限がなかった**。そのため個々の段落はOKでも、長い一文と過剰な総量が残り続けていた。以下を数値で固定する。

| 対象 | 基準 | 判定 |
|---|---|---|
| 本文の総字数 | 目安2,500〜3,500字／上限4,000字 | 4,000字超は機械チェックでNG |
| 一文の長さ | 70字以内 | 70字超は機械チェックでNG |
| 段落 | 160字以内 | 従来どおりNG |
| H2直下のリード文 | 2〜3文以内 | 従来どおりNG |

根拠：公開53本の実測で総字数は中央値3,563字、直近2本は2,552字・2,860字。平均文長は34〜53字で、70字超の一文は各記事0〜8件しかない。つまり**長い記事・長い一文はこのメディアの標準ではなく逸脱**。

削るときの優先順位は次のとおり。

- 同じ内容の言い換え・二重説明を消す（最優先）<br>
- 「〜という形で」「〜ということでもあります」等の水増し表現を消す<br>
- 補足のための補足（本筋を理解するのに不要な但し書き）を消す<br>
- 説明が3文以上続く箇所は、表・箇条書き・ブロック要素に置き換える<br>
- セクション自体が本題に効いていなければ、セクションごと落とす

**文字数が目安を超えたとき、内容を足して帳尻を合わせない。必ず削る方向で直す。**

### 冗長を避ける・リード文を長くしない（2026-07-14〜）
- H2直下のリード文（見出し後、最初のブロック要素や箇条書きが出るまでの説明）は2〜3文以内を目安にする。1段落が4行を超えたら分割・削除・箇条書き化を検討する
- 回りくどい言い方・同じ内容の言い換え（「〜です。つまり〜ということです。」のような二重説明）を避け、伝えたいことを1つに絞る
- 具体例・手順・比較要素は、文章で説明せず箇条書き・表・`【ポイント】`等のブロック要素に落とし込み、文字だけの長文段落を作らない
- 執筆後、H2ごとにリード文が長すぎないかを自己チェックする（提示前チェックリストに追加）。**「意識する」だけでは実行時に飛ばされるため、必ずBashスクリプトで機械的にカウントしてから提示する**（手順は`feedback-article-self-check`メモリ参照）
- **箇条書き・表・ブロック要素の「後」に続く地の文も、リード文と同じ基準（4行=160字）でチェック対象になる（2026-07-31〜）**：`article-self-check.py`の旧チェックは「最初のブロック/箇条書きが出るまで」しか見ておらず、その後に続く地の文が野放しになっていた。M-02執筆時にこの穴を突いて長文段落が複数箇所残った実例あり。文数（3文以内）だけでなく字数も機械チェックの対象

### 体験談は「主役」にしない（2026-07-22〜）
士業シリーズ・業務適性シリーズなど「環境構築の価値」を訴求する記事では、体験談は導入のフックに徹し、本体は「読者の業務に何が任せられるか」に紙面を割く。

- 体験談セクションは合計でも記事全体の3割程度を上限の目安にする。3つのH2に分けて経緯を語らない。1つのH2（導入）に圧縮し、表・ポイントボックスで要点だけ見せる
- 「何が起きたか」の details（やり直した回数・小さな失敗の列挙など）は本筋への興味を削ぐノイズになりやすい。当事者にとって印象的でも、読者にとって重要でなければ削る
- 記事タイトルが「〇〇×職種」の形式の場合、記事の主役は職種でも体験でもなく「環境」。読者が知りたいのは「導入すると何が変わるか」であって、筆者の過去の苦労の詳細ではない

### AIっぽい文章を避ける
執筆後に「真面目すぎる」「抑揚がない」と感じたら、以下の接続表現が混じっていないか確認する。

- NG：「ここまで〜書いてきましたが」「〜について整理すると、大きく〇つあります」「〜という点が重要です」「〜ということが言えます」
- 対処：体験の具体的な感情を入れる、短文でオチをつける、自分の失敗・癖をそのまま書く、「でも正直〜」「ただ〜」で本音を差し込む

### ブロック要素の記法（2026-07-22再訂正）
ブロック要素は`>`（Markdown引用記法）を使わず、`【ブロック名】`を単独行で書き、次の行から内容を書く形式で記載する。HTMLコメントで`<!-- [WP入稿: ポイントボックス] -->`のように囲む記法も、`>`を使う旧形式も、どちらも使わない。

```
【ポイント】<br>
内容
```

複数項目を列挙する場合は、各項目の末尾に`<br>`を付けて改行する（最後の項目は不要）。空行は使わない。

**Why:** `>`を使うと、WPにコピペした際に各行が個別の引用ブロックとして認識され、1行ずつ`>`マークを消す作業が発生する。単純な改行（空行なし）はMarkdown上で無視され1行に連結される。空行を入れると別々の段落として扱われ、WP上で段落間の余白が大きく空いてしまう。この3つの問題を同時に解決できるのは`<br>`のみ（2026-07-22・弁護士編で3段階の試行錯誤の末に確定）。

使いどころはH3ごとの要点まとめ・注意警告系のリスト・H2末尾の結論。全セクションに入れると逆効果なので絞る。ブロック名一覧・使い分けは`operations/wp-block-guide.md`を参照する。

### 記事の流れ（H2の設計）
①自分の体験・失敗から入る（共感の入口。ただし圧縮する。上記「体験談は主役にしない」参照）→②なぜそうなるかを構造で説明する→③自分が変えたことを書く（解決策）→④具体的な現在のフローを書く（再現性）→⑤まとめ・読者へのメッセージ（押しつけない）

### 設定手順・ハウツー記事のルール
- WordPress・SWELL・プラグイン・**Search Console等の外部サービス管理画面**など、AIが実画面を直接確認できないUI依存の情報はたたき台として扱う。項目名・ボタン名は執筆時点で確定させず、実際の画面と異なる箇所がないか公開前にユーザーへ確認を依頼する（2026-07-28〜：Search Console記事のレビューで「AI経由インプレッション」という独自表現を正式名称と確認せず使いかけた実例あり）
- 導入文は推測で書かず、事前にユーザーから経緯・感じたことを聞いてから書く

### シリーズ記事の内部リンク
- 内部リンクを提案する前に、必ずリンク先記事のMDファイルを読んで内容を確認する（タイトルだけで判断しない）
- 前回記事へのリンクは単体行ではなく、前回の内容を軽く振り返る文章の中に埋め込む（例：`[前回](URL)、〇〇を試みました。結果は〇〇で、そこから今回の〇〇につながります。`）
- 関連記事は記事MD末尾にコメントアウトで記載しておき、WP入稿時に関連記事ブロックへ設定する

## 7〜8. 完成前チェック（省略禁止・2026-07-28に統合、2026-07-28夜に強化）

**手順は2ステップのみ。ただしNG0件は「完成」の合図ではなく最低条件。**

1. **機械チェック（🤖）**：`python3 operations/article-self-check.py articles/[slug].md`を実行し、出力を全部読む。NGが0件になるまで直す。このスクリプトが`-`箇条書き・`・`ネスト・表の数・CTA文言/間隔・関連記事本数・リード文の文数と字数（箇条書き/ブロック後の地の文も含む全段落が対象）・ブロック要素の字数・タイトル/description文字数・AIっぽい接続表現・重複表現などを機械的に検出する（検出項目の一覧はスクリプト冒頭のコメント参照）。**ブロック要素80字超・段落160字超は2026-07-31〜NGカウントに入る（旧仕様の「要確認」表示は見落とされるため廃止）。内容が濃く超過が妥当な場合のみ、その場で目視判断してOK扱いにしてよい（機械的に緩めない）**
2. **判断チェック（👁・スクリプトでは検出不可）**：スクリプト出力の末尾に表示される以下の項目を目視で確認する
   - 事実以外を書いていないか（実体験のないことを「試みた」と書いていないか）
   - AIと人が対等な目線か（「AIはこういうもの」という断定がないか）
   - 一般論と自社サービスの説明を混同していないか
   - 断定を避ける表現・本音を出す表現が自然に入っているか（6章参照）
   - 軽い自虐が1〜2箇所程度か
   - ネガティブな内容の後に前を向く一文があるか
   - 体験談セクションが記事全体の3割を超えていないか
   - 内部リンクが前回記事の振り返り文の中に自然に埋め込まれているか
   - 文字だけで長く続くセクションに図解画像候補の提案余地がないか（提案のみ・生成まではしない）
   - GEO対応：冒頭150文字以内にメインKW＋メインクエリへの直接回答（ナラティブ書き出し禁止）／Rシリーズは「実務での使い方」視点を明示
   - 文字数：目安2,500〜3,500字・上限4,000字（6章「記事はコンパクトにする」参照。機械チェックでNG判定される。水増し禁止・冗長を削った結果下回るのは可）
   - タイトルと本文の内容が一致しているか
   - **H3・地の文の段落が、箇条書き/表/ブロック要素に変換できないまま連続していないか**（表やH3の直後でも、まだ地の文の段落が続く場合は変換を検討する。機械チェックのリード文カウントは表の中身も含めてしまうため、この項目は必ず目視で見る）
   - **【ポイント】【アラート】等のブロック要素は「一言で意味が伝わる」長さになっているか**（箇条書きを2つ以上並べた対比説明・複数文の長文はブロックの役割を超えている。表か地の文に戻すか、1文に凝縮する）
   - **「対象外」「できない」の理由付けが、実際にできる範囲まで除外する不正確な表現になっていないか**（例：「対話・調整が必要だから対象外」は、下書き作成等でできる部分まで対象外に見せてしまう。何が具体的にできないのか＝人にしかできない行為そのものを名指しする）

**大きな構造変更（セクション削除・大幅圧縮）をした場合は追加で以下を確認する（2026-07-28夜〜）：**
   - frontmatterのdescription・見出し・結び・次回予告など、削除/変更した内容を前提にした記述が他の箇所に残っていないか記事全文を通しで読み直す
   - 削除前にあった内容の過去形の実感表現（「〜でした」「〜見当たりませんでした」等）が、体験の裏付けがなくなった状態で浮いていないか確認する

**ユーザーから1箇所を指摘されたら、その箇所だけ直して終わらない（2026-07-28夜〜）**：同種の問題（長い段落・冗長な理由付け・ブロック要素の使い方等）が記事の他の箇所にもないか、記事全体を横展開して確認してから再提示する。指摘のたびに1箇所ずつ直す往復を繰り返さない。

**スクリプト実行を「したつもり」で済ませない**：ターミナル出力を実際に読み、NG項目を1つずつ直してから再実行する。0件になるまで提示しない。0件になった後も、初見の読者のつもりで記事を1回通しで読んでから提示する。

**統計データを複数引用する記事は、公開ステータスに切り替える直前に一次情報での最終ファクトチェックを行う（2026-08-03〜・恒常ルール）**：本文中に登場する出典（媒体名・数値・調査対象・調査時期）を1つずつ、可能な範囲で一次情報（公式発表・調査元のレポート）に当たって確認する。`research/seo-insights.md`に書かれている内容も孫引きの可能性があるため無条件に正としない。誤りが見つかった場合は本文だけでなく`research/seo-insights.md`側の該当行も訂正する（M-02執筆時に出典・数値の誤りを発見し訂正した実例がある）。この確認は該当記事だけの一回限りの対応にせず、統計を扱う記事すべてに毎回適用する

記事MDファイルは必ずメインリポジトリの`articles/`に作成する（`.claude/worktrees/`配下には作らない）。本文はチャットに貼り付けず、MDファイルのパスのみ提示する。

## 9. 記事公開時の必須作業（省略禁止）

「入稿が完了した」の報告を受けたら、以下7つすべてを実行する。公開日はcurrentDate。確認不要。

1. MDファイル：`status: draft` → `published`／`date:`にcurrentDate記入
2. `operations/article-md-workflow.md`：作成済み記事一覧に追記
3. `operations/article-backlog.md`：`[ ]`→`[x]`、次の記事に**次回確定**マークを移動
4. GitHub issue #2：`[ ]`→`[x]`、タイトル更新、次の記事に**次回確定**、公開済み本数更新
5. `~/Documents/GitHub/tasks/README.md`：TOP6を更新
6. MDファイルのWP同期：公開ページを取得し、誤字脱字がなければWPの内容を正としてMDのテキストを修正する
7. **X投稿キューへのネタ抽出**：公開記事から気づき型断片を3本抽出→下書き化（文字数Bash実測）→ランク判定→★★★★☆以上を`knowledge/x/queue.md`に追加。リンク型候補は`knowledge/x/ideas.md`の記事由来に追記（詳細は`rules/x-post-flow.md` 3.5章）

> 注意：MDファイルはWPの最新状態と一致しない場合がある。grep確認しても古い記事はWP側で個別に変更され同期漏れの可能性がある。ズレを指摘されたらユーザーに正しい情報を確認する。

「入稿しました。」の一言だけでも、上記6点＋WP比較を自動実行する。「内容を確認してください」等の追加文言の有無は関係ない。トリガーは入稿完了の報告そのもの。
