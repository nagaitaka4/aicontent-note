# タスクリスト自動更新ルール

`~/Documents/GitHub/tasks/README.md`は全リポジトリ横断の優先順位一覧。迷ったらここに戻る。TOP10はここが唯一の正。

## TOP10の運用（2026-07-21確定）

- 1本公開して枠が空いたら、待機列（TOP11〜20）の上から入れる。待機列から選ばないときは理由を1行書く（手順は`rules/article-flow.md` 8章5番）
- 過去に「見送り」と判断した項目でも、状況変化（デフォルトモデルの変更など）があれば見直してよい。ただし見直す場合はCC判断・理由欄に「従来の見送り理由」と「見直した根拠」の両方を明記し、ユーザーが経緯を追えるようにする
- TOP10の入れ替えはCCが確認なしに実行してよいが、変更内容は`tasks/README.md`の該当行に必ず理由付きで残す

## 更新の基本原則（省略禁止）

- 記事公開・タスク完了・新タスク発生のたびに`tasks/README.md`を即更新する。確認不要
- 「○○公開後に検討」などの条件付き表記は、条件が満たされた時点で確認なしに文言を更新する（例：S-21公開済みなら「S-21公開後に検討」→「S-21公開済み・順次検討中」）
- セッション開始時にtasks/README.mdの情報を確認し、古い情報があれば確認なしに即更新する
- 🔴（要対応）・⚠️（期限近い）の絵文字はCCが日付を見て自動で付け外しする。GSC確認完了後・リサーチ実施後は確認なしに更新する
- TOP10の補足・常時掲載の状態欄も、完了・着手タイミング到来などの変化に合わせてCCが自動更新する

## 表示ルール

`tasks/README.md`を見せるときはテーブル形式そのまま提示する。要約・変換・省略はしない。

## マーケティングリサーチとの連動

- リサーチは朝ブリーフ（スケジュールタスク`x-morning-brief`・毎朝6:30）が自動実行し、月・金は同じフォルダの`full-research.md`でフル版を回す（2026-09-18に`marketing-research-mon-fri`を統合）。通常セッションでの週次リサーチは原則不要
- 手動で臨時実施する場合は、直近の自動実行分と記事ネタ・追記内容が重複しないよう確認する
- リサーチ対象は4領域：①Claude Code/Anthropic（research/trends.md）②競合AIツール・新興ツール（research/ai-tools.md）③SEO・GEO・AI検索（research/seo-insights.md）④市場・ターゲット動向＋補助金（research/market.md）。週次リサーチ時は必ず4領域すべてを確認する
- リサーチ結果の報告前に必ず既存記事（articles/）とXポストストック（sns/posts-stock.md）を確認し、重複する記事ネタ・Xネタは提案しない
- マーケティング部署リサーチを実施した場合は、セッション内でリサーチ結果の概要を必ずユーザーに報告し、**記事ネタは`operations/article-backlog.md`「リサーチ由来の記事ネタ」のM-番号テーブルに、Xネタは`knowledge/x/ideas.md`「リサーチ由来」テーブルに**、それぞれ必ず追記する（片方だけの追記は禁止）。実施後は`tasks/README.md`の「最終リサーチ日」を更新し🔴を外す
  - **⚠️ 宛先は上の2つだけ。**`sns/posts-stock.md`「断片ストック」と、`article-backlog.md`末尾の「リサーチ由来の記事ネタ（随時追加）」箇条書きは使われていない旧置き場なので書かない
- `tasks/README.md`の更新は「マーケティング部署」セクションに留めない。リサーチ結果が既存タスク（TOP10・バックログの補助金ネタ等）の状況・期限に影響する場合は、該当箇所も確認なしに更新する
- 補助金・助成金動向は「小規模事業者持続化補助金」（このメディアの受注導線として◎・詳細は`research/market.md`）を主軸に、他に使える新しい助成金・補助金がないかも毎回探索する。デジタル化・AI導入補助金2026はこのメディアの受注導線としては使えないと結論済み（個人事業主単独登録不可）のため深追いしない

### リサーチ → 制作への接続（2026-08-21確定・省略禁止）

**リサーチはストックで終わらせない。**バックログ・素材置き場は倉庫であって入口ではない。リサーチのたびに、Xネタ・記事ネタそれぞれを**制作の入口まで**運ぶ。

| ネタ種別 | 置き場（倉庫） | **運ぶ先（制作の入口）** | 運ぶ条件 |
|---|---|---|---|
| Xネタ | `knowledge/x/ideas.md`「リサーチ由来」 | **`knowledge/x/queue.md`**（下書き＋在庫サマリー表） | 鮮度期限3日以内／3条件チェックで★★★★☆以上 |
| 記事ネタ | `operations/article-backlog.md` M-番号テーブル | **`tasks/README.md`「待機列」**（2026-09-10〜） | 0番テスト（④含む）と、下記の記事化可否チェックを通過 |

- **優先順位付けは、X編集部側でもルーティン側でもよい。**ただし**根拠は必ず書く**（Xはランク＝3条件の該当数、記事は「検索需要 × 受注距離」）。根拠のない順位は後から検証できない
- **TOP10の順位は自動実行で組み替えない。**TOP10は常に10本で埋まっているため、差し込みは記事公開で枠が空いたときに行う（`rules/article-flow.md` 8章）　**⚠️ 2026-09-10追記：0番のテストを通るネタが無いときは空欄のままにする。無理に埋めない**
- **運ばなかったものは理由を1行書く。**「基準に届かず0本」は正しい結果。無理に通すほうが害になる
- **期限切れ・前提が消えたネタは取り消し線＋理由で閉じる。**残すと在庫を水増しし、編集会議の判断を狂わせる

### 0. 読者の経路テスト（2026-09-10〜・全ネタ共通・最初に通す・省略禁止）

**「この記事で得をするのは誰で、その人はいつ、どうやってこの記事に来るか」を1行で書く。**あわせて、**④このメディアの実物・実測を1つは入れられるか**を確かめる（実物＝実体験・自サイトの数字・使っている指示書や画像・公式の原文の記録）。書けない、または④を満たさないネタはバックログに留め、待機列に運ばない。

| | 書くこと | 証拠として数えないもの |
|---|---|---|
| ① 誰 | 具体的な状況の読者 | 「非エンジニア」だけ |
| ② いつ | その人が行動を起こす瞬間 | — |
| ③ どうやって | GSCの実数（直近3か月） | X（フォロワー1桁）／軸を示す／材料が揃っている／CCが自分で回せる |
| ④ 何を渡すか（2026-09-11追加・**2026-10-29緩和**） | このメディアの実物・実測を**1つは入れる**（主役でなくてよい）。検索の上位の記事に無い一手になっている | 実物が1つも入らず、一般的な手順の説明だけになる／表示やサジェストの多さ |
| ⑤ X編集部の在庫（2026-09-11追加・2026-09-12に機械化） | **`python3 operations/x-article-sync-check.py`を実行し、記事側に渡っていないX側の下書きを出す。**同じ題材のIDと数字を材料シートに書く | 読まずに「材料が無い」と判定すること／「ルールが無い」と言ってルールを足すこと（決まりは前からある。守られていないだけ） |

**③の判定**

| 判定 | 条件 | 扱い |
|---|---|---|
| ◯ | 直接のクエリに2桁の表示、または同じテーマの記事に2桁のクリック | 昇格させてよい |
| △ | 直接のクエリは1桁で、同じテーマの記事に2桁の表示がある | 残してよいが、**経路が1桁のうちは着手しない** |
| ✗ | 直接のクエリの表示がゼロ | 昇格させない |

**⚠️ 2026-09-10改訂：まだ記事が無いテーマは、GSCだけで判定しない。**
GSCは自サイトに記事があるテーマにしか表示を持たない。**GSCだけで見ると、書いていないテーマは構造上ほぼ通らない**（9/10に「新規記事の合格は1本」になった原因）。新規テーマは次で判定する。

| 判定 | まだ記事が無いテーマの条件 |
|---|---|
| ◯ | **④を満たす（実物・実測を1つは入れられ、上位の記事に無い一手になる）** **かつ** Googleのサジェストが5件以上（2語まで）。自サイトの需要クラスタ（GSCで2桁表示）の隣なら、なお良い |
| △ | サジェストが1〜4件、または④が弱い（実物は入るが、上位の記事と差がつかない） |
| ✗ | **④を満たさない（実物が1つも入らず、一般的な手順の説明だけになる）**、またはサジェスト0件（2語までの短い語で取り直しても0件のとき） |

**⚠️ 2026-10-29：④を緩め、テーマの作り方を「検索で読まれている記事から作る」に変えた（ユーザー了承）。**手持ちの材料から考えると候補が手持ちの範囲に閉じ、GPT案20本から◯が5本しか残らなかった。新しい作り方：①種の語からGoogleサジェストを数百件集める ②読者の判断になっている語を選び、その語のサジェスト件数を測る ③その語の検索上位を読み、読まれている型（構成・切り口）と足りない所を見る ④型を借りて、このメディアの実物・実測を1つ入れる。**真似るのは骨組みだけ。上位の記事の文章は借りない。**初回の記録と手順は`operations/theme-candidates-2026-10-29-demand-first.md`

記事の種類別のGSC実測は`operations/editorial-strategy.md`（1-0章・1章）が正。

**サジェストの取り方**：実Chromeで`https://www.google.com/robots.txt`を開き、そのページのJSから`fetch('/complete/search?client=firefox&hl=ja&ie=utf-8&oe=utf-8&q=<語>')`で読む（最大10件）。
**⚠️ サジェストのURLを直接開かない**（Chromeがファイルとして保存する・2026-09-10に`~/Downloads/f.txt`が作られた）。**⚠️ 長い語は0件になりやすい**ので2語までで取る。

### テーマの出どころ（2026-09-12・ゼロベースで改訂）

### 編集方針（`operations/editorial-strategy.md`・2026-09-11新設）

**記事の種類別の実測（何が当たり、何が当たらないか）とハブ（足りない記事）の定義はここが正。**TOP10・待機列の提案はこの方針から作る。毎週月曜の定期リサーチが実測とハブの状態を更新し、月次のGSCで勝ち筋・負け筋を見直す。

### 補充の手順（朝ブリーフの定期リサーチ＝`full-research.md`で自動実行）

**実行するのは朝ブリーフの定期リサーチ（`x-morning-brief`の`full-research.md`）。新しい記事ネタの補充（③）は、曜日を問わずTOP10が10本を切っているときだけ実行する**（2026-10-20 ユーザー指示で変更。旧：月曜は必ず・金曜は待機列の◯が5本未満のとき）。手動で補充するときも同じ手順で行う。

1. **テーママップの空欄から候補を出す**（`operations/theme-map.md`）：「アーカイブ：無い」かつ需要がある欄。材料は`operations/editorial-meeting.md`の回答・直近1週間の`git log`・体験由来のバックログ・**`python3 operations/x-article-sync-check.py`が出すX側の下書き**から集める
2. **需要を確かめる**：候補ごとに、GSCのクエリ全件（直近3か月）で隣のクラスタを探し、2語までの語でGoogleサジェストを取る
3. **既存記事と重ならないか確かめる**：既存記事のH2・H3で扱っている意図はリライト側に回す（カニバリ防止）。**ただし、その既存記事のfrontmatterに`series:`があるときは改稿にしない**（前後の記事が「前回の#03」「次の#05」でつながり、題の型もそろっている）。新規で書き、既存記事の末尾から1行リンクする（2026-10-23追加）
4. **0番テストをかける（④含む）**：◯は`tasks/README.md`の待機列へ、△は`operations/article-backlog.md`へ
5. 取った数字は`operations/site-status.md`に残す
6. **◯が足りないときは、基準を下げずに「編集会議で補充が必要」と報告する**

### ツール・機能系ネタの記事化可否チェック（2026-07-30〜・省略禁止）

**着手してから「動かせない」「説明が複雑すぎる」と分かる事態を、追加前のチェックで防ぐ。**

新機能・アップデート系のネタを`article-backlog.md`・`tasks/README.md`に追加する前に、以下を確認する。

1. **一次情報を確認する**：ニュースサイトの要約（二次情報）だけで判断しない。公式ドキュメント・公式ブログを確認し、機能の実際の仕組みを把握する。似た名前の別機能（例：Chrome拡張機能連携とDesktopアプリ内蔵ブラウザ）が混在していないか確認する
2. **CC自身が実演・検証できるかを見積もる**：このメディアは「実際に動かして見せる」実況が軸。CCがそのセッション環境で実際に触って動作確認できる見込みが低い機能（実行環境依存・別アプリのネイティブ機能等）は、記事化の優先度を下げるか、着手前にユーザーへ検証可否を確認する
3. **非エンジニア向けに一言で説明できるかを自問する**：仕組みの説明に前提知識の対比（AとBは別物、のような整理）が必要な機能は、読者に伝わりにくいリスクが高い。TOP10に入れる時点でこの確認を行い、複雑すぎると判断したら見送るか、後回しにする
4. 上記1〜3を経てもなお記事化に値するか判断がつかない場合は、TOP10ではなく`article-backlog.md`のストックに留め、正式にTOP10へ格上げする前に5分程度の簡易検証（公式ドキュメントを読む・可能なら実際に触ってみる）を済ませる
