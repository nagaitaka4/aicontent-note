# タスクリスト自動更新ルール

`~/Documents/GitHub/tasks/README.md`は全リポジトリ横断の優先順位一覧。迷ったらここに戻る。TOP10はここが唯一の正（session-handoff.mdのTOP6は廃止）。

## TOP10の運用（2026-07-21確定）

- 記事制作タスクはTOP5からTOP10に拡張。リサーチ由来の記事ネタが週2回増え続けるため、5枠だと頻繁に枯渇し棚卸しが必要になっていたことが理由
- 1本公開して枠が空いたら、CCが`operations/article-backlog.md`のストック全体を見直し、その時点で最も価値が高いものを選んで補充する。**ストックした日付順（古い順）に機械的に繰り上げない**。日付順に繰り上げると、鮮度切れ（期間限定ネタの期限切れ・価格改定前の情報等）や既存企画への統合対象を誤って単独記事に昇格させるリスクがあるため
- 補充時の判断基準：①旬（情報が古びていないか）②このメディアの軸（環境構築→実際に動かす実況・非エンジニア向け・受注導線）との適合度③既存TOP10タスクとの統合可否（データの重複は統合し単独記事化しない）
- 過去に「見送り」と判断した項目でも、状況変化（デフォルトモデルの変更など）があれば見直してよい。ただし見直す場合はCC判断・理由欄に「従来の見送り理由」と「見直した根拠」の両方を明記し、ユーザーが経緯を追えるようにする
- TOP10の入れ替えはCCが確認なしに実行してよいが、変更内容は`tasks/README.md`の該当行に必ず理由付きで残す

## 更新の基本原則（省略禁止）

- 記事公開・タスク完了・新タスク発生のたびに`tasks/README.md`を即更新する。確認不要
- 「○○公開後に検討」などの条件付き表記は、条件が満たされた時点で確認なしに文言を更新する（例：S-21公開済みなら「S-21公開後に検討」→「S-21公開済み・順次検討中」）
- セッション開始時にtasks/README.mdの情報を確認し、古い情報があれば確認なしに即更新する
- 🔴（要対応）・⚠️（期限近い）の絵文字はCCが日付を見て自動で付け外しする。GSC確認完了後・リサーチ実施後は確認なしに更新する
- TOP5の補足・常時掲載の状態欄も、完了・着手タイミング到来などの変化に合わせてCCが自動更新する

### リサーチ → 制作への接続（2026-08-21確定・省略禁止）

**リサーチはストックで終わらせない。**バックログ・素材置き場は倉庫であって入口ではない。リサーチのたびに、Xネタ・記事ネタそれぞれを**制作の入口まで**運ぶ。

| ネタ種別 | 置き場（倉庫） | **運ぶ先（制作の入口）** | 運ぶ条件 |
|---|---|---|---|
| Xネタ | `knowledge/x/ideas.md`「リサーチ由来」 | **`knowledge/x/queue.md`**（下書き＋在庫サマリー表） | 鮮度期限3日以内／3条件チェックで★★★★☆以上 |
| 記事ネタ | `operations/article-backlog.md` M-番号テーブル | **`tasks/README.md`「待機列」**（2026-09-10〜） | 0番テスト（④含む）と、下記の記事化可否チェックを通過 |

- **優先順位付けは、X編集部側でもルーティン側でもよい。**ただし**根拠は必ず書く**（Xはランク＝3条件の該当数、記事は「検索需要 × 受注距離」）。根拠のない順位は後から検証できない
- **TOP10の順位は自動実行で組み替えない。**TOP10は常に10本で埋まっているため、差し込みは記事公開で枠が空いたときに行う（`rules/article-flow.md` 8章）　**⚠️ 2026-09-10追記：0番のテストを通るネタが無いときは空欄のままにする。無理に埋めない**
- **運ばなかったものは理由を1行書く。**「基準に届かず0本」は正しい結果。無理に通すほうが害になる
- **期限切れ・前提が消えたネタは取り消し線＋理由で閉じる。**残すと在庫を水増しし、編集会議の判断を狂わせる

> **経緯**：2026-08-21の棚卸しで、8/14以降リサーチ由来のX下書きが0本のまま7日続き、その間に鮮度期限切れが3件発生していた。リサーチ側の責任範囲が「ideas.mdに書く」で終わっていたことが原因。

### 0. 読者の経路テスト（2026-09-10〜・全ネタ共通・最初に通す・省略禁止）

**「この記事で得をするのは誰で、その人はいつ、どうやってこの記事に来るか」を1行で書く。**あわせて、**④この記事でしか渡せないもの（実体験・実データ）が主役になるか**を確かめる。書けない、または④を満たさないネタはバックログに留め、待機列に運ばない。

| | 書くこと | 証拠として数えないもの |
|---|---|---|
| ① 誰 | 具体的な状況の読者 | 「非エンジニア」だけ |
| ② いつ | その人が行動を起こす瞬間 | — |
| ③ どうやって | GSCの実数（直近3か月） | X（フォロワー1桁）／軸を示す／材料が揃っている／CCが自分で回せる |
| ④ 何を渡すか（2026-09-11追加） | この記事でしか渡せない実体験・実データが主役になる | 一般的な手順の説明が主役になる／表示やサジェストの多さ |
| ⑤ X編集部の在庫（2026-09-11追加・2026-09-12に機械化） | **`python3 operations/x-article-sync-check.py`を実行し、記事側に渡っていないX側の下書きを出す。**同じ題材のIDと数字を材料シートに書く | 読まずに「材料が無い」と判定すること／「ルールが無い」と言ってルールを足すこと（決まりは前からある。守られていないだけ） |

**③の判定**

| 判定 | 条件 | 扱い |
|---|---|---|
| ◯ | 直接のクエリに2桁の表示、または同じテーマの記事に2桁のクリック | 昇格させてよい |
| △ | 直接のクエリは1桁で、同じテーマの記事に2桁の表示がある | 残してよいが、**経路が1桁のうちは着手しない** |
| ✗ | 直接のクエリの表示がゼロ | 昇格させない |

**⚠️ 2026-09-10改訂：まだ記事が無いテーマは、GSCだけで判定しない。**
GSCは自サイトに記事があるテーマにしか表示を持たない。**GSCだけで見ると、書いていないテーマは構造上ほぼ通らない**（9/10に「新規記事の合格は1本」になった原因）。新規テーマは次で判定する。

| 判定 | まだ記事が無いテーマの条件 |
|---|---|
| ◯ | **④を満たす（実体験か自サイトの実データが主役になる）** **かつ** Googleのサジェストが5件以上 **かつ** 自サイトの需要クラスタ（GSCで2桁表示）の隣 |
| △ | サジェストが1〜4件、または④が弱い（実体験はあるが、記事の主役にするには足りない） |
| ✗ | **④を満たさない（一般的な手順の説明が主役になる）**、またはサジェスト0件（2語までの短い語で取り直しても0件のとき） |

**⚠️ 2026-09-11：④を足した理由。**9/10に需要の数字（サジェストの件数）から作った新規ネタが、一般的な手順の説明に寄った（被リンク・検出 - インデックス未登録・SWELLの目次など）。ユーザーから「これまでと毛色が違う・内容が薄い」と指摘され、9/11に外した。③は「読者が来るか」しか見ておらず、「来た読者に何を渡すか」を見ていなかった。

自サイトでクリックが2桁あるのは、実体験×製品・業務の2本だけだった（GSC直近3か月・`operations/site-status.md` 2026-09-10）。

新機能・アップデート系のネタを`article-backlog.md`・`tasks/README.md`に追加する前に、以下を確認する。

1. **一次情報を確認する**：ニュースサイトの要約（二次情報）だけで判断しない。公式ドキュメント・公式ブログを確認し、機能の実際の仕組みを把握する。似た名前の別機能（例：Chrome拡張機能連携とDesktopアプリ内蔵ブラウザ）が混在していないか確認する
2. **CC自身が実演・検証できるかを見積もる**：このメディアは「実際に動かして見せる」実況が軸。CCがそのセッション環境で実際に触って動作確認できる見込みが低い機能（実行環境依存・別アプリのネイティブ機能等）は、記事化の優先度を下げるか、着手前にユーザーへ検証可否を確認する
3. **非エンジニア向けに一言で説明できるかを自問する**：仕組みの説明に前提知識の対比（AとBは別物、のような整理）が必要な機能は、読者に伝わりにくいリスクが高い。TOP10に入れる時点でこの確認を行い、複雑すぎると判断したら見送るか、後回しにする
4. 上記1〜3を経てもなお記事化に値するか判断がつかない場合は、TOP10ではなく`article-backlog.md`のストックに留め、正式にTOP10へ格上げする前に5分程度の簡易検証（公式ドキュメントを読む・可能なら実際に触ってみる）を済ませる
