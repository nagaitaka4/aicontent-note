X投稿を提案・作成するすべての作業でこのファイルを参照する。

## このアカウントでXをやる目的

バズを狙うのではない。以下を目的とする。

- **フォロワー獲得**：「Claude Code × 実務」の視点を持つ人と繋がる
- **記事への送客**：投稿が記事を読む理由になる
- **ポジション確立**：「Claude Codeを実際の業務に当てはめて考察する人」として認知される

**差別化の軸：**  
「Claude Code × ○○業」という紹介をするのではなく、**Claude Codeを実際の業務へ当てはめて考察すること**がコンテンツの核。単なるAI紹介ではなく、業務への落とし込みを見せる。

## X編集部の構造

このアカウントの投稿は「CCが考えたネタを出す」のではなく、**「ユーザーの体験を取材して価値を引き出す」** 編集部として動く。

```
[取材] → [素材ストック] → [ネタ選定] → [制作] → [公開] → [振り返り]
          ideas.md                         published.md更新
             ↑
   月・金リサーチ自動連携（軸②）
```

**CCの役割は編集者：**
- 取材者として、ユーザーの体験から価値を掘り起こす
- 編集者として、素材から「一番強い断片」を選ぶ
- ライターとして、選んだ断片をXの上限（重み280）に収める

**ユーザーの実作業が素材の起点：**
強い投稿は、ユーザーが実際にやったこと・気づいたこと・驚いたことから生まれる。CCはそれを材料にHR級の完成品まで書き切り、本人が体験・本音に差し替える（【2026-09-30 確定】）。

## 1. 取材フロー（軸①・気づき型の起点）

インタビューした内容は `knowledge/x/interviews.md` に記録する。断片の解像度・取材日・ステータスが残ることで、次のセッションでも続きから動ける。

### 日常拾いが主・取材は補助（2026-08-06設計変更）

**素材の供給は「会議で取材する」から「日常の作業から自動で拾う」に変える。**理想は常にHR級10本。取材はそれでも枯れたときの補填に回す。

**拾うタイミング（確認不要・即実行）：**

| 場面 | 拾うもの |
|---|---|
| ユーザーが感情を表に出した瞬間 | 「まじで」「いや」「困る」「意味がない」「なんで」等が出たら、その直前の話題が素材 |
| 作業で数字が出た瞬間 | GSC分析・リライト・時間計測・料金確認など。**数字＋その数字で何を決めたか**をセットで記録 |
| 判断を変えた瞬間 | 方針転換・ルール変更・撤回。「◯◯にしていたが△△に変えた」は3条件の「決断」に直結 |
| 詰まった・やり直した瞬間 | 手戻り・失敗・想定外。**うまくいった話より伸びる**（実測：「全く気が付きませんでした」64・「面倒で」42） |
| 記事公開・GSC/X分析の完了時 | 作業結果から3本抽出（従来どおり） |

**拾い方：**その場で`knowledge/x/ideas.md`に1行書く。**下書き化はしない。**「いつ・何があったか・3条件のどれを満たすか」だけ記録して作業に戻る。

### 取材するタイミング（補助的手段）

日常拾いを実行したうえで、**在庫5本未満、または出せる★★★★★が2本未満のとき**に、朝ブリーフで取材の候補を出して実施する（2026-10-29に朝ブリーフの基準にそろえた）。それ以外では取材のためだけに時間を取らない。

- ユーザーが「面白い」「気づいた」「変わった」「驚いた」を含む発言をした（従来どおり即取材可）
- 記事制作中にユーザーが体験ベースのコメントをした

### 取材の候補を作る前に、2つを必ず通す（2026-09-22新設・省略禁止）

1. **「え、そうなの？」になるか。**仕様上そうなるだけの話、当たり前のことは聞かない
2. **事実関係を確認してから候補を書く。**「誰が」「どこで」「どうやって」を推測で埋めない

**「何を思いましたか」を聞かない。**感情は結果であって、取材で掘るのは**事実のほう**。事実が「え、そうなの？」なら、感情は後から1行で付く。

### インタビューの作法（省略禁止）

CCは質問と同時に「ホームラン候補3つ」を必ず提示する。質問だけ投げない。

```
【フォーマット】
質問（1文）

ホームランになる答えの候補：

候補A：〇〇
（Before → After を1〜2行で）

候補B：〇〇
（Before → After を1〜2行で）

候補C：〇〇
（Before → After を1〜2行で）

どれかに近い体験がありますか？
「全部違う」でも構いません。そこから始めます。
```

**なぜこのフォーマットか：**
- 質問だけだと答えに詰まる
- 候補がヒントになって、「少し違うけどこういう感じ」が出やすくなる
- 候補の中にない答えが出たときが最もホームランになりやすい

**判断：取材した断片がホームラン候補か？**

| 判断基準 | Yes → | No → |
|---|---|---|
| 「永井さんにしか書けない」か | ideas.mdにストック | 没（記録せず） |
| 数字・変化・逆説がある | 強い素材として記録 | インタビューを深める or 没 |

## 2. リサーチ連携フロー（軸②・AI動向型の起点）

**X編集部が大本で、マーケティング部署の2つの自動ルーティンはその供給ライン。**基準はこの章が正で、ルーティン側（`~/.claude/scheduled-tasks/*/SKILL.md`）は基準を写経せずここを読む（2026-08-21確定）。

### 走っているルーティン

毎朝6:30の`x-morning-brief`が①Claude/Anthropic ②競合AIツールを調べ、月・金は同じタスクが`full-research.md`で③④フル＋補助金＋記事ネタ＋編集会議準備まで行う。Xネタは ideas.md →**下書き→queue.md**→同じ朝の投稿候補、記事ネタは→**待機列**。詳細は3.8。

### 各リサーチ後にCCが実行すること

1. `research/`配下の更新内容をReadして確認する
2. 下記の採用基準でX向きネタを判定する
3. 該当ネタを `knowledge/x/ideas.md`「リサーチ由来」に追記する（**宛先はここだけ。**`sns/posts-stock.md`「断片ストック」は旧置き場で、入れても誰も見ない）
4. **鮮度期限が3日以内のものは、その場で下書きにして`queue.md`へ入れる**（3.5章の手順）。ここまでやらないと素材が積み上がるだけになる
5. 下書き化したら ideas.md の行を取り消し線にし、消化先IDを書く
6. **期限切れのネタは取り消し線＋理由で閉じる**（再利用条件があれば書く）

**X向きの判断基準（軸②用・2026-08-11実測確定／これが正）：**

| 採る | 採らない |
|---|---|
| **使う側の何かが変わる**（料金・制限・既定モデル・提供終了・使える範囲） | **新モデルが出たという報告だけ** |
| 実務に落として語れる | ニュースの要約で終わる |

実測：当たった＝Opus 5デフォルト化94／Gemini CLI有料化72／Claude障害63。当たらなかった＝Desktop刷新3／Opus 4.8発表9／ゼロクリック83%が5。**速報だから伸びるのではない。「自分にどう影響するか」が書けるかどうか。**

> **⚠️ 2026-08-11以前の基準（タイムリー／実務に落とせる／「知らなかった」が動く）は廃止した。**「タイムリーかどうか」で採ると、新モデル発表の報告が通ってしまう（実測3〜9ビュー帯）。

**旬ネタの鮮度：**
- AI動向は発表から3日以内が最高ビュー帯。リサーチ当日か翌日に出すのが原則
- 3日を過ぎたら「実務への影響の振り返り」に切り口を変えて出す

**基準の見直し（省略禁止）：**
ルーティンは毎回`knowledge/x/published.md`の直近10本を読み、**この章の実測値と直近の実績がズレていないか確認する。**ズレていれば報告に明記する（ルーティン側で基準を書き換えない。改訂はこの章で行う）。

## 3. ネタ選定フロー

### 基本投稿サイクル

**気づき型 → リンク型 → 気づき型 → リンク型** を基本サイクルとする。リンク型が続く場合は気づき型を挟む。

### テーマを育てる設計（最優先ルール）

テーマは単発で終わらせない。1つのテーマを以下の流れで育てる：

1. **気づき投稿**（新しい視点・認識が変わる切り口）
2. **親記事リンク**（考え方・構造を解説した記事への入口）
3. **子記事リンク**（具体例・実践事例への入口）

記事単位ではなく**テーマ単位**でX運用を設計・提案する。CCはネタ選定・制作提案のとき、常にこの「テーマの育て方」視点で動く。

### 「次の投稿」を決めるとき

1. 0章の必読ファイルを見て選ぶ（素材は`ideas.md`を全件、高ビューパターンは`published.md`、重複・開き方の被りは`posts-stock.md`）

**選定の優先順位：**

| 優先 | 素材 | 条件 |
|---|---|---|
| 1 | 旬のリサーチ由来（軸②） | 発表から3日以内 |
| 2 | 取材済み断片・日常拾い（軸①） | — |
| 3 | 記事由来リンク型（軸③） | X向き判定済みで投稿タイミングが来ている |

ランクは4章「3条件チェック」で数える。**出すのは★★★★★（3条件2つ以上）だけ**（【2026-09-08 判定】）。

**NG選定の補足：**

**投稿ペース：下限なし（2026-08-07変更・最小コスト運用へ）**

## 3.4 リプライ運用（2026-08-07新設・露出を増やす唯一の低コスト手段）

**自分の投稿は5フォロワーにしか確実には届かない。**リプライは相手のフォロワーに届くため、1回1分で自分の最高ビュー（94）を超える露出が取れる。

### 選ぶ順序（2026-08-17確定・省略禁止）

**規模から選ばない。噛み合うかを先に見る。**

1. **相手の投稿に対して、手元の実測で噛み合う返しがあるか**（なければ規模がいくら大きくても見送る）
2. 同じ実測データを過去に使っていないか（`published.md`のリプライログで確認）
3. そのうえで規模（1,000ビュー以上）と鮮度（48時間以内）

### 対象アカウントの選定基準

| 選ぶ | 選ばない |
|---|---|
| 実務・等身大の悩み・誠実な検証 | **煽り・数字盛り・情報商材系**（規模ではなく中身で除外する） |
| **1,000ビュー以上**（下限のみ。2026-08-17に上限10,000を撤廃） | 1,000ビュー未満（絡んでも読まれない） |
| 投稿が**48時間以内**（見られている状態） | 1週間以上前の投稿 |

| 狙い | 選ぶ相手 |
|---|---|
| リーチ（露出の絶対量） | **1万超**。率は落ちるが人数は増える |
| 反応・関係づくり | **小規模**。実測でいいね・返信は小規模から来ている（3ビューでも13ビューでもいいねが付き、104ビューでは付かなかった） |

**規模ではなく中身で除外する。**@oikon48は4.4万だが書籍著者で煽りではない。一方「1ヶ月で3,700フォロワー・即マネタイズ」のような投稿は規模に関係なく対象外。

**フォローの有無は選定基準に入れない**（2026-08-12）。フォロー中／相互フォローの相手に絡んで構わない。むしろ**対象アカウントはフォローしておく**。タイムラインに流れてくるので「48時間以内の投稿」を探す手間が消える（08/12は未フォロー中心に探して1件しか見つからず、検索に時間を使った）。

- ⚠️ **ただし絡みやすい相手に偏らない。**「特定の1人としか会話していないアカウント」に見えると広がらない。歯止めは既存の「1アカウントにつき週1回まで」

### 除外台帳（2026-08-24新設／同日中に訂正・**「今日は誰に絡めないか」だけを示す表**）

**⚠️ この表は候補リストではない。**リプライ先は**投稿日にその場でリサーチして決める**。**「鮮度が高い投稿をしている人」が選定の起点**であって、表の上から順に当てにいくのではない。

**この表の役割は1つだけ：14日以内に絡んだ人を機械的に外すこと。**毎回リプライログから逆算する手間を省くためにある。

**表は`knowledge/x/reply-ledger.md`の「除外台帳」**（2026-10-29にこのファイルから移した）。リプライを出したら、その日のうちに相手の行を足し、解除日を過ぎた行は消す。

**解除済み＝「絡んでよい」であって「絡む」ではない。**その日に鮮度の高い投稿がなければ、解除済みでも見送る。

**投稿日の実際の手順（この順序を守る）**

1. **鮮度で探す。**その日に**48時間以内の投稿**があって、**中身が噛み合う**ものを探す。`3.4`「対象アカウントの選定基準」（実務・等身大の悩み・誠実な検証／1,000ビュー以上／煽り・情報商材系は規模に関係なく除外）で絞る
2. **見つけた相手を除外台帳（`knowledge/x/reply-ledger.md`）で照合し、14日以内に絡んでいれば外す。表だけで判断せず、Xで`from:aicontent_note to:相手のID`を検索して返信済みでないかも確かめる**（2026-10-01：9/30の返信が記録漏れで台帳に無く、@sakamoto_582へ同じ本文を二重送信した）
3. **相手の投稿を最後まで読む**（`3.4`「相手の投稿を最後まで読む」4項目・省略禁止）
4. **手元の実測で噛み合う返しがあるか**を見る。なければ見送って次の候補へ

**探す先は対象リストに限らない。**リストは「絡む価値が確認できている人」の記録であって、母集団ではない。**その日いちばん鮮度が高く噛み合う投稿が、リスト外にあればそちらを選ぶ**（新規はリーチの母数を増やす・`3.4`「なぜ1アカウント1回きりにしないか」）。**良かった相手はリストに追加する。**

### 対象リスト（**候補ではなく「絡む価値が確認できている人」の記録**）

**表は`knowledge/x/reply-ledger.md`の「対象リスト」**（2026-10-29にこのファイルから移した）。リプライを出したら、相手の行を足すか更新する。

### 相手の投稿を最後まで読む（2026-08-17確定・省略禁止）

**下書きを1文字も書く前に、相手の投稿を全部読む。**タイトル・冒頭・検索結果のスニペットだけで書かない。

**読む範囲（すべて必須）**

| # | 対象 | やり方 |
|---|---|---|

## 3.5 投稿キュー運用（半自動化の中核・2026-08-03〜）

**目的：ユーザーの時間を使わずにX運用を回す。**ユーザーがやるのは「次のポスト内容と、リプライ先と内容をお願いします」（または朝ブリーフの候補を見る）→投稿・いいね・リプライ→「3点完了しました」の報告のみ（7章）。それ以外はすべてCCが管理する。

### キューの定義（`knowledge/x/queue.md`）

- **理想は常時10本（HR級）。**毎日1本のペースでは10本＝約10日分にあたる。**在庫5本未満、または出せる★★★★★が2本未満なら取材で補充する**（判断基準の表は3章「キュー在庫の判断基準」）
- 目標構成：★★★★★（HR級）7〜8本＋★★★★☆（ヒット）2〜3本。★★★☆☆は原則入れない（在庫不足時の暫定枠のみ・差し替え前提）。**出すのは★★★★★だけ**（【2026-09-08 判定】）
- 順位はCCが管理する。基準：ランク ＞ 鮮度 ＞ 軸・テーマのバランス（同軸・同テーマの連続を避ける）＞ テーマを育てる順序
- `ideas.md`＝素材（未下書き）、`queue.md`＝完成下書き。下書き化したらideas.mdから削除してqueue.mdへ移す

### 整合チェック（2026-08-23新設・在庫を数えるときに毎回実行）

**在庫の本数だけ見ても、中身がズレていることがある。**在庫確認とセットで以下3点を必ず通す。朝ブリーフ（`x-morning-brief`）も、セッション中にCCが在庫を見るときも、同じチェックを実行する。

| # | 見るもの | ズレていたときの処理 |
|---|---|---|
| 1 | **在庫サマリー表の行数 ＝ 本文の下書き数か** | 一致しなければ孤児。表に無い下書きを検出して報告し、生かすなら表に行を足す／死んでいるなら削除する |
| 2 | **`ideas.md`で生きている行のうち、`queue.md`に同じ素材の下書きがあるものはないか** | あれば`ideas.md`側を取り消し線にし、消化先IDを書く。**鮮度期限に関係なく実行する**（期限が長いネタほど見落とす） |
| 3 | **直近5投稿（`sns/posts-stock.md`）と内容が重なる下書きがキューに残っていないか** | 重複なら削除する。角度を変えれば生きる場合のみ、その角度を書いて残す |

### 運用ループ（2026-08-07・迷わない運用に確定）

**CC下書き → 盲検（読者3人）＋`x-gate.py` → そのまま投稿。**ユーザーは「ニュアンスをどうするか」で悩まない。

**2026-09-25改訂：GPTレビューは廃止（ユーザー承認）。**`x-gate.py`で[出してよい]になった本文は、GPTに通さずそのまま出す。GPTが見ていた読者目線・トーン・文字数は、元ネタを知らない読者役3人（`x-review-judge.py`が合否）とゲートで置き換えた。**読者役は事実の正しさを見ないので、事実確認（0章）はCCが記録・一次情報と照合してから出す。**朝ブリーフの目的「やりとりなしで一発で出せる1本」と、GPTの往復は両立しないため。**ユーザーが本文を直した場合は、その版をゲートに通し直す**（盲検の合格と一字一句一致しなくなるため）。

理由：**毎日1本のペースで1本ずつニュアンスを悩むと、それだけで週の時間が埋まる。**事実（数字・固有名詞）はCCが実測・確認済み、読者目線・トーン・文字数は盲検とゲートで確認済みなので、2段階で品質は担保されている。「ニュアンスの好み」に正解はなく、悩んでも精度は上がらない。

**ユーザーが止めるのは次の場合だけ：**
- 事実が違う（自分の体験と食い違う）
- 出したくない情報が入っている
- 読んで明らかに違和感がある

**それ以外は迷わず出す。**反応が悪ければ2週間おきの分析で分かるので、そこで直せばよい。

手順は7章「次の投稿内容を教えて」。

## 4. 制作ルール（執筆）

### 3条件チェック（2026-08-06・全56投稿の実測から確定・全下書きに適用）

下書き作成時とキュー投入時に必ず自己判定する。**該当数がそのままランクになる。**

```
□ 今これを出す理由があるか（旬・変化・締切・自分に起きた出来事）
□ 具体物があるか（数字・固有名詞・実際の作業・画面・金額）
□ 決断か感情が入っているか（やめた・変えた・驚いた・イライラした）
```

| 該当数 | ランク | 実測の裏付け |
|---|---|---|
| 0個 | **出さない** | 一般論・所感で終わる投稿は10未満（全体の45%がこれ） |
| 1個 | ★★★★☆ | 中位で安定。ただし今は出さない（【2026-09-08 判定】） |
| 2個以上 | ★★★★★ | 80超に届く（Opus5-気94＝旬＋感情／メルカリ-リ81＝具体物＋実況） |

**数字だけの投稿は禁止。**「◯本書いた」「8時間→4〜5時間」は単独では伸びない（実測8ビュー・6ビュー）。必ず**「だから何を変えたか／やめたか」**とセットにする。同じ数字系でも「8応募2テスト0契約435円→やめます」は94ビュー。**違いは決断の有無。**

**軸で判断しない。**「AI動向は伸びる／実験ログは伸びない」ではない。実測では軸②も軸①も2〜94まで振れており、**差は軸ではなく上の3条件を満たすかどうか**。AI動向に寄せるとポジション（非エンジニアがClaude Codeでメディアを回している人）が薄まる（軸比率の目標は【2026-09-08 判定】で凍結）。

**ランクの判定に使う補助基準：**
- 「え、そうなの？」意外性・逆説 ／ 「自分もそうだった」共感 ／ 「それ知らなかった」発見
- 「真似したい」再現性 ／ 「この人面白い」価値観・思想

### 一人称に「自分」を使わない（2026-10-13改訂・ユーザー指示・投稿もリプライも）

- **基本は主語を省く。**どうしても要るときは**「私」**。一人称でない「自分」（「自分で確認」）も避ける（「手で確認」「自力で」）

- 事業として言うときは**「このメディア」「当メディア」**（記事本文と揃える）。⚠️ ただし**冒頭は主語なしで始めない**（別ルール）。文頭には対象・話題を置く（例：「引用、」「Claude Code、」）

### キャラ・トーン（2026-08-03確定・全投稿に適用）

**堅い投稿は5万とある。差別化はトーンでも起きる。**

**目指すキャラ：カジュアル・ラフ・本音ベース。自分をネタにできる実況者。**先生ではない。教える人ではなく、やってみて詰まっている様子をそのまま見せる人。

- ⭕「公式ページ見てるから大丈夫、と思ってた自分が一番あぶなかったです」（自分の失敗）

### 自虐に使ってはいけない題材（2026-08-03確定）
