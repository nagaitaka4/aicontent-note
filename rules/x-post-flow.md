# X投稿制作フロー・ルール

X投稿を提案・作成するすべての作業でこのファイルを参照する。

---

## 0. 提案前に必ず読むこと（省略禁止）

`sns/posts-stock.md`は投稿済み一覧の表だけでなく、**冒頭の「運用ルール」「Xのポジション」「戦略メモ」「投稿4軸と優先順位」を毎回読んでから**提案する。

- 提案する内容の書き出し・テーマが投稿済みと重複していないこと
- 現在の軸別比率目標（軸①50%／軸②30%／軸③15%／軸④5%）を踏まえる
- 気づき型とリンク型の同記事ペアは3〜5本間隔を空ける

### リンク型を作る前の判断（省略禁止）

記事を公開したからといって、必ずXで紹介する必要はない。**X向きの記事とSEO向きの記事は別物。**

リンク型を作る前に以下を確認する：

**X向き（作る）：**
- 数字がある（出品時間が半分・8時間→4時間）
- あるある・共感フックがある（最新版どれ？）
- 「知らなかった」「すごい」「自分もやりたい」のどれかが動く

**SEO向き（Xでは触れない）：**
- 検索クエリに刺さるが、スクロールを止める力がない
- フックを無理に作ろうとしても弱さを解消できない記事

→ SEO向きの記事は公開・内部リンクで十分。Xで無理に戦わせない。

## 1. 目的とポジション

**目的：情報を伝えるのではなく、スクロールを止める。**

投稿単体で価値を出しつつ、「AIで仕事を回している非エンジニア」というブランドを積み上げる。

**ポジション：非エンジニアなのにClaude CodeとAIでメディアを回している人。**

- ニュース解説アカウントではない。**AI運用ログアカウント**
- 気づきを伝えるだけでなく、実際の運用の断片（READMEの一部・ルールの一部・実際の設定）をひとつ見せて「本当にやっている人」の信頼感を作る。全部公開する必要はない。断片で十分
- リンク型も「記事書きました」ではなく、読みたくなる入口として設計する
- **AIと人は対等な目線で発信する**：「AIはこういうものだ」という断定を避け、「気がします」「思います」などで出す

---

## 2. 最重要ルール

```
説明を書くな。変化を書け。

知識を書くな。体験を書け。

AIを説明するな。AIを使って自分がどう変わったかを書け。

記事を要約するな。記事を読む理由を書け。

気づきだけで終わるな。断片を見せろ。
```

**品質基準：90点未満は出さない。**
弱いと判断したらテーマから見直し、別テーマを提案する。「一応これで」という案は出さない。

---

## 3. 投稿の優先順位

1. 一次情報（自分が実際にやった）
2. 変化（Before→After）
3. 数字（時間・本数・割合）
4. 気づき
5. リンク

---

## 4. 必ず入れるもの

できるだけ以下のいずれかを含める。

- Before→After
- 実際の数字（時間・本数・回数）
- 実体験
- 感情（迷い・驚き・気づき）
- 変化
- **実務の断片**（実際に使っているREADME・ルールファイル・設定の一部）← 気づきに加えることで再現性が生まれる

**良い例：**

```
× AIは便利です

○ 44本書いたら
  8時間 → 4時間になった
```

```
× Gitは便利です

○ 「最新版どれ？」
  がなくなった
```

## 5. NG（禁止）

以下は出力しない。

**説明だけの投稿**
- 「Gitとは〜」「READMEとは〜」「Claude Codeとは〜」

**一般論**
- 「AIは便利です」「AIは仕事を変えます」「Gitはおすすめです」

**まとめで終わる**
- 「だから重要です」「役立ちます」「おすすめです」

**記事の要約**
- 記事内容をそのまま140文字にしただけの投稿

**情報だけ・ニュースだけ・リンクだけ**

**気づきだけで終わる**
- 「環境を作る方が大事だと感じました」← 具体例がなく、誰でも書ける投稿になる

---

## 6. 良い投稿の基準

以下のどれかになっているか確認する。

- 自分が変わった
- 作業が変わった
- 時間が変わった
- 考え方が変わった
- 失敗した
- 数字がある
- 比較がある
- **気づき + 具体例（断片）がセットになっている** ← これがあると「この人は本当にやっている」になる

---

## 7. 出力前チェック（省略禁止・7項目）

① スクロールを止める1文目か
② 説明ではなく体験か
③ 具体的か（数字・固有名詞・状況）
④ 一般論になっていないか
⑤ 「自分はこうだった」になっているか
⑥ 140文字以内か
⑦ 最後に余韻があるか（断定で終わっていないか）

---

## 8. 投稿種別ごとのルール

### リンク型
「記事を書きました」は禁止。必ず「読む理由」を書く。

```
× Gitの記事を書きました

○ Gitってエンジニア向けだと思ってました。
  でもAIと作業するようになって、
  「変更を記録する」
  という考え方がかなりしっくりきました。
  [リンク]
```

### ニュース・AI動向型
ニュース紹介で終わらせない。必ず実務または自分の実験につなげる。

### Claude Code関連
「コード生成ツール」ではなく「仕事を整理するツール」として扱う。

### Git関連
Gitの説明は禁止。Gitを使って何が変わったかを書く。

### README関連
READMEの説明は禁止。READMEで何が変わったかを書く。

### 断片公開型（軸①の強化版）
気づきだけで終わらせない。実際に使っているルール・README・設定の「一部」を見せて再現性を加える。全部公開する必要はない。

**基本構成：気づき → 断片 → 気づき**

```
気づき（Before）：「ゼロから構成を考えなくなった」
断片（運用の具体）：「確認・調整する時間が増えた」
気づき（After）：「判断する仕事になってきた」
```

単なる感想でもノウハウでもなく、「運用している人の観察」になる。これが軸①の基本型。

```
× Claude Codeって、環境を作る方が大事だと感じました。

○ Claude Codeって、
  一番すごいのはAIじゃないかもしれません。

  README.mdに
  ・文体
  ・読者
  ・NG表現
  を書いておいたら、
  毎回説明することがなくなりました。

  「会話」じゃなく
  「環境」を作る方が大事だと感じています。
```

## 9. 投稿するかどうかの選定基準（テーマ決定時に必ず確認）

**「この投稿じゃないと読めない一次情報はある？」**

なければ没。記事リンクだけにする。

**強い投稿の条件：永井さんにしか書けないか**

- メルカリ出品が半分になった → 永井さんしか書けない
- 44本書いて8時間→4〜5時間 → 永井さんしか書けない
- Gitで「最新版どれ？」がなくなった → 永井さんしか書けない
- 「プロンプトを設計書として渡す」 → 記事の要約。誰でも書ける → 没

**戦略：量よりホームラン**

毎日投稿より、「永井さんしか書けない一次情報」を出す方がアカウントが強くなる。テーマが弱いなら記事リンクだけにして、気づき型は出さない判断をする。

## 10. 最終確認の問い

投稿を書き終えたら必ず自問する。

> この投稿は「へぇ」で終わるか？
> それとも「この人、実際にAIで仕事してるんだ」と思われるか。

前者なら全面的に書き直す。

## 10. 良い投稿の例（再現すべきトンマナ）

下書きを作る前に以下を読んで感覚をそろえる。

### 例①（メルカリ-気 / 軸①AI実験ログ）
```
メルカリの出品って、
ルーティン作業ですよね？

Claude Codeでどこまで時短できるか試したら、
一回の出品時間が約半分になりました。

でも、写真を撮ることやサイズを測ること、
最終的な判断は、結局自分です。

どれだけAIをうまく使えても、
「人がする仕事」は残る気がしています。
```
→ 問いかけの開き→数字→逆説オチ。「便利」で終わらない。

### 例②（no.55 / 軸①AI実験ログ）
```
ルールファイルは自分で書くものだと思っていました。

今は、Claude Codeと一緒に育てています。
```
→ 「過去の認識 → 変化」の最短形。余韻で終わる。

### 例③（no.58 / 軸①AI実験ログ）
```
44本書いて、
作業時間が8時間から4〜5時間になりました。

「ここはAI、ここは自分」
が見えるようになってきた気がします。
```
→ 数字→抽象化の順。「気がします」で断定しない。

### 例④（README-気 / 軸③Rシリーズ連動）
```
Claude Codeって、
一番すごいのはAIじゃないかもしれません。

README.mdを置くだけで、
毎回説明していた前提が共有される。

「AIと会話する」より
「環境を作る」方が大事なんだと感じました。
```
→ 「一番すごいのはAIじゃない」という逆張りで開く。最後の一文が哲学まで昇華していてRTされやすい構造。

### 例⑤（Git-気 / 軸③Rシリーズ連動）
→ テーマ：最新版に迷う→Gitで迷いが減った→失敗しても戻れる環境
→ 「問題シナリオ → 変化 → 余韻」の構造

### 例⑥（Git-リ / 軸③Rシリーズ連動）
```
Gitってエンジニア向けだと思ってました。

でもAIと作業するようになって、
「変更を記録する」という考え方がかなりしっくりきました。

記事にまとめています。
[リンク]
```
→ リンク型のお手本。「読む理由」が冒頭の認識転換になっている。

## 11. 制作手順

**気づき型のロードマップ登録条件（必須）**
テーマだけでのストックは禁止。以下が決まった段階で登録する。
- テーマ（何について）
- 断片・核（具体的に何が変わった・何をしているか）

```
× レビューの仕事が変わった（テーマのみ）
○ レビューのとき最初に見るのが内容ではなくレイアウトに変わった（断片まで確定）
```

1. **テーマ＋断片決定**：投稿済み一覧を踏まえテーマと核を1案提示。断片が弱ければ別テーマを提案する
2. **インタビュー要否の判断**
   - リンク型：元記事があるためインタビュー不要。本文を作成する
   - AI動向型：公開情報に実務視点を加えて作成。実体験が必要な部分のみ確認する
   - 気づき型（断片型）：断片がまだ曖昧な場合は1〜2問だけ確認して核を固める
3. **投稿文作成 → 90点チェック → 提示**：90点未満なら出さずテーマから見直す
4. **投稿後**：`sns/posts-stock.md`の投稿済み一覧に追記し、ストックから削除する

## 14. CCの自動ストック動作（省略禁止）

以下のタイミングでCCは確認なしに`sns/posts-stock.md`の断片ストックに追記する。

- **日常作業中**：「これ面白い」「気づいた」「意外だった」を含む発言 → X可否を即判断してストック
- **記事公開時**：公開記事をReadしてX可否を即判断。X向きなら断片をストック、SEO向きなら「X投稿見送り」と記録
- **定期リサーチ後**：research/更新時にX向きネタがあれば断片ストックに追記

**X可否の判断基準（3秒で判断）：**
「知らなかった」「すごい」「自分もやりたい」のどれかが動くか。数字・あるある・感情フックがあるか。なければSEO向きとして記録して終わり。

## 15. セッショントリガー

### 「次の投稿内容を教えて」

CCが以下を実行して投稿を1本提示する：

1. `sns/posts-stock.md`の断片ストック・ロードマップ・投稿済み一覧を読む
2. 直近の投稿と開き方パターンが被らないか確認
3. 最適な1本を選んで以下のいずれかを提示：
   - **リンク型・断片が明確**：CCが140文字で組み立てて提示（インタビュー不要）
   - **気づき型・断片が明確**：CCが140文字で組み立てて提示
   - **気づき型・断片が曖昧**：GPTへのプロンプトを提示（インタビュー込み）
4. 80点以上にならないと判断したら別の断片を選ぶ

### 「投稿完了しました」（または投稿内容を貼った場合）

CCが以下をすべて実行する（確認不要・自動実行）：

1. `sns/posts-stock.md`の投稿済み一覧に追記
2. 断片ストック・ロードマップの該当項目を完了マーク
3. `~/Documents/GitHub/tasks/README.md`のX継続投稿セクションを更新
4. 両リポジトリをコミット
